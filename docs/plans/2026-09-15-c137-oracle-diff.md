# The c137 anchor, audited against its own artifacts

**The question:** can we read c137's source and copy how it gets its LongMemEval-S
number?

**Answer: no — the implementation is withheld. But the package it publishes is worth
more than the code would have been, and it moves three cards.**

Everything below is free. One `git clone`, no API calls.

---

## 1. What is actually published

`github.com/ra1ngod/c137-runner` — **MIT** for scripts and scaffolds (benchmark content
remains LongMemEval's, redistributed for verification).

It is the **answer stage only**. In their words:

> "ingestion and retrieval ran inside the c137 pipeline against a live database; they
> are **not packaged here**."

So the two stages we would most want — extraction and retrieval — are exactly the ones
missing. There is nothing to copy.

What is there, and why it is better than source would be:

| artifact | what it gives us |
|---|---|
| `prompts/<qid>.txt` × 500 | **the exact memory context their retrieval surfaced for every question.** A per-question oracle. |
| `scaffolds/gemini.txt`, `gpt4o.txt` | the answer-stage prompt, disclosed in full |
| `published/{pro,flash,gpt4o}.grading.json` | per-question judge labels for all three runs |
| `questions.json` | qid → question, type, gold |

All 500 qids match ours; **all 24 of our failures are present.**

---

## 2. The anchor is a model choice, not a memory score

The three published runs share **the same 500 frozen memory contexts** — same ingestion
(an open-weight **Qwen3-235B** extractor), same retrieval. Only the answer model differs:

| answer model | full 500 | **on the same 100 we scored** |
|---|---|---|
| `gemini-3.1-pro-preview` | 470/500 = 94.0% | **91%** |
| `gemini-3-flash-preview` | 455/500 = 91.0% | — |
| `gpt-4o` | 412/500 = 82.4% | **80%** |
| **ours — `claude-sonnet-4-6`** | — | **76%** |

**11.6 points of spread on identical memory, purely from the answer model.**

This reframes the whole track. "We are ~14 points behind c137" was never a statement
about memory quality; it compared across a variable nobody controlled for. The honest
statements are:

- We are **4 points** behind c137's GPT-4o configuration.
- We are **15 points** behind their Gemini-Pro configuration.
- **We beat c137-Pro on 3 of the 100** (`d6233ab6`, `dd2973ad`, `7405e8b1`).

The stale "90.4%" in project memory has been corrected.

---

## 3. Our 24 failures, cross-referenced against their labels

**c137-Pro also failed 6 of our 24. It solved 18.**

That is the number that should govern the roadmap, and it cuts *against* comfort:
**three quarters of our failure set is demonstrably winnable** — someone else won it, on
the same corpus, with the same labels.

| our 24 | c137-Pro | c137-GPT-4o |
|---|---|---|
| solved | **18** | 13 |
| also failed | **6** | 11 |

**The 6 c137-Pro also failed** — `0a995998`, `7024f17c`, `88432d0a`, `9a707b81`,
`6e984301`, `5809eb10` — are a meaningful list:

- **2 of the 3 TASK-368 bad-gold rows are here** (`0a995998`, `7024f17c`). Independent
  corroboration of that audit from a system with no stake in it.
- `9a707b81`, `6e984301`, `88432d0a` are the date-arithmetic and counting rows. Hard for
  everyone.
- **`5809eb10` is one of TASK-366's two extraction-gap rows** — and their retrieval did
  not surface "2014" either. See below.

**The bad-gold row they DID solve:** `eaca4986`. Their context holds both the note
sequence and the word "chord", and they answered it. So the row is winnable by being
less pedantic than we were — which **weakens TASK-370's "must not fix" classification**
for it. Our answer was defensible; it was not the only defensible answer.

## 4. The oracle, on the rows where our extraction lost the value

This is the decisive check. For each row TASK-361 attributed to extraction loss: does
*their* retrieved context contain the value ours dropped?

| question | value our Observer dropped | in c137's context? | c137-Pro |
|---|---|---|---|
| `352ab8bd` | `20%` / `HAMT` / `framerate` | **yes, all three** | PASS |
| `gpt4_5438fa52` | «cultural festival» | **yes** | PASS |
| `5809eb10` | `2014` | **no** | FAIL |

Two of three are **confirmed fixable**: a different extraction pipeline, run on the same
sessions, kept exactly what ours discarded. The third defeated both systems.

**And here is the target representation.** For `352ab8bd`, their memory carries *both*
halves — the activity *and* the document's contents:

```
### research summaries
- [2023-05-22] user requested a borderline review of a research paper on real-time
  adaptation for semantic segmentation

### algorithms
- [2023-05-22] Assistant provided a summary of the Experimental Results section from the
  HAMLET framework paper, detailing performance improvements in real-time domain
  adaptation on OnDA benchmarks and the SHIFT dataset, including a 20% average framerate
  gain with HAMT and a 4x further improvement with Active Training Modulation, plus up
  to 4-point reduction in synthetic-to-real performance gap.
```

Our tree for the same session held **five facts, every one about the review activity** —
the 8/10 review, the 2/10 review, the borderline 6/10, the Program Chair's reject — and
none about what the paper said.

So TASK-366's mechanism is confirmed with a worked target, and the fix is not "extract
more". It is **one dense, dated, attributed fact carrying the figures**, filed under a
topical header, *alongside* the activity fact rather than instead of it.

Two incidental observations from their memory format, both of which corroborate our own
measurements:

- Their headers include **empty sections** (`### training procedures` with nothing under
  it). Dead map lines exist in their system too — consistent with our finding that map
  fidelity is not the lever.
- They **do** extract assistant content, explicitly attributed ("Assistant provided a
  summary of…"). Our assistant-content extraction (25.9% → 87.0%) went the same way. The
  "dual-sourcing rule — only user messages create persistent facts" recorded in project
  memory from their earlier write-up is **not** what this artifact shows.

## 5. The scaffold maps onto our failure profile almost line by line

`scaffolds/gemini.txt` is 5,962 bytes, MIT, and disclosed in full. It is **honestly
labelled as benchmark-tuned** — "These are bench prompts, not c137 prod prompts" — which
is the caveat to carry into any adoption. But read against our 24:

| scaffold rule (abridged) | our rows it would have caught |
|---|---|
| "the actual occurrence over a mere **intention** ('thinking of', 'planning to')" | `gpt4_4fc4f797`, `gpt4_e061b84f`, `88432d0a` — **exactly TASK-363** |
| "**take the NEWEST dated value and COMMIT to it** … never average it with an older figure and never fall back to an older exact number" | `a2f3aa27` (we said "1,250–1,300"), `6a1eabeb` (we returned the stale 27:12) |
| "A newest value phrased approximately ('around/about/nearly/close to X') **resolves to X; state X**" | `a2f3aa27` |
| "**LITERAL QUALIFIER** … if it names a window, exclude anything dated outside it" | `gpt4_7f6b06db` (Sequoia, outside the window) |
| "**EVENT-DATE ANCHORING** … resolve that offset AGAINST the fact's [date] … **Do not abstain when a dated fact records the event**" | `9a707b81` (had both dates, refused to subtract), `c9f37c46`, `6e984301` |
| "**GIVE THE ANSWER UNDER EACH READING** … '3 — or 4 if the borderline item counts'" | the hedging rows — `4b24c848`, `7024f17c` |
| "**ALWAYS finish with a clean, one-sentence statement** … a grader reading only your conclusion must get it right" | `4b24c848` ("at least 5" buried mid-answer), `7024f17c` replay |
| "**Preference-centred answers** … RECALL the stored facts … and LEAD with them … do NOT drift into generic advice" | `32260d93`, `d24813b1` — both our preference failures; c137-Pro passed both, GPT-4o failed both |
| "Abstain ONLY when the asked thing is genuinely absent" | the false-refusal bucket generally |

**"Give the answer under each reading" is the resolution to TASK-370's tension.** That
card was written around a real worry: making the agent more decisive trades away
abstention, which is the property this system is supposed to be best at. The scaffold
does not resolve it by hedging less — it resolves it by **committing to an answer per
reading**. That keeps calibration *and* satisfies a grader, and it is a better shape than
the one TASK-370 currently proposes.

## What this changes on the board

| card | change |
|---|---|
| **TASK-366** | **Confirmed, with a target representation.** Keep. The sizing run still earns its ~$2 — but the fix is now specified, not open-ended. |
| **TASK-363** | **The fix may be one scaffold sentence**, not an extraction change. "The actual occurrence over a mere intention" is testable for the price of one run. Try that before touching the Observer. |
| **TASK-370** | **Rewrite.** Not "hedge less" — adopt the answer-under-each-reading + newest-value-commits + finish-with-one-sentence rules, and keep the abstention guard. Higher value than the 2–3 points it was scoped at. |
| **TASK-369** | Unchanged and still first. Their own rerun churned **19/500 labels (3.8%) at temperature 0**, balanced both ways — external corroboration of TASK-365 and a reference noise floor. |
| *new* | **An answer-model arm is now a measurable, unexplored lever.** 11.6 points of their spread is the answer model alone. We have never varied ours. |

## The honest caution

The scaffold is **tuned on this benchmark and says so**. Adopting it wholesale is
benchmark-fitting, and a number bought that way does not transfer to the product. The
rules worth taking are the ones that are simply correct reasoning discipline — plans are
not occurrences, the newest value supersedes, lead with what you know about the user —
and each should be justified on its own merits before it ships, not because it moved a
score.

## Reproducing

```bash
git clone --depth 1 https://github.com/ra1ngod/c137-runner
python3 - <<'PY'
import json, os
S='c137-runner'
pro=json.load(open(f'{S}/published/pro.grading.json'))
ours={r['questionId']: r for r in (json.loads(l) for l in open(os.path.expanduser(
    '~/.cache/ax-memory-bench/longmemeval-s-e2e/2026-09-14.jsonl')))}
both=[q for q in ours if q in pro]
ok=lambda q: ours[q]['verdict'] in ('correct','abstained-correctly')
print('same-100  ours=%d  c137-Pro=%d' % (sum(map(ok,both)), sum(pro[q]['label'] for q in both)))
fails=[q for q in both if not ok(q)]
print('of our %d failures, c137-Pro solved %d' % (len(fails), sum(pro[q]['label'] for q in fails)))
PY
# does their context hold what our extraction dropped?
grep -c '20%' c137-runner/prompts/352ab8bd.txt      # 352ab8bd -> present
grep -c '2014' c137-runner/prompts/5809eb10.txt     # 5809eb10 -> absent (they failed it too)
```
