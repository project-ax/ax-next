# TASK-919: immutable run classification for memory capture

Base inspected: `97b4aba367f9f1663f0d77d6496535cd9d2a8557` (schema 14).

## Evidence and decisions

`acceptDispatch` locks the definition, builds `AcceptedDispatch.row`, and inserts its dispatch in the same `receiptTransaction`. `receiptCopy` removes mutable task state from its settled result but retains the accepted definition, including explicit `row.kind`. Thus existing dispatch receipts can prove historical kind without looking at today's definition. Their `dispatchId`, `reqId`, `row.agentId`, `row.routineId`, and `row.revision` can be matched to the dispatch. Missing or malformed kinds are not proof: do not apply a schema default of repeat while reconstructing history.

`taskConversationQuery` currently joins the mutable definition and checks `r.kind`. This is the actual defect. It already scopes by agent and conversation and uses the version-5 conversation index. `taskCaptureVeto` checks both host context and payload conversations, regardless of source, within half memory's subscriber timeout. Preserve that behavior.

Dispatches survive `deleteAuthored`, owner changes, completed runs, host restart, and ordinary maintenance (there is no dispatch retention pruning). Only `purgeAgent` removes them, under the lifecycle fence; agent deletion also removes conversations and memory. No new retention/tombstone system is needed. A shared conversation is unsafe if any bound run is task or unknown, even if another run is known repeat.
