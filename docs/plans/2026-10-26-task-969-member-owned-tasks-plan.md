# TASK-969 — member-owned tasks on team agents

Source: `docs/plans/2026-10-20-agent-tasks-design.md` §12 PR 4 and the supplied TASK-969 card. Base: `68e734184`. This is a permission and ownership change, with the existing routines plugin retaining all state and execution ownership.

## Decisions from current code

- `agents:can-manage-routines` currently calls `connectorsManageAllowed`, which requires team-admin role. Split this into a routine-specific predicate: a personal agent's owner or any current member of the owning team may create/manage their own work. Ignore workspace-admin status as today. Missing teams provider denies; every other dependency error propagates.
- Keep connector administration, shared credentials and per-agent webhook token read/ensure/rotate on their existing narrower rules. A team member gaining routine creation must not gain any of those capabilities. The current address embeds an agent-wide activation token, so even an own-task address can reveal authority over teammates' webhook routines. Do not expose it to ordinary members or implement PR 5's token migration. If a member's webhook needs an administrator to finish setup, expose a truthful capability/restriction for downstream Tasks UI rather than widen token access.
- Extend the existing host-only `agents:can-manage-routines` answer with required `stopOthers: boolean`, a capability rather than a role label. It is true only for a proven current team admin. Return both fields from one membership read. Do not introduce a second permission hook or import agents from routines.
- `routinePermissions(row, caller, allowed, stopOthers = false)` remains the single row-policy helper. Edit/fire/secret management need current membership and the row's execution owner; stopping/deleting an authored row needs either its owner or `stopOthers`. Defaults retain their current special behavior. Pass the capability through `resolveRoutineAccess`, views and tool preparation. Existing lightweight mocks lacking it must fail closed for other people's rows, never infer it from `allowed`.
- Repair **both** pre-existing shortcuts when broadening `allowed`: services.update accepts any stop-only patch today; tools.prepare accepts any stop-only update receipt. Use the same row policy for those paths, including replay. Never return a stale privilege snapshot as new authority. Delete receipts contain no private row and stay actor-scoped, with live agent access rechecked.
- Add required `ownedByCaller: boolean` to `RoutineViewShape`, and explicitly set it from `row.ownerUserId === caller` in `routineView`. This is independent of the owner's current write authority and reporting state. It applies consistently to full views and the smaller list/update tool views. No owner ID is added to a public shape.
- Tasks list/detail reads use `ownedByCaller === true` in `isOwnTask`, with the appropriate `Pick` fields updated. Their final SPA responses remain field-by-field projections; they need no new owner identifier. A never-reported task remains visible to its owner when write permission is lost, while teammate report/fire-shaped mocks cannot manufacture ownership.
- Preserve TASK-936/947's reviewed history policy: teammates can see **live run metadata**, never another owner's report; deleted-task runs list only for their execution owner. Do not silently redefine metadata visibility. Private task reports, notes, steps, replies and check-in transcript routes keep their existing owner gates.
- Execution already sets `ownerUserId` from the authenticated creator, persists it on accepted dispatches, resolves the owner again in `fire.ts` before creating a conversation, and invokes with that owner context. Prove those paths through the real bus; add runtime code only if the regression exposes a real gap. Do not add a redundant identity store or substitute an admin.

- Sandbox/capabilities: current members gain execution of their **own** saved work under their own identity; no connector, credential-selection, token-rotation or teammate execution authority. No new filesystem/network/process/env capability.

- Supply chain: no new dependency or manifest version change is needed.

## Review corrections and complete signing-secret setup

The first independent review found that tool recovery could return a previous stop receipt as success after an administrator lost stop authority during authorization. Recovery now uses the same current row policy as live execution. One exact stop-only classifier is shared by the service, preparation and recovery; a patch with another field requires edit permission. Six actual HookBus regressions cover demotion at authorization, membership loss, legitimate lost-response recovery and owner edits after demotion. Two assertions failed before the fix; the focused recovery/tools/returns group then passed all 45 tests. The receipt's original actor fence remains intact.

Own signing-secret service permission also needs HTTP and UI reachability. Keep every `/admin/credentials` and `/admin/destinations` gate intact. Only `routine-hmac` gains authenticated settings writes, still carrying its exact agent destination and revision into `routines:set-webhook-secret`. The settings presence read authenticates the caller, asks `routines:get` for current central `manageSecret` authority and projects scoped credential metadata to `{ configured: boolean }`. Other owners, including administrators without ownership, receive 404. No secret bytes, credential references or unrelated metadata leave this route; read failures return 503, never false unset.

The actual HTTP regression starts the real HTTP server, encrypted SQLite credential vault and routines services, with an isolated fixed routine repository and authenticated directory stubs. It tests member Save/Delete through the real wire client, configured status, peer/admin nonowner denial and unchanged admin/global-list restrictions. Six of seven cases failed on old production behavior. The member list gate, client routing and row/form state tests had seven failures before UI changes. The row now reads only its own status, offers Remove for a configured secret, names a retryable read failure and isolates drafts and pending responses by destination/scope. Existing primitives and tokens remain the UI language. Agent-wide webhook token read/ensure/rotation is unchanged; receiver-address setup still requires the existing manager authority until PR 5.

This adds no service-hook signature or IPC action. The HTTP output schema lives in routines-contract and is shared by the host adapter and client. Credentials-admin-routes declares its existing `routines:get` service dependency. Alternate routine/directory/vault implementations can return the same ownership/capability and presence response without exposing backend fields.
