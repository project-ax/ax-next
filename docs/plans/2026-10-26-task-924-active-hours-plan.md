# TASK-924 — selected days and reliable active hours

Implement the supplied TASK-924 card and its PR4 addendum. Support overnight windows; selected days name the day a window starts. Keep one scheduling implementation in `@ax/routines`, and compose the existing shadcn controls in channel-web.

## Evidence and decisions

- `routines/src/active-hours.ts` currently tests `candidate >= start && candidate < end`, so an overnight window is never active. Its two-pass local-time conversion can return a nonexistent, earlier, or outside-window instant around DST. `services.ts: routineView` trusts that answer as the promised next run; `tick.ts` uses it to defer execution. This is the measured TASK-910 review finding, not a hypothetical redesign.
- `ActiveHoursSchema` currently has only start/end/timezone. The tools already claim overnight windows work. The design's §§3.2/3.3 explain that weekday selection waits for PR4. Correct the as-built notes when this slice ships; leave historical memory archives unchanged.
- TASK-970 PR1058 (reviewed `855a610e2d737d5a957e8cc195dae53c40ced39f`) is not merged yet. It changes triggers to nullable `schedule` and `webhook`, and provides post-receipt `validateScheduleWrite`. Integrate its actual merged main before final implementation/review; do not copy its branch or implement another trigger adapter. Existing tests can first demonstrate overnight/DST defects against today's base.
- Use domain days `mon,tue,wed,thu,fri,sat,sun`. `days` is optional: omission stays omitted in parsed legacy definitions, hashes, stored snapshots, and requests. Only runtime and UI interpretation treats omission as all seven. A supplied set is nonempty, unique, closed, and sorted Monday-first for semantic request identity. Do not default an array into legacy data or change TASK-970's measured byte allowance.
- Reject equal start/end on fresh effects. Historical equal windows remain structurally readable, including completed receipts. They receive a repair-needed schedule posture with no promised next run; scheduled execution refuses them. Never clear the hours, fabricate a runnable time, or globally pause a dual-method Repeat, because app updates ignore schedule hours.
- No new dependency, schema migration, timer engine, hook, authority, or broad clock abstraction is needed.

### Runtime

- Make `advanceToNextActiveWindow` return `Date | null`: null means no safe runnable candidate, including historical equal windows. Use one common membership predicate for current candidate and future search. For overnight membership, the early-morning portion uses the **previous local calendar day**. `24:00` remains an end boundary; start24:00 remains invalid.
- Search real UTC minutes, with one `Intl.DateTimeFormat` per call and `hourCycle: h23`, rather than guessing local instants. Keep an already-active candidate byte-for-byte, seconds/milliseconds included. Otherwise start at the next real minute and advance strictly forward. Bound the search at16real days (23,040 minute checks), enough to skip a selected DST window that disappears entirely and reach the following week. Return null on exhaustion/date overflow; never spin or return an earlier/outside-window candidate. A read-only Node benchmark of11,520 `formatToParts` calls with one formatter took22ms locally; keep formatter construction out of the loop. No unbounded cache is needed.
- Run the expensive future search only when the current candidate is outside the allowed window. Preserve unchanged legacy fast-cron seconds while already inside; this change must not clamp cadence. After implementation, measure the **actual** `routineView`/runtime helper across a realistic100-row mix (mostly already-active, some next-day, a few weekly deferrals) plus a separately named worst-case batch. Record timings and search counts in scratch and the handoff, without a flaky wall-time test threshold. The single-formatter microbenchmark above is not product-scale evidence. Optimize only if the actual measurement identifies a material problem, while keeping the same shared predicate.
- Wire nullable results through BOTH tick and `routineView`. A null result refuses timer dispatch and supplies `nextRunAt:null`. For an authored claimed row, clear its scheduled target using existing revision-fenced `advance`; repairing hours resets it through the ordinary scheduling change. Default rows retain their required-null target and use existing last-run bookkeeping to avoid a hot claim loop. Preserve the actual default scheduling convention; do not turn this into a new default cadence policy.
- Give invalid legacy windows fixed host repair copy using existing warning/schedule presentation paths, while retaining the original hours for editing. Do not misreport the whole routine as disabled when webhooks still run. Ensure list/get/tool return validation accepts this repair posture.
- Keep the cron engine and its existing deferral behavior: a due cron occurrence outside active hours is deferred to the next allowed opening, just as before. Selected days do not add a second cron parser or change TASK-970's cadence/legacy rules.

Days are inert closed enum data, not cron source or code. Time strings/timezone remain bounded and validated, with a bounded search.
