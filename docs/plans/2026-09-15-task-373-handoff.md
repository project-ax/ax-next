## What is already done — task 1, committed

`ChunkBuffer` can now answer "which pending grants belong to this user":

```ts
appendPermissionCard(key, card, owner?: { userId: string; agentId: string })
pendingGrantsForUser(userId): readonly { conversationId, agentId, card }[]
```

The producer (`createPermissionCardFillSubscriber`, `server/sse.ts`) passes `ctx.userId` / `ctx.agentId`. Nothing calls the accessor yet — this is groundwork with no behaviour change.

**Do not re-litigate these.** They are decided and the reasoning is in the design doc and the commit message:

- **The owner is recorded at append time, not resolved at read time.** Resolving per-read means an N+1 (already filed against `/api/workspace/state`) and a scope re-derived from reader-supplied data. The producer holds the identity; it writes it down once.
- **Host cards are excluded from the accessor.** They are turn-scoped, and `proxy:add-host` widens the *live* session's allowlist — a wall answered after its session has gone offers "just this once", which reports success and changes nothing. That is **TASK-375**, and it needs a different question, not this card replayed. If you find yourself making host cards outlive `evictReqId`, stop: you are building TASK-375 inside TASK-373.
- **An unowned card is never enumerable.** Still replayable on its own stream; just not attributable.
- **Do not fill `Decision.kind: 'grant'`.** It is a reserved enum arm with no producer and no consumer, and it looks like an invitation. `Decision.call: ToolCall` is required and the approve machinery routes on `ExecutionPath` to replay a held call. A grant has no call. Settled 2026-09-12 and re-confirmed 2026-09-15.

## What is left

### Task 2 — `GET /api/workspace/grants`

In `packages/channel-web/src/server/routes-workspace.ts`, matching the posture that file already documents: *"identity is ALWAYS the authenticated user (`auth:require-user` → 401). `userId` is never read from the body, query, or params."*

- No parameters. The caller cannot ask about anybody else because there is nothing to ask with.
- Returns `{ grants: [{ conversationId, agentId, request }] }`.
- No existence leak is possible by construction — the response is built from the caller's own rows, so "no such conversation" and "not yours" are the same empty list.
- The route needs the buffer. Check how the existing workspace routes reach host-side singletons before inventing a way; `server/plugin.ts` already wires the buffer into the chat routes and the SSE handler.

Tests: an authenticated read returns only that user's grants; a second user reading the same deployment gets their own and not the first's; unauthenticated is 401; an answered grant is gone.

### Task 3 — client fetch and merge

- `workspaceApi.grants()` in `lib/workspace-api.ts`.
- `WorkspaceShell` fetches on mount and merges via `workspaceGrantActions.raise(request, conversationId)`.

**Reuse `raise()` — do not add a second entry point.** It already replaces in place on the subject key (`skill:<id>` / `connector:<id>`), so a grant that is both fetched and streamed is one row and the newer payload wins. A separate "hydrate" path is how you get two rows for one grant.

Test the case that matters: fetch a grant, then have the same grant arrive on the stream, and assert **one** row.

### Task 4 — the PR

- `security-checklist` skill. The real surface is **cross-tenant enumeration**: a naive "return all pending cards" leaks skill ids, connector names and hostnames belonging to other people. Task 1's filter is the mitigation; say so and point at the probe.
- **Boundary review is required** — this adds a route, which TASK-350 deliberately did not. Answer the four questions in CLAUDE.md.
- State the known limit rather than implying it away: the buffer is **in-memory and replica-local** (Invariant J7 — the chart refuses `replicas > 1`). A grant survives a page reload, an idle Today and the turn ending. It does **not** survive a host restart.
