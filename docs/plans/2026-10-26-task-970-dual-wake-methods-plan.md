# TASK-970 — independent schedules and app updates

Design: `2026-10-20-agent-tasks-design.md`, §5 and §12 PR 4. Base inspected: `68e734184`. This plan delivers one reviewed PR, including all callers; none of the intermediate steps is a separately shippable half-wired change.

## Decisions and boundaries

- Canonical authored definitions and views have `schedule: RoutineSchedule | null` and `webhook: WebhookTrigger | null`; no mutable `trigger` mirror. A schedule is the existing interval/cron object, including its `kind`. A webhook retains its existing object, including `kind: 'webhook'`, path, events and HMAC configuration. The existing opaque routine ID and computed credential reference do not change.
- Repeat requires at least one method. Stay-on-top/get-done require a schedule and refuse a non-null webhook until PR 5. Root resolved the discovered cadence gap: **new/actually changed repeat schedules, custom cron included, enforce 60 seconds**; task schedules retain their 15-minute floor. Current code accepts sub-minute repeat cron, so preserve its existing stored reads, runtime, completed receipt replay and edits that leave its schedule semantically unchanged. Never clamp or migrate it. Apply the new repeat-cron authoring guard after receipt lookup and against the prior schedule, not globally in row parsing or merely because a field was supplied. Offered repeat interval controls start at 60 seconds.
- A canonical patch changes only supplied keys. Null removes that method; the resulting full definition must remain valid. A legacy `trigger` patch is an explicitly exclusive replacement, as before: normalize to its matching method plus explicit null for the other. Reject mixed `trigger` plus canonical method keys, even if their values appear equivalent. This compatibility rule is deliberately different from canonical omission.
- Preserve `RoutineDefinitionObjectSchema` as the canonical extendable Zod object; put legacy input normalization in a separate boundary parser/preprocess. Do not make every internal object accept both representations. Views and newly stored receipts emit only canonical fields. Stored snapshots normalize before strict validation.
- Defaults remain a separate interval-only catalog/settings concept. Keep their table and current interval-only `trigger` DTO, with an explicit adapter to canonical authored/materialized definitions; do not add app-update controls or authored Tasks to housekeeping. This avoids an unnecessary admin API migration while maintaining one source of truth for each concept.
- Authored/materialized rows use nullable `schedule_spec` and `webhook_spec` JSONB columns, replacing `trigger_kind`/`trigger_spec`. The next migration after the actual integration base atomically backfills and removes old authored columns/index before installing the webhook index on the new field. Catalog defaults retain their own columns. No routine, agent token, path, secret, revision, owner or next-run timestamp is regenerated by migration. Webhook-only rows remain unscheduled.
- Match old create/update receipts through narrowly reconstructed legacy hash candidates only when the canonical request expresses the exact old effect. Hash-only request rows cannot be globally rewritten from their results. Canonical `schedule` omission is never treated as an old trigger replacement. Dispatch hashes are unchanged. Every receipt entry point must use the same candidate comparison.
- Schedule changes affect `nextRunAt`; webhook-only configuration changes do not reset an existing schedule. Webhook dispatch ignores the schedule's active-hours window, as existing repeat webhooks do. Only scheduled dispatch is constrained by work hours.
- TASK-969 owns member/owner permissions. Do not widen any permission here, especially the agent-wide webhook token's read/ensure/rotate capability. Per-task tokens are PR 5. Existing setup remains available only under its current authority.

## PR security and boundary notes

- Sandbox/capability: no new filesystem, process, env or network destination. Webhook HTTP path remains its reviewed domain field, not a filesystem path. Requests remain agent/actor scoped; current HMAC/token/credential and owner-execution checks remain. The schema replacement grants a second existing wake method, not broader tool reach. Agent-wide receiver tokens remain under current authority.
- Injection: definitions/tool calls and webhook payloads are untrusted. Strict schemas, existing size caps, HMAC/filter checks and fenced payload rendering remain; normalization never evaluates strings, resolves paths or constructs a tool call from payload text. JSONB writes remain parameterized. Error projection remains closed and regenerates trusted text.
- Supply chain: no package/lockfile dependency changes planned; N/A with that reason only after final diff verifies it.
- Changed hooks: existing create/update/list/get/default/duplicate result definitions carry canonical method fields. Alternate implementation: a SQLite/external scheduler behind the same domain API. Backend field leaks: none added; `webhook.path`, HMAC header/algorithm and cron expr/tz are reviewed protocol/domain configuration, with their existing strict constraints. Subscribers must read optional independent methods, never assume exclusivity. Wire schemas and manual JSON schemas live in owning `routines-contract`/routines package, no central IPC schema file or cross-plugin implementation import.
- Explicitly deferred: caps/dedupe/queue (TASK-971); unified Tasks/history (TASK-972); New/Edit/housekeeping move (TASK-973); Activity removal (TASK-974); PR 5 inbox/nudges/signatures/per-task tokens/delivery counts/setup UX. These are already tracked, not new follow-ups invented by this plan.
