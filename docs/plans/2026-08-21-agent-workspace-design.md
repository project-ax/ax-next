# Agent workspace — design

**Date:** 2026-08-21
**Status:** design. The clickable prototype at `/workspace` (dev-only, PR `feat/agent-workspace-prototype`) is the executable half of this document; where the two disagree, this document is the intent and the prototype is a sketch.
**Supersedes:** nothing. Extends the agent-centric direction in `2026-04-27-agent-centric-design.md` to the UI surface.

---

## 1. What changes

Today the noun is the conversation. You start a chat, an agent is a property of it, and everything an agent has done lives inside whichever chat you had at the time.

The refresh inverts that. **The agent is the object you navigate to**; a conversation is one of its properties, alongside what it did, what it wrote, and what it remembers. The home screen stops being a chat and becomes a queue of things waiting on a human.

That inversion is cheap. What it *requires* is not: a durable notion of "an agent stopped and needs an answer" that outlives the turn which produced it. Section 3 is that mechanism, and it is the only genuinely new subsystem here. Everything else in this document is either surfacing something we already store or deciding what sentence to put in front of a human.

Which turns out to be the hard part, so it gets the longest section.

---

## 2. The honesty rules

These govern every decision below. They are stated first because most of the specific choices in this document are consequences of them rather than independent judgements.

**H1. Never claim an outcome that was not observed.** A receipt says what happened, derived from the record of it happening. It is never derived from the record of something *else* happening.

**H2. Never state a number the system cannot know.** Elapsed time is knowable. Remaining time is not. A count of processed items is knowable. A percentage of an unknown total is not.

**H3. A claim about reach is a security claim.** Anything that tells a human what an agent may do without asking is load-bearing, and must be generated from the thing that actually enforces it — never written separately and kept in sync by hand.

**H4. Understating reach is worse than overstating it.** A capability that is omitted reads to a human as "it cannot do that". If we cannot describe something, we say so out loud rather than leaving it off the list.

**H5. Third-party prose is evidence, never our claim.** A description supplied by an MCP server, a connector vendor, or an agent-authored skill is untrusted text. It may be rendered as *what they say*, clearly attributed. It is never rendered as *what we assert*.

**H6. No model-generated text on a trust surface at render time.** Prose generated by an LLM cannot be reviewed before a user reads it, cannot be reproduced, and cannot be tested. It has no place in a permissions list or a receipt. (It has a bounded place in a status line — see §4.2.)

**H7. Stale is a state, not an absence.** A surface that stops receiving updates must change what it says. Continuing to display the last known truth is how a hung agent ends up claiming to be working.

## 3. The approvals substrate

### 3.1 `hold` — a third verdict that does not block

`tool.pre-call` carries a **10-second ceiling** (`ipc-protocol/src/timeouts.ts:12`), and `agent-runner-core/src/tool-policy.ts:70` converts *any* failure of that call — timeout included — into `{ decision: 'deny' }`. Two consequences:

- A human can never be waited for inside pre-call. Human latency is not ten seconds, and blowing the ceiling produces a **denial the model then improvises around** — the single worst outcome when the reason for stopping is "a person must see this first".
- Raising the ceiling is not available. Every tool call in the system crosses this path.

So the host answers immediately, and gains a third verdict:

```ts
type PreToolVerdict =
  | { decision: 'allow'; updatedInput?: Record<string, unknown> }
  | { decision: 'deny';  reason: string }
  | { decision: 'hold';  decisionId: string; note: string }   // new
```

(Note the two names for one concept that already exist in the codebase: the runner-facing `PreToolVerdict` in `agent-runner-core/src/tool-policy.ts:17` says `deny`, while the wire schema `ToolPreCallResponseSchema` in `ipc-protocol/src/actions.ts:89` says `reject`. `hold` is added to both, spelled the same on each side.)

`hold` returns as fast as `deny` and differs in meaning: *I have recorded this call, do not retry it, do not route around it, tell the user what you were about to do, and end your turn.* The distinction earns its keep because `deny` invites a workaround — a different tool, a shell command — and "not yet" must not read to the model as "not this way".

The runner's obligation on `hold` is to surface the note and stop cleanly. It never sees the decision resolve.

### 3.2 The Decision row

```ts
interface Decision {
  id, agentId, conversationId
  kind: 'action' | 'grant'
  attendance: 'attended' | 'unattended'
  status: 'pending' | 'executed' | 'dismissed' | 'stale' | 'expired' | 'failed'
  call: ToolCall                    // { id, name, input } — verbatim, from ipc-protocol
  freshness: FreshnessPredicate | null
  summary, detail, preview          // what the human reads
  approvedText, dismissedText       // both authored — see H1
  createdAt, expiresAt, resolvedAt
  staleReason: string | null
}
```

One row, three renderers: the in-thread card, the Today queue, and (later) Slack's interactive message. There is no separate "live approval" concept, which is what makes §3.3's degradation free.

`approvedText` and `dismissedText` are **both stored**. Neither is derived from the other. The mockup this design came from produced its dismissed line by regexing the approved one and shipped *"You took over from Inbox — sent your reply to Priya"* for a reply that was never sent. That is H1 violated by string surgery.

### 3.3 Attendance decides the path

Attendance is a property of the **channel that opened the conversation**, plus a park budget. It is not a synonym for "was this a routine".

| | Attended (web, Slack) | Unattended (tick, webhook) |
|---|---|---|
| `tool.pre-call` returns | `hold`, immediately | `hold`, immediately |
| Decision row written | yes | yes |
| Runner then | parks on `session.next-message` | ends the turn; sandbox reaped |
| On approval | the decision arrives as the next message; **the agent executes its own call** | the host replays `decision.call` through `tool.execute-host` |
| Staleness risk | seconds — not a concern | hours — §3.4 applies |
| Nobody answers | reaper ends the turn; **the row stays in Today** | n/a |

Park budgets: web short (a browser tab is either there or it isn't), **Slack long** (buttons resolve through `session.next-message` exactly like a web click, and conversational continuity in Slack is worth the warm sandbox), tick and webhook zero.

The last row of that table is the point. An abandoned attended approval *is* an unattended one — same row, later. No special case is written anywhere for "the user walked away mid-approval".

### 3.4 The freshness guard

A decision drafted at 7am and approved at 1pm may be approving a world that no longer exists. Replaying the recorded call is byte-faithful to what the human read and **blind to everything that changed since**.

So a `hold` captures a predicate alongside the call:

```ts
interface FreshnessPredicate {
  kind: string;    // 'thread-head' | 'slot-etag' | 'doc-revision'
  value: string;   // opaque token, produced by the tool
  label: string;   // the only part a human reads
}
```

On approval the host re-reads the predicate. If it matches, the call executes. If it moved, **nothing executes** and the decision re-opens carrying what changed, with the predicate re-captured so a second approval proceeds. The primary button re-words itself, because approving now means something different than it did.

Two details that matter:

- The stale row **drops its "checked against…" clause**. That sentence describes hold-time and is false once the guard has tripped; repeating it under an alert saying the opposite is worse than silence.
- Actions that need several calls, or judgement about the new state, take the other branch: approval spawns a scoped one-shot grant and the agent re-checks the world itself. This gives up byte-identity in exchange for adaptability, and is the right trade exactly when byte-identity was never achievable.

### 3.5 Idempotency, undo, expiry

Approving twice sends once — a double click, a retried POST, and two open tabs all collapse to one execution; anything not in `pending` or `stale` absorbs the click silently. Irreversible outward actions carry a **ten-second undo** inline, and an undo retracts the Activity receipt with it (H1: an undone action must not leave a log line claiming it happened). Decisions expire; an expired decision cannot be approved, only re-raised by the agent.

## 4. Where the rail's words come from

This is the section the prototype fakes hardest. Every sentence in the right-hand rail is currently a string in a fixture file. This section is how they are produced for real.

### 4.1 Ranking the sources of a sentence

Any sentence on this surface comes from one of four places, and they are not equal:

1. **Authored in-repo, next to the thing it describes.** Reviewable in the same diff, testable, cannot drift. Highest trust.
2. **Derived mechanically from structure.** Deterministic and often ugly, but never wrong.
3. **Supplied by a third party** — an MCP server's tool description, a connector vendor's copy, an agent-authored skill. Untrusted (H5). Renderable only as attributed evidence.
4. **Generated by a model at render time.** Banned on this surface (H6).

The rest of §4 assigns each rail block to sources 1 and 2, with an explicit fallback path for 3.

### 4.2 "Right now" — the activity line

**What it must produce:** a short present-tense phrase describing an *activity*, an optional real counter, and a start time. Never an outcome, never a percentage, never an ETA (H2).

```ts
interface AgentActivity {
  phrase: string;                                       // "Reading email"
  counter: { done: number; total: number; unit: string } | null;
  startedAt: string;                                    // ISO
  source: 'declared' | 'tool' | 'trigger';              // provenance, for debugging and for §4.2.4
}
```

Three tiers produce `phrase`, in descending precedence. Every tier below the top is always available, so there is never an empty state and never a stale one.

#### T0 — the trigger label (the floor)

`RoutineRow` already carries a human-authored `name` and `description` (`packages/routines/src/types.ts`). A routine called *"Morning email pass"* yields `"Morning email pass"`. Written by a person at routine-creation time, so it cannot be wrong about what the agent was asked to do — only coarse. It never changes during the turn.

For a user-initiated turn the equivalent floor is `"Working on your request"`.

**This tier always resolves.** Everything above it is refinement.

#### T1 — tool-derived (the deterministic middle)

`ToolDescriptor` (`packages/core/src/types.ts:35`) gains two optional fields:

```ts
interface ToolDescriptor {
  // …existing: name, description, inputSchema, executesIn
  /** Present-participle clause, ≤40 chars, no outcome claim. "Reading email" */
  activityPhrase?: string;
  /** Names the unit this tool iterates over, when it iterates. "messages" */
  countable?: string;
}
```

The host's `tool:pre-call` subscriber already sees every call. It sets the activity line from the tool's own `activityPhrase`, and where the tool reports progress, from `countable`. The verb comes from the **tool manifest**, authored in-repo — not from the model, and not from the tool's model-facing `description` (which is written to steer an LLM, not to inform a human, and for MCP tools is third-party text).

This tier is what produces `29 of 41 messages`. It is honest, it is free, and it reads a bit like a progress log: **"Reading email · 29 of 41 messages · started 6 min ago"**.

#### T2 — agent-declared (the charming top)

An agent may optionally set a short status. This is where *"Reading this morning's email"* actually comes from — the definite article and the "this morning's" are context only the agent has.

Because it is model output rendered on a host surface, it is fenced hard:

- **≤60 characters**, single line, plain text. Newlines, markup, and URLs stripped.
- **Rate-limited** to one update per step; a burst is coalesced, not queued.
- **Never a fact anywhere else.** It feeds the status line and nothing else — not the receipt, not Activity, not memory. It cannot become evidence.
- **Never an outcome.** Lint it on the way in: a declared status matching an outcome shape ("Sent", "Cleared", "Finished", past tense generally) is rejected and the line falls back to T1. An agent may say what it is doing; only the system says what happened.
- **Treated as untrusted content** at every hop, per invariant 5.

Cost is one short field per step, which is real but small. If T2 is absent, malformed, or rejected, the line silently drops to T1. Nobody ever sees a gap.

#### 4.2.1 Being honest about the prototype's voice

The copy in the prototype — *"Reading this morning's email"*, *"Summarising #go-to-market"* — is **T2-quality throughout**. The deterministic floor is plainer:

| Tier | What the rail actually says |
|---|---|
| T2 | Reading this morning's email · 29 of 41 messages · started 6 min ago |
| T1 | Reading email · 29 of 41 messages · started 6 min ago |
| T0 | Morning email pass · started 6 min ago |

All three are honest. Only the first is charming. Anyone reviewing the prototype should read its rail copy as the ceiling, not the expected case, and decide separately whether T2 is worth its cost — because **T1 is the tier that ships first**, and the surface must be good at T1 or it is not good.

#### 4.2.2 Staleness (H7)

The line is derived from a stream of steps. If no step arrives for **90 seconds**, the phrase is replaced — not decorated — with the actual elapsed gap (`"No activity for 4 minutes"`) and the state dot goes neutral. If the turn errors, it becomes the error state.

This is the difference between a status line and a lie. A hung agent that keeps saying "Reading email" for forty minutes is worse than one that says nothing.

#### 4.2.3 What the counter may count

Only a countable the tool itself reports, over a total the tool itself knows before it starts. An agent iterating a list of 41 fetched messages qualifies. An agent "working through your inbox" with no enumerated set does not, and gets no counter — not an estimated one.

### 4.3 "What it may do alone" — the permission rows

This block is a **security claim** (H3), and the most important thing on the surface: an autonomy product survives on whether a human believes they know the blast radius.

#### 4.3.1 The rule that carries its own sentence

The sentence is a **field on the policy rule**, authored in the same file, reviewed in the same diff:

```ts
interface PolicyRule {
  id: string;                                  // 'gmail.send.scheduling'
  match: { tool: string; when?: PredicateSpec };
  verdict: 'allow' | 'hold' | 'deny';
  /** Bare infinitive clause, no leading "to", no verdict wording. */
  capability: string;                          // "reply to scheduling requests"
  subject: 'agent';
}
```

The rail renders `capability` through a frame chosen by `verdict`, and prints `id` beside it as the source.

**Why not derive the sentence from `match`.** `gmail.send · intent=scheduling` is not a sentence, and any function that turns a predicate into English is guessing at what the predicate *means to a user*. That guess would be unreviewable and would change silently when the predicate is refactored.

**Why not generate it with a model.** H6. A security boundary described by non-deterministic, unreviewable, untestable prose is not a described boundary.

**Why co-location is the whole trick.** Because the claim lives on the rule, **the only way to change what the UI says is to change the rule**. They cannot drift, because there is nothing to keep in sync. This is the same reasoning as invariant 4, applied to a sentence.

CI enforces it: every built-in rule has a `capability`; a lint checks shape (≤60 chars, starts with a bare verb, no verdict words like "never"/"always"/"asks", no tool identifiers).

#### 4.3.2 The verdict is never in the authored text

The frame comes from the verdict, so an author cannot write an `allow` phrase that reads like a `deny`:

| verdict | rendered |
|---|---|
| `allow` | ✓ Can **reply to scheduling requests** — on its own |
| `hold` | ✋ Can **write to a customer** — asks you first |
| `deny` | ⃠ Cannot **delete anything** |

This closes a real class of bug: someone edits a phrase for clarity, and it now contradicts the verdict it is filed under. With the frame generated, that is unexpressible.

Rows are grouped **allow first, then hold, then deny**. The allows are the risky facts and get top billing; the denies are reassurance and belong at the bottom.

#### 4.3.3 Rules that are not ours

Not every capability comes from an in-repo rule. Three other sources, each handled by trust level (H5):

**Connectors.** A connector manifest supplies its own `capability` clause per exposed operation. Operator-configured and reviewable, so it renders normally — with the connector id as the source rather than a rule id.

**MCP server tools.** `ToolDescriptor.description` is written by a third party, is a prompt-injection carrier, and can straightforwardly misdescribe what the tool does. It is **never rendered as a capability claim**. The row is mechanical instead:

> ✋ Can call `linear__create_issue` — asks you first
> *described by Linear · not verified*

The vendor's description is available behind that affordance, clearly attributed. Our claim is the tool name and the verdict — both of which we control. Their prose is evidence.

**Agent-authored skills.** These are already zero-reach by construction: `packages/agents/src/authored-caps.ts` records that a skill manifest declares no capabilities at all, only `connectors` it references, and a connector's reach is gated at `connectors:resolve`. **So an authored skill never adds a rail row of its own** — the connector rows already cover its reach. A pleasant property we get for free from TASK-100, worth not losing.

#### 4.3.4 Dynamic grants

JIT host grants (`@ax/host-grants`) and connector approvals change the answer at runtime. They are rows too, sourced from the grant record, in their own group:

> **Granted by you** — 14 Aug
> ✓ Can reach `api.linear.app` — on its own · *revoke*

Separating "built in" from "granted by you" matters because the second group is the one a user can act on, and the one they are most likely to have forgotten.

#### 4.3.5 The unmapped row

A capability that reaches the rail with no `capability` clause and no mechanical fallback renders **explicitly**:

> ⚠ Reads your calendar to check availability — *no rule mapped*

Not omitted (H4). For built-in rules this state is a CI failure, so it can only ever appear for third-party or dynamic sources — which is exactly where a human should be told that our description is incomplete.

The prototype ships one of these deliberately, so the state is visible in review.

### 4.4 "This week" — the counters

Numbers from the event store, never prose. What matters here is that each number has **one written definition** that cannot quietly change:

| Row | Definition |
|---|---|
| Handled on its own | tool calls with verdict `allow`, this agent, in window |
| Brought to you | Decisions created, any status |
| You overruled it | Decisions `dismissed` + executions undone |

*"You overruled it: 1"* is the most valuable number on the surface — a product volunteering its own correction count — and it is worthless if its meaning drifts. Hence the table.

## 5. The conversation model

**One current conversation per agent**, long-running and compacted rather than forked. Past conversations move to the rail. Routine fires do **not** appear there — 612 unattended Slack Digest runs would bury the two conversations a human actually had; they are Activity rows.

`packages/routines/src/types.ts` already draws this line as `conversation: 'per-fire' | 'shared'`. The "current" thread *is* `shared`.

Parallel conversations are not removed from the data model, only demoted: "Start a new conversation" archives the current one rather than forking beside it. If that turns out to be wrong, the capability is still there.

Compaction's summarize rung surfaces as a fold marker in the thread — *"Earlier turns were summarised into memory · 34 messages folded"*. This is deliberate: the user is being told that the agent's recollection of this conversation is now a summary. That is a fact with consequences for them, not an invisible cost optimisation.

## 6. Memory, split by owner

Two writers, two sections, labelled:

- **Rules you gave me** — the human's. Verbatim, always injected, never rewritten by rollup, safe to hand-edit.
- **What it worked out** — the agent's. Inspectable and editable, but subject to the same compaction and GC as the rest of the strata, and the UI says so.

The source mockup put both in one editor under the promise *"anything you write here sticks"*. For half the files that promise is false, and a user whose hand-written note is eaten by the strata GC does not forgive it.

---

## 7. One event feed

`ActivityFeed` is a single component. The global Activity page is it unfiltered; the per-agent "What it did" tab is it with `agentId` set. Today's "Done" filter is **cut** — it was a third renderer over the same rows, and the reassurance it carried moved into the digest sub-line, with a link into the real feed.

Three components rendering one collection is invariant 4 violated in the UI layer, and it is precisely the shape that drifts.

The Today headline is **templated from counts**, never generated. *"Nothing has gone wrong"* being wrong once ends the relationship.

## 8. What the prototype fakes

Stated plainly so nobody mistakes the sketch for the thing:

| Prototype | Reality |
|---|---|
| Rail sentences are fixture strings | §4.3.1 — authored on the rule, CI-enforced |
| "Right now" phrases are fixtures | §4.2 — T0/T1/T2 with T1 as the shipping floor |
| Freshness predicates are two hardcoded tokens | §3.4 — produced by the tool |
| Approve executes nothing | §3.3 — agent-executes or `tool.execute-host` replay |
| Attendance is a fixture field | Derived from the channel that opened the conversation |
| No staleness timeout on the status line | §4.2.2 |
| Counters are static | Reported by the tool per step |

## 9. Delivery

Each phase is independently shippable and honest on its own.

| | | Touches |
|---|---|---|
| **P1** | Agent-centric navigation over existing chat | `channel-web` only; no backend |
| **P2** | Activity feed from `FireRow` + audit-log | read-only, no new semantics |
| **P3** | Rail: permissions from real policy, counters from real events | §4.3, §4.4 — forces the `capability` field |
| **P4** | **Approvals substrate** — `hold`, Decision row, attendance, replay, guard | §3. The one that matters |
| **P5** | Scheduled background runs, digest rollup, `AgentActivity` T0/T1 | routines are most of the way there |

P4 is the load-bearing one; everything above it is decoration without it. P3 before P4 is deliberate — authoring `capability` clauses for the existing policy is useful on its own and surfaces how many rules currently have no describable meaning.

Out of scope here: New agent, per-agent settings, connectors UI, day-one empty state. Noted only because **New agent should not be built as the mockup's form** — a textarea and three checkboxes cannot produce a working agent, and the conversational-identity flow already shipped is the better answer.

## 10. Open questions

1. **Is T2 worth it?** The declared status is what makes the rail feel alive, and it is the only place model prose touches this surface. T1 ships first regardless; T2 is a separate decision with a real token cost and a real fencing burden (§4.2).
2. **Who authors `capability` for existing rules?** There is no inventory yet of how many enforced policy conditions exist or how many have a describable user-facing meaning. P3 begins by counting them.
3. **Freshness predicates per tool.** Which tools can cheaply produce one, and what happens to `hold` for a tool that cannot. Current answer — `freshness: null`, execute on approval — is right for `slack__watch_channel` and wrong for anything that spends money.
4. **Cost.** Nothing on this surface shows spend, and background agents running overnight make that a support problem. "This week" is the obvious home.
