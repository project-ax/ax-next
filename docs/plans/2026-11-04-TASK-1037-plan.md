# TASK-1037 Implementation Plan: say when a Repeat edit cancels its waiting app updates

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A saved Repeat's waiting app updates are never cancelled without a notice:
- A kind switch away and back changes nothing.
- Every other edit that cancels them says so by Save, in the Tasks form and in Settings.

**Architecture:**
- The host's rule stays exactly as it is. `repeatConfigurationHash` keeps its six fields and its code.
- `@ax/routines-contract` gains one exported list of those fields, and a routines test pins the list to what the hash really covers.
- `useRoutineDraft` (shared by both forms) gets two changes:
  - a kind switch back to Repeat undoes what the switch away changed;
  - a new flag, `cancelsWaitingUpdates`, computed from the exact definition the save sends.
- TaskForm and Settings' `RoutineForm` each draw one notice from that flag.

**Tech stack:** TypeScript, zod 3 (contract), vitest, @testing-library/react (jsdom) for channel-web, shadcn `Alert`.

**Spec:** the card (below), plus the decisions shard `.claude/memory/decisions/2026-11-04-TASK-1037.md`. Every design call here has its evidence in that shard. Read it before you deviate.

> **Card.** A saved Repeat's waiting app updates are cancelled with no notice in two cases:
> 1. A kind switch away and back: `changeKind` leaves conversation `'per-fire'`, so the config hash changes.
> 2. An edit to `promptBody`, `silenceToken` or `silenceMaxChars`, which are all in `repeatConfigurationHash`.
>
> Fix: restore the original conversation on a switch back, or show the same cancel notice for every edit that changes the hash. Decide which fields really belong in the hash.
>
> **Acceptance:** for each case, a TaskForm test shows the notice, or proves the queue survives.

## Design calls (where this plan departs from the card or the brief, and why)

- **The hash keeps all six fields, and its code doesn't change.**
  - TASK-971 designed it this way: "Prompt, app-update method, conversation policy, silence policy, kind or owner changes invalidate waiting entries" (`docs/plans/2026-10-26-task-971-repeat-admission-plan.md:23`).
  - A waiting update runs with the routine *as it is at claim time*. Dropping a field would let an app's untrusted payload run under instructions or memory it was never accepted for.
  - Removing a field would also change every stored `configuration_hash`. The claim compares those (`repeat-deliveries.ts:64-66`), so every waiting update would be cancelled at deploy.
- **The round trip also restores the schedule.** For a webhook-only Repeat, a switch to a task kind fills in an hourly schedule (`use-routine-draft.ts:145`), and switching back keeps it. That isn't in the hash, but a save would silently add hourly paid runs. Restore it, but only while it is still the filled-in schedule. A schedule the person picked while it was a task stays.
- **The notice covers more than the card listed.** "Memory between runs", the address name, the event filter and app updates switched off all cancel too. All of them come from one flag, computed against the contract's field list.
- **Settings is included.** `RoutineForm` uses the same draft and makes the same write. It is reachable by every user (Settings → Routines → Scheduled), and it has no cancel notice at all today.
- **App updates switched off shows the save notice too**, on top of TASK-1033's help text under the switch. That help is read only while the popover is open; the save notice is what's on screen at Save.
  - The only case left out is a switch to a task kind. The kind-switch notice (TASK-1035) already says it there.
- **No count gating.** The notice doesn't check `delivery.waiting`, matching the two existing notices. The count is a load-time snapshot.

## Review Focus

1. **A webhook-only Repeat round-tripped through a task kind must not come back with an hourly schedule** (paid runs nobody asked for). Pinned by Task 2's hook test and the second row of its TaskForm `it.each`.
2. **A legacy-signature or event-filtered webhook with no real edit must not raise the notice.** `draftDefinition` moves `events` last, so diffing it would see a change that isn't there. Pinned by Task 2's "untouched legacy signature" hook test.
3. **Pausing a saved Repeat must not warn.** A pause keeps the queue. Pinned by the "a pause" rows in Task 2 (hook) and Task 4 (Settings).
4. **Undoing an edit (typing back the saved value) must clear the notice.** Pinned by Task 2's "clears again" hook test.
5. **A prompt edit plus a switch to a task kind says "cancelled" once (the kind-switch notice), not twice.** Pinned by Task 3's "leaves a switch to a task kind…" test.

```ts
  /**
   * A task keeps a schedule and a fresh conversation; Repeat has no response timing or going-well line.
   * Leaving Repeat for a task kind forces a fresh conversation and, when the Repeat had no schedule,
   * fills in an hourly one. Coming back undoes both (the schedule only while it is still the one filled
   * in), so a switch away and back changes nothing: a changed conversation would cancel a saved
   * Repeat's waiting app updates (TASK-1037).
   */
  function changeKind(value: RoutineDefinition['kind']) {
    const toRepeat = value === 'repeat';
    if (toRepeat) {
      const { respondWithin: _respondWithin, ...webhook } = webhookDraft.current;
      webhookDraft.current = webhook;
    }
    const left = toRepeat ? leftRepeat.current : null;
    const hourly: RoutineSchedule = { kind: 'interval', every: '1h' };
    if (toRepeat) leftRepeat.current = null;
    else if (form.kind === 'repeat') leftRepeat.current = { conversation: form.conversation, filledSchedule: form.schedule === null ? hourly : null };
    setForm(f => ({ ...f, kind: value, goodWhen: toRepeat ? null : (f.goodWhen ?? ''),
      schedule: toRepeat
        ? (left !== null && left.filledSchedule !== null && f.schedule === left.filledSchedule ? null : f.schedule)
        : (f.schedule ?? hourly),
      webhook: toRepeat && f.webhook !== null ? webhookDraft.current : f.webhook,
      conversation: toRepeat ? (left?.conversation ?? f.conversation) : 'per-fire' }));
    clearErrors();
  }
```
