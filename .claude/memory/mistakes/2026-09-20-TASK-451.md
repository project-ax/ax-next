# mistakes — TASK-451 (2026-09-20)

## "It passes 24/24 in isolation" does not mean the test is flaky

Two previous builders (TASK-399, TASK-422) saw `consent-focus.test.tsx` fail
under load, re-ran it in isolation, got a clean 24/24, and filed it as a flake.
It was a real one-task-wide window in the product (focus applied from a passive
effect — see the patterns shard). A test that races an effect passes in
isolation **by construction**: there is no load to lose the race to. The
isolation run carries no information about which cause it is.

What DOES discriminate is the failure *shape*. Here it was
`document.activeElement === <body>` while the target `<p>` was mounted,
`tabindex="-1"` and all — i.e. the element existed and was focusable, and focus
had simply not arrived. That is a scheduling window, not CI noise.

## Read the CI log before reproducing

The whole diagnosis came out of `gh run view <id> --log-failed`: the error
annotation carries the full serialized DOM of the received `activeElement`,
which showed the target node present and focusable. Ten minutes of log reading
beat an hour of trying to reproduce a 1-in-hundreds scheduler race locally —
which, tried directly (`--repeats 15` under a load average of 147), did not
reproduce at all.

## Do not reach for "add a `waitFor`" as the fix for a focus race

`waitFor` proves focus lands *eventually*; it cannot prove there was never a
moment where the answer was on screen without it. If the window is real, close
it in the product. The tell that a previous fix had papered over rather than
closed it: TASK-388's comment in this same file said "it is the assertion, not
the product, that was early" — and the same file went red twice more afterwards
on its siblings.
