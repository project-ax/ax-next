## `git checkout -- <file>` to undo a mutation ALSO deletes uncommitted work in that file

Hit today, in my own worktree, with nobody else involved. The documented hazard is a
reviewer subagent running it and reverting the builder's edits. There is a simpler
version: **`git checkout --` restores the file to HEAD, and if the fix itself is not
yet committed, the fix is what you just deleted.**

Sequence: wrote the fix in `App.tsx` (uncommitted) → mutated one line to prove the
test goes red → `git checkout -- packages/channel-web/src/App.tsx` → the whole fix
was gone. The tell was `git diff --stat` listing 2 files when it should have listed 4.

Rule: **commit the fix before mutating anything to prove non-vacuity.** Then
`git checkout --` restores exactly the mutation and nothing else, and it is safe to
run as many mutations as you want. Mutation testing is a post-commit activity.

## Prefer the tool that writes a file over `python3 - <<'PY'` with backticks

Two `Bash` heredocs were refused outright by the worktree-isolation guard
("too complex to verify that it stays inside the worktree") — the trigger appeared to
be embedded backticks / nested quoting in the heredoc body, not the command's actual
target. `Edit`/`Write` went through immediately. Don't spend turns re-quoting; switch
tools.
