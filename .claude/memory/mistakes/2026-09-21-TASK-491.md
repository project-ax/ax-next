# TASK-491 — two measured traps

## 1. The Write tool materialises `\uXXXX` escapes into literal characters

**Measured twice, on two different files, in one task.** Writing a TypeScript source
containing the regex literal `/[\n\r  \u0085]+/g` produced a file whose bytes
held the REAL U+2028 and U+2029 characters, not the six-character escape sequences. Since
U+2028/U+2029 are JavaScript line terminators, `tsc` reported
`TS1161: Unterminated regular expression literal` — an error that reads as a typo in the
regex and is not.

It then happened AGAIN when writing a Python repair script: the script's own
`replacements = {' ': r' '}` became `{literal: literal}`, i.e. a silent no-op,
so the "fix" ran clean and changed nothing. That is the dangerous half — the first failure
is loud, the second is not.

`\n`, `\r`, `\t` in the same files were NOT materialised, so the rule is specific:
**`\uXXXX` escapes, in any file the Write tool creates.**

Workaround that worked: write the source with `python3 -c` building the text from `chr(92)`
and string concatenation, never from a literal escape, and assert afterwards that no
codepoint below 0x20 (other than `\n`) and none of 0x85/0x7f/0x2028/0x2029 survives in the
file. Same family as the already-recorded "NUL byte → git treats the file as binary" note.

## 2. Measuring a surviving mutant beats assuming the test covers it

`escapeStatementText`'s line-break strip is the escape the whole block's structural safety
rests on. Deleting it outright reddened **zero** tests.

The cause was not a missing guard. JavaScript's `\s` already contains `\n`, `\r`, `\t`,
`\v`, `\f`, U+2028 and U+2029, and the separate control-character pass already contains NEL
(U+0085) and the rest of C0/C1 — so the later `.replace(/\s+/g, ' ')` was silently doing
the job and the named constant was redundant. A reviewer reading the file would have
believed the named constant was load-bearing; it was not.

Generalisable: **a surviving mutant on a security control usually means the control is
implemented more than once, not that it is untested.** The useful fix is a test of the
COMPOSITE behaviour rather than of the one line — here, a table over every character that
can start a line. Re-measured after the fix: removing any ONE pass still reddens nothing
(the layers overlap by design); removing TWO reddens 7 cases.

Corollary worth keeping: when restoring a mutant with `git checkout -- <path>`, any
UNCOMMITTED real fix in that same file goes with it. It happened here — a comment written
between applying and restoring a mutant was silently reverted. Commit the real edit before
the next mutant, or apply mutants only to files you have no pending edits in.
