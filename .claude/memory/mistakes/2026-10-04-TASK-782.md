- `2026-10-04` (TASK-782) — **A fixed sleep before a "the window was entered" (non-vacuity) assertion is a CI flake waiting to happen when the code under test does SYNCHRONOUS crypto.** `credential-proxy/src/__tests__/listener-shutdown-race.test.ts` › "listener.stop() while targetTls is mid-handshake does not crash" slept 200ms, then asserted `expect(upstreamSockets.length).toBe(4)`. On PR #912 CI it failed `expected 3 to be 4` on two attempts in a row, and main passed the same day. Cause, measured: `handleMITMConnect` calls `generateDomainCert` before `tls.connect`. The first cert per (host, CA) runs pure-JS node-forge RSA-2048 keygen synchronously, which blocks the event loop. That keygen took 29–65ms locally, with high variance, and every test mints a fresh CA, so every test misses the cache. A timeline probe (40+ runs) put the 4th upstream accept at 33–136ms after the first CONNECT unloaded, and at 236–532ms under 3× CPU oversubscription. In one loaded run the gap between the 3rd and 4th accept was 128ms ([206,206,211,339]). Every run reached 4/4. Fix: `vi.waitFor(..., {timeout: 5000})`. The waitFor is fail-closed, so a tunnel that never dials still reddens. It hides latency only, never a missing dial. Lesson: before you poll, find WHY the state is asynchronous, measure the timeline, and confirm the end state is always reached.
