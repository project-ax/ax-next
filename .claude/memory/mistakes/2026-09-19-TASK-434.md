# TASK-434 — mistakes / gotchas

## `gh api rate_limit` can report a FULL GraphQL budget while GraphQL hard-refuses

**Observed 2026-09-20 02:49–02:59 UTC, repeatedly, across ~10 minutes.**

Every `gh api graphql` call — including the trivial `{viewer{login}}` — returned:

```
{"errors":[{"type":"RATE_LIMIT","code":"graphql_rate_limit",
  "message":"API rate limit already exceeded for user ID 100092."}]}
```

while the REST budget endpoint, polled in the same second, reported the window as
**pristine**:

```
$ gh api rate_limit --jq '.resources.graphql'
{"limit":5000,"remaining":5000,"reset":1789876772,"used":0}
```

`used: 0`, `remaining: 5000` — and the `reset` value slid *forward* on each poll
(…184 → …772), i.e. the REST view kept reporting a brand-new, unused window while the
real limiter still held the debt.

**Why it matters, concretely.** The auto-ship skill's budget guard
(`.claude/skills/auto-ship/references/github-project.md`, the poller's
"refuses to poll when the budget is low" pre-check) reads exactly
`.resources.graphql.remaining` and green-lights on a high number. In this state that
guard reads **5000** and waves the poller straight into a hard refusal. The guard is
not wrong about its own rule; it is reading an oracle that was lying. So:

- **A high `remaining` is not evidence that the next GraphQL call will succeed.** Treat
  the budget pre-check as a way to avoid *causing* exhaustion, never as a liveness
  probe.
- **The only reliable probe is a trivial GraphQL query** (`{viewer{login}}`, ~1 pt).
  Check the response body for `"code":"graphql_rate_limit"` — and note `gh` prints the
  error payload to stdout *and* exits non-zero, so a bare `|| return 1` catches it but
  a `2>/dev/null` swallows the diagnosis.
- This is the same class as the failure already documented in the 2026-09-20 handoff §4
  ("rate-limited `gh project item-list` returns an **error payload**, `jq` renders it
  blank, and a card reads as missing") — an error response wearing the costume of a
  valid answer. Here the costume is worn by the *budget check itself*.

**Consequence for this run:** TASK-434 shipped board-free — the card body was never
read and no progress heartbeat was posted, because GraphQL refused for the whole
session. The handoff records `progress: FAILED-transient`. Work from the design doc and
the handoff when the board is unreachable; do not block on it, and do not retry in a
loop — it burns nothing but wall clock and the refusal is not yours to clear.
