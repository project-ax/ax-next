# TASK-479 — mistakes

- `2026-09-20` (TASK-479) — **`git checkout <ref> -- <path>` writes the INDEX too, which
  silently disarms the mutation-restore protocol.** Mid-mutation-run I used
  `git checkout origin/main -- .claude/skills/auto-ship/SKILL.md` as a mutant (revert the
  whole block), then restored with the prescribed `git checkout -- <path>`. That restores
  *from the index*, and the index now held the origin/main copy — so the "restore" put the
  mutant back, `git status` said clean, and the next mutant was applied on top of a file
  that was not the head. Caught only because the next mutant's Python `.index()` threw on a
  string that should have been there. The prescribed remedy has a gap for this shape:
  `git checkout HEAD -- <path>` is index-proof, and `git status --short` must be asserted
  EMPTY between mutants rather than assumed. `scripts/__tests__/mutation-restore-protocol.test.js`
  enumerates three ways the protocol fails; this is a fourth and it is not in it.

- `2026-09-20` (TASK-479) — **A mutant table measured against an intermediate state of a
  patch, carried forward unedited, is evidence of nothing and reads as evidence of
  everything.** The first (killed) builder recorded `--verify --quiet "…^{commit}"` →
  bare `rev-parse` as **2 red**, i.e. load-bearing. Re-run against the head actually being
  shipped it is **0 red**: a later commit added a `merge-base --is-ancestor` arm that
  catches the same garbage one line down, so the two arms overlap. Its baseline counts
  (19/26) were stale by the same mechanism — a test added afterwards. Nothing in the patch
  was wrong; the *claim about which line does the work* was. Re-run the whole table against
  the head you ship, and date the table with the sha or the state it was taken against.
