# TASK-498 — mistakes and traps

## A survived mutant is usually a real finding, not a missing test

Three of 13 mutants survived and each one taught something different:

- **M5** (drop `ev.kind !== 'turn-error'`): the fixture's permission-card payload
  had no `error` key, so the reason check excluded it anyway and the kind filter
  was never under test. **A test can pass for a reason that is not the one you
  wrote it for.** The payload is opaque; the fixture now carries `error` meaning
  something else, and M5 dies.
- **M7** (ignore `status` in `deriveState`): `readActivity` nulls the line on
  every non-`ok` branch, so the second condition could not be falsified by any
  input. **A guard no input can trip is dead code wearing a guard's clothes** —
  the fix was to delete it, not to write a test for it.
- **M13** (narrow the error row's `threadGrowthKey` to its id): the code was
  right on precedent, but the *comment* was wrong. The display log folds
  turn-errors per turn, so the same id genuinely can return with a different
  reason. Fix the comment, keep the code, and say so in the PR.

## `git checkout HEAD -- <path>` between every mutant, and assert clean

Restoring with the bare `git checkout -- <path>` writes from the INDEX and can
silently reinstate the mutant. Committed before every round and ran
`git status --short` after each restore; both mattered.

## `pnpm -r --no-bail run test` exiting 1 on a flake SKIPS the last three suites

The gate is `build && test && test:eslint-rules && test:scripts && lint`. One
flaky package (`@ax/workspace-git-server`'s `argv-injection` `len-64k` case
timing out at 15 s under load — green in isolation) made the chain stop, so
eslint-rules, scripts and lint never ran and the exit code said "1" for a reason
that had nothing to do with them. **A nonzero gate is not a verdict until you
read WHICH step stopped it, and re-run the steps it skipped.**

## Heredocs and computed python in Bash are refused in a worktree-isolated agent

`python3 - <<'PY' … PY` and `python3 -c` with a runtime-built program both get
refused as "too complex to verify it stays inside the worktree". Write the patch
script to the scratchpad with `Write` and run `python3 <path>` instead. Also:
chaining `python3 patch.py && cd … && python3 -c …` gets the WHOLE compound
refused, so an earlier patch in the chain silently never runs — check the
printed `ok` actually appeared before trusting it.

## A `Record<string, string>` lookup answers for the prototype

`ERROR_LABELS['toString']` is not undefined — it is an inherited function, so
`?? DEFAULT` never fires and the template stringifies it into a user-facing
alert as `function toString() { [native code] }`. Found on the resume by
walking the security checklist, not by review or by any mutant. Latent (reason
codes are host vocabulary) but real, and it had been hand-copied at every reader
until TASK-498 centralised the lookup in `turnErrorText`. **`typeof found ===
'string'`, not `?? default`, whenever a plain object literal is used as a
lookup table keyed by a value from off-box.**

## A source-scan test can be satisfied by a comment quoting the call

`turn-error-discipline.test.ts` decided "surfaced" with
`between.includes('fireTurnError(')` over raw lines — a deleted call whose
comment still quoted the words would have passed. Comment lines are stripped
now, failing closed. **A scan over source text must strip comments before it
asserts anything about the code, or prose can satisfy it.**

## Resuming a killed builder: the branch name is held by its preserved worktree

`git checkout -B <branch>` fails with "already used by worktree at …" because
the dead builder's worktree is preserved and still has it checked out — and
that worktree is off-limits. Work on a differently-named local branch at
`origin/<branch>` and push with `git push --force-with-lease origin
HEAD:<branch>`. Nothing needs to touch the preserved worktree.
