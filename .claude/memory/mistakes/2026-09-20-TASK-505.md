# TASK-505 — I "reproduced" a hang by watching the wrong namespace

**The mistake.** The card's central `MEASURED-BY-PROBE` claim was "`agent:invoke`
hangs 120 s and **creates no runner pod**". I drove a turn against
`kind-ax-next-dev`, polled `kubectl get pods -n ax-next` every 15 s for 100 s,
saw zero `ax-sandbox-*` pods, and posted a heartbeat declaring the hang
reproduced. It was not. **Runner pods live in `ax-next-runners`, a separate
namespace the host's RBAC is scoped to** — `ax-next` never contains one. The pod
had been Running for 2 minutes. Both probe turns had in fact completed in ~4 s
each, with the assistant reply already in the transcript.

**What caught it.** Streaming the host log (`kubectl logs deploy/ax-next-host
-f`) instead of polling pods: `creating_pod {namespace: "ax-next-runners"}` →
`pod_ready` 2.4 s later. The namespace was printed in the log line I had not
been reading.

**Why it matters more than a normal slip.** The card's whole shape is an
*absence* — no pod, no log. A namespace mistake **manufactures exactly that
absence**, so it confirms the brief instead of contradicting it, and every
downstream inference stays coherent. A bug whose evidence is "nothing happened"
cannot be confirmed by looking somewhere and seeing nothing; it needs a positive
signal from the component that would have done the thing.

**Rules I want next time.**

- Before concluding "X was never created", prove the observation channel can see
  an X that *does* exist. One `kubectl get pods -A | grep sandbox` up front would
  have cost 3 s and saved two false conclusions and a wrong heartbeat.
- When the probe's expected result is "nothing", prefer the producer's own log
  over polling the store. `creating_pod`/`pod_ready` are emitted by the code path
  under suspicion; a pod listing is a guess about where to look.
- The transcript is the ground truth for "did the turn run" —
  `GET /api/chat/conversations/:id` showed the assistant reply and would have
  refuted me in one call, at any point during those 100 s.

**Second-order.** The same session's earlier `docker ps` hang and
`TLS handshake timeout` were real (OrbStack wedged; the documented quit/relaunch
fixed it). Two genuinely broken things on one host make a third false one very
easy to believe. Environmental noise raises the bar for evidence, it does not
lower it.
