# TASK-1082 — what bit us (mistakes)

- 2026-11-07 — T2 shipped `@ax/frame-guard` with a `build` script that copied `src/frame-guard.js` into `dist/` and an export map pointing at that copy. It passes on any machine that has run `pnpm --filter <pkg> build` (every local gate, including `pnpm --filter @ax/frame-guard build && test`) and would have failed in CI: CI runs only `pnpm typecheck` (`tsc --build` over project references) before the tests, which never runs a package's npm `build` script, so `dist/frame-guard.js` does not exist there. Dependents then die with "Failed to resolve import" (channel-web's `?raw`) or ENOENT (the Node loader). Found in T3 by reproducing CI: `rm -rf packages/<pkg>/dist && pnpm exec tsc --build packages/<pkg>`, then run the dependents' tests. Serve a non-TS asset from `src/` (export map + `files`) so the only build is `tsc --build`, as `agent-runner-core` did for its bootstrap after the same trap bit it twice. The Dockerfile `--filter` rule in `image-asset-packaging.test.ts` covers the image, not the test run.

- 2026-11-07 — T4: **`git commit --amend --no-edit` in a worktree the orchestrator also commits to rewrote the orchestrator's commit.** I had amended my own T4 commit five times (to keep it one commit between mutation rounds); the sixth time HEAD was the lead's "Log navigation-exfil review finding and scoping", landed 22 seconds earlier, so my three staged edits went into it and its sha changed. Caught because `git log --oneline -1` printed a message that was not mine. Repair, from the reflog: `git reset --soft <their original sha>` (their commit is byte-identical again, my edits stay staged), then commit mine separately. Before an amend in a shared worktree, run `git log -1 --format=%h:%s` and compare it with the sha you expect, or make follow-up commits instead; `git add -A` followed by an amend is also the combination that would sweep in someone else's uncommitted files.
- 2026-11-07 — T6: **my first kill-switch test passed when the purge was broken, so it proved nothing about the route it was written for.** It asserted "blank page + guard warning + no UDP". With the purge removed the bait iframe is itself the live child, `check()` kills the page, and all three assertions hold without the re-entrancy route ever running. Found by predicting the purge mutant's result before running it, not by the suite. Fix: the page logs from inside the callback with the child count it sees and the test requires that line. Rule: when a test can pass by two routes, make the page report which one it took.
- 2026-11-07 — T6: **a first green run of a new browser suite is not stability evidence; the load profile of the whole suite hid a 40% flake.** The ordinary-page anchor check passed 8 full-suite runs and one mutation pass, then failed 5 of 12 runs when one cell was run alone. The only sign in the full runs was ONE unexplained extra red in a mutation result (9 failures where I had predicted 8), whose message my harness had not kept. Rules: chase every unpredicted red at once; keep each failing test's message (not only the first) and the raw JSON per mutant; loop the smallest unit that contains the test (`-t` one cell, 12 runs) before calling a suite stable.
- 2026-11-07 — T6: **my mutation harness counted a mutant that did not compile as KILLED.** `if (false) {` makes TypeScript treat the block as dead code and drop the narrowing inside it (`Property 'attrs' does not exist on type 'ChildNode'`), the build failed, and "no tests ran" fell into the killed branch. The tell was the runtime (0.8 s, no test counts). Use a runtime-false condition TS cannot narrow on (`&& Math.random() < 0`), and give "did not build" its own verdict.
- 2026-11-07 — T6: **a surviving mutant was a missing probe, not a redundant lock.** Removing the `document.write`/`open` locks left all 242 tests green, and the first reading was "the locks are redundant" (true for a plain iframe: the observer sees it). The right question was "what can only this lock stop?": a closed shadow root written at run time, which the streaming parser builds and nothing in-page can see. One probe made the mutant die. Ask that question of every survivor before documenting it as defense in depth.
- 2026-11-07 — review fix: **T4 and T5 wrote "linear in the page size" and "4 MiB is ~0.7 s worst case" from two timings of ordinary pages, and nobody ran one hostile shape at the cap.** parse5 7.3.0 is quadratic on nested divs (1 MiB = 180 s), on formatting elements that come back (4 MiB ends the process), on the attributes of one tag, on repeated `<body x>`, and more; the whole-branch reviewer found it by timing `'<div>'.repeat(n)` at three sizes. Rule: a complexity claim about a third-party parser that reads untrusted input goes in a comment or a decision row only after an adversarial run at the cap (nesting, repetition, amplification, one huge token), and the test for it runs the SAME input at 1/32 of the size first so a regression fails in a second instead of hanging the run.
- 2026-11-07 — review fix: **`timeout 240 sh -c 'vitest run'` in my mutation harness killed the shell and left the vitest worker running its 4 MiB hostile case at 100% CPU for 12 minutes.** Everything timed after that was noisy: a timing assertion failed once in six runs at 8x its normal time, a mutant was "killed" by an unrelated test of a 5 KB page (most likely the wall-clock deadline, with the load average at 25; I had not kept its message), and I almost tuned constants to the noise. Check `ps` for orphans between mutants (kill by process group, or `pkill -f <worktree path>.*vitest`), rerun any mutant killed by a test that has nothing to do with it ALONE before counting it, and keep the failure text of every unexpected red.
- 2026-11-07 — review fix: **I picked the first limits from synthetic pages and a wall clock, and both were wrong in the same direction (too tight for real pages, too loose for the machine).** The synthetic "prose" test page was 5x denser than the densest real page I had (180 vs 32 nodes per KB), and the deadline refused good pages whenever the machine was busy (and a cached refusal sticks). Measure real files first (I had eight of 60 KiB-4 MiB in ~/Downloads), calibrate on node and call counts per character, and use `process.threadCpuUsage()` for a budget on synchronous work.
- 2026-11-07 — review fix: **calling parse5's `preprocessor.dropParsedChunk()` between tokenizer writes to stop a quadratic copy corrupted character references.** `&amp;` x 40000 fed in 7-character or 4096-character pieces came out short (16 characters at 7, 4094 at 4096); whole, or in pieces without the drop, it was identical. Any chunked-vs-whole driver needs a differential test (chunk sizes 1, 7, 64, 4096 over entity, CRLF, surrogate and comment inputs) before it is trusted; I found this by running one on a whim, and then removed chunking entirely.

- 2026-11-07 — second review fix: **I wrote that a worker's heap limit "ends the worker and not the process" from one fixture test, and it is not a guarantee.** The real transform in a worker with `maxOldGenerationSizeMb` 64, 96 or 128 and a 4 MiB script page ended the WHOLE process (SIGABRT, "Reached heap limit Allocation failed"); at 160 MB and above, and for every memory-hungry shape of the earlier rounds (the unbounded transform's 1 GB reconstruction, the 16.8M-quote page) at 256, 384 and 512 MB, only the worker ended. A limit of 0, 1, 2 MB, a negative number or NaN aborts the process while the worker is being MADE ("GC during deserialization"). A thread is not a memory boundary; a child process is the only hard one. Rules: measure the failure you rely on with the real workload and several limits, in a child process so the abort does not take the shell with it; never put an OOM of the real transform in a test (it can abort the test runner: it killed the vitest fork once); validate numeric limits before they reach `new Worker`.
- 2026-11-07 — second review fix: **`worker.unref()` before `worker.on('message', ...)` leaves the worker holding the process open**: a message listener takes hold of the port again (measured with a 10-line script: unref first, listeners after, an idle process never ends; the other order ends it). Found because a mutation sweep left "worker not unref-ed" alive and a test that runs a child which makes a pool, uses it and does NOT close it then hung. Unref after the listeners, and keep a ref'd deadline timer while a page is being prepared (otherwise the process can end under a pending await).
- 2026-11-07 — second review fix: **my first line for pages waiting on the worker was four, and the Chromium hostile suite (16 pages at once) was turned away: 20 `busy` 422s, 17 failures.** The first full run after wiring the origin caught it; a unit test with a stand-in worker never would. Size the line from the real concurrent users of the thing (the browser suite loads 16 at once) and bound it by characters held too (each waiting page is a 4 to 8 MB string in the request thread), not by a guess of 4.
- 2026-11-07 — second review fix: **the intermediate commit that raised the transform's budget to a flat 1.5 s still had the origin running the transform on the request thread**, a worse DoS cap there than the size-scaled budget it replaced (the coordinator's security review flagged it). - 2026-11-07 — second review fix: **the weigh-before-write count under-counted by one per `<pre>`/`<textarea>`/`<listing>` (the newline `restoreSkippedNewlines` puts back)**, found only because a test asserted "never lower than what the page comes back as" over a page of structural variety; an exactness test on strings alone would not have.
