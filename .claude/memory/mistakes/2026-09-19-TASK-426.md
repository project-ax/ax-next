## 2026-09-19 — TASK-426 Task-ID allocation is a racy read-modify-write

- `2026-09-19` (TASK-426) — **A BEGIN-only `awk` that stops being BEGIN-only turns into a blocking read on stdin, and hangs forever with no error and no exit code.** `backoff()` shipped for about an hour as `sleep "$(awk "BEGIN{printf \"%.3f\", $ms/1000}")"`. The nested `\"` inside a `$( )` inside `"…"` did not survive parsing: the trace showed awk being handed `BEGINprintf "%.3f"` — braces gone, second argument gone. `BEGIN` is then no longer a block keyword but a bare pattern, so the program is no longer BEGIN-only, awk falls back to its default "read input and print", and stdin is the **never-written pipe** that `child_process.spawn` (and therefore vitest, and therefore any test runner) hands a child. Two `claim` processes sat there past 120s. `ps` showed the bash processes alive with **no children**, which sent me looking in the wrong place — the grep pattern I used to list the tree did not match the stub's argv, so the hung `awk`/stub was invisible. What actually found it was `bash -x` with the child's stderr **streamed live** rather than buffered into a promise that a timeout then discarded. PREVENTION: format numbers with the `printf` **builtin** (`printf -v secs '%d.%03d' …`) instead of shelling out — it removes the quoting hazard and the stdin hazard in one move. More generally: a subprocess in a shell helper inherits an open, never-closed stdin in every automated context, so any tool that *might* fall back to reading stdin is a latent hang, not a latent error.
- `2026-09-19` (TASK-426) — **A concurrency test built on the headline scenario grades the easy case.** My suite ran two racers, and a mutant that deleted the settle loop's whole re-verification step (`exit 0` as soon as the rename succeeds) **survived all 19 tests**. With two parties the deterministic keeper rule means only ONE of them renames, and it renames to a number nobody else is taking — so one round genuinely is enough and the loop is dead weight *in that scenario*. It is load-bearing only at three, where two non-keepers compute the same `max+1` and swap one duplicate for another. The fix was a second test that constructs a three-way collision and settles two of the cards at once. Generalise: when the mechanism is "retry until stable", the test that proves the retry is the one where the FIRST attempt is also wrong — reproducing the reported incident (which was 2-way) is necessary and not sufficient.
- `2026-09-19` (TASK-426) — **A reviewer subagent runs mutants in YOUR worktree, and its `git checkout -- <file>` discards your uncommitted edits.** The existing rule is "never restore a mutated file from a `cp` backup, use `git checkout --`". This is its mirror image: `git checkout --` is the right restore *for the agent doing the mutating* and a destructive one for anybody else editing that file at the same time. A reviewer dispatched WITHOUT `isolation: "worktree"` — which is what yolo-ship Phase 5 prescribes, so it can see the branch — shares the tree with the builder. I applied six review fixes to `scripts/board-task-id.sh`, ran the suite, and got two failures whose symptom was impossible (a deterministic keeper branch that never fired). I spent a detour testing the jq in isolation before running `git diff --stat` and finding **the file had no changes at all**: the reviewer had restored it, and the run I had just debugged was executing ITS mutant. Two tells, both cheap: `git diff --stat` disagreeing with what you just wrote, and a failure whose mechanism you can prove impossible by hand. **Prevention: do not edit files while a reviewer that mutates-and-restores is live in the same tree.** Either commit before dispatching and treat the tree as read-only until the review returns, or commit each fix the moment it is green so a stray restore can only cost the working copy. Dispatching a SECOND reviewer while you are mid-fix is the specific thing not to do — I did it because the first had gone quiet, and then both were live at once.
