## 2026-09-19 — TASK-413 the workspace contract makes every backend prove tenant isolation

- `2026-09-19` (TASK-413) — **I WROTE THE VERY CO-VARIATION DEFECT THE CARD WAS ABOUT, INSIDE THE TEST MEANT TO PREVENT IT.** The card's central warning was that `runIndexContract`'s isolation case varied `userId` AND `agentId` together, so it held under any partition containing either. I wrote a contract block whose header claims "every ctx pair below varies EXACTLY ONE field" — and a `caller` helper that derived `sessionId: ${userId}:${agentId}`. So every pair varied TWO. `ax-code-reviewer` caught it and, instead of arguing, ran the mutant I had not: a backend partitioned on `sessionId` alone scored **1 red / 15 green**, the single red being the shared-tree guard. Three isolation-direction cases waved a wrong partition through; the entire rejection rested on one case that a future edit could delete while trusting my false comment. Pinning `sessionId` to a constant took the sessionId mutant to **3 red / 13 green**. **Lesson: enumerate EVERY field of the ctx you construct, not just the ones you meant to vary — a derived or convenience field is still a field a backend can key on.** And: a claim like "varies exactly one field" is executable — count the object literal.
- `2026-09-19` (TASK-413, round 2) — **MY FIX FOR THE CO-VARIATION DEFECT CREATED A SECOND ONE, AND THE REVIEWER MEASURED IT.** Round 1: my ctx pairs varied two fields because `sessionId` was derived from `userId`+`agentId`. I fixed it by pinning `sessionId` to a constant and claimed a strict improvement. It was a TRADE: with `sessionId` constant in every case, NOTHING varied it, so nothing pinned it out of the key — and a backend partitioned on `(agentId, sessionId)` ("a fresh workspace per conversation") went from 1 red to **0 red / 16 passed**. The reviewer ran that mutant against both versions to prove the regression in both directions. **Lesson: "every pair varies exactly one field" is necessary, not sufficient. A field held constant in every case is a field the suite says nothing about.** The completeness check is not "did I enumerate the fields" but "did I mutate every SUBSET of them": `ctx` has three identity fields, so seven wrong partitions, and the fix was a sixth case varying `sessionId` alone and asserting SHARED. Final matrix — `{}` 3 red, `{userId}` 4, `{sessionId}` 4, `{userId,sessionId}` 5, `{userId,agentId}` 1, `{agentId,sessionId}` 1, `{userId,agentId,sessionId}` 2, and `{agentId}` (shipped) the only one green at 17/17. This is the second time in one PR that fixing a claim created a new false one — the #583 meta-finding, reproduced.
- `2026-09-19` (TASK-413, round 3) — **THE COMPLETENESS CLAIM WAS FALSE A THIRD TIME, AND THE FIX FOR ROUND 2 IS WHAT MADE IT FALSE.** After rejecting all seven subsets of `{userId, agentId, sessionId}` I wrote "`ctx` carries exactly three identity fields, so those three axes are the whole space". `AgentContext` also carries `conversationId`, `source`, `triggerLabel`, `reqId` and `workspace.rootPath`. The reviewer measured `(agentId, conversationId)`: **0 red / 17 passed** — "a fresh workspace per conversation", a *more* tempting wrong key than `sessionId`, shipping green. **The mechanism is worth memorising: an OPTIONAL ctx field left `undefined` by every test caller collapses `(agentId, thatField)` onto `agentId` INSIDE THE TEST while it splits for real in production.** An unset optional field is not a pinned field. Adding only `conversationId` then left `(agentId, source)` green at 18/18 for the identical reason — I checked, having learned by then. The real fix is structural, not per-field: ONE case where two callers agree on `agentId` and differ on **every** field `makeAgentContext` accepts, asserting the inequalities themselves so it fails loudly if a new field appears. Final matrix: every field alone → red, every `(agentId, field)` pair → red, `{agentId}` → the only green at 18/18. **Three rounds, three false completeness claims, each created by fixing the previous one. Enumeration cannot prove completeness; construction can.**
