# TASK-470 — `awk -v` cannot carry a newline, and nobody checked its exit status

**The mistake.** All three auto-ship card helpers (`append_progress`,
`append_learnings`, `set_needs_input` in `.claude/auto-ship-progress.sh`, generated from
`.claude/skills/auto-ship/references/github-project.md` §6/§8.3) spliced their entry with
`awk -v e="$entry" -v end="$END" '$0==end{print e} {print}'`.

An awk `-v` assignment **cannot hold a literal newline**. Given multi-line text awk
aborts with `newline in string`, writes **nothing** to stdout and exits **2**. The
helper captured that into `nb=$(…)` without checking `$?`, handed the empty string to
`updateProjectV2DraftIssue` as the **entire card body**, and printed its normal success
line. A live card (TASK-463) was reduced to **1 byte** on 2026-09-19 and was only
rebuilt because its sources happened to still be in a scratchpad.

**Why it hid for months.** It fires only on the **second-or-later** multi-line append to
one card. The first takes the `printf` arm (no block exists to splice into yet) and
works. Ten sibling cards audited the same day looked fine — each had received exactly
one multi-line append. **A single-append test passes against this bug.** Any
reproduction must be two appends.

**The two lessons, generalised:**

1. **A command substitution that swallows a nonzero exit is a data-loss bug whenever the
   result is written somewhere.** `nb=$(… | awk …)` returning empty is indistinguishable
   from "the body is empty" at the write site. Gate the write on a property of the
   constructed value (it grew, it still has its markers), not on the pipeline having
   looked like it worked.
2. **The direction of failure is the design decision.** The old pairing — destroy the
   data, print success — is the worst one available. The fix makes the only reachable
   failure "write nothing and say so loudly" (`<label>: REFUSED (… body untouched)`,
   `return 3`, wrapper class `HEARTBEAT-FAILED(refused)` / exit 7).

**Second-order trap hit while writing the test.** `JSON.stringify(entry)` interpolated
into a shell command renders a real newline as the two characters `\` `n`, which a
double-quoted shell word keeps **literal** — so the first version of the "multi-line"
test passed a single-line string and went green against the bug. Single-quote shell args
(`'…'` with `'` escaped as `'\''`) when the payload's newlines are the point.

**Third-order trap.** The old `awk -v` also *expanded escapes*, so a caller writing
`"a\nb"` in double quotes got two lines. Replacing awk with parameter expansion silently
dropped that. Kept deliberately (`${line//\\n/$nl}`), matching the convention
`set_needs_input` already documented — a "fix" that removes undocumented-but-relied-on
behaviour is a regression wearing a bugfix label.

## Correction, measured on CI: the awk claim is platform-specific

The card (and my first test) said an awk `-v` assignment **cannot** carry a literal
newline. Measured: that is true of the **one-true-awk macOS ships** — the platform
auto-ship runs on and where the card was destroyed — and **false of gawk/mawk on
ubuntu-latest**, which accept it and print the value. The first version of the mechanism
test asserted the macOS behaviour unconditionally and went **red on CI**, correctly.

Two consequences worth carrying forward:

1. **CI could never have reproduced this data loss.** A repo-wide green run is not
   evidence about a defect whose trigger is a host-tool implementation difference. When
   a bug's mechanism is "which build of a POSIX tool is installed", gate the mechanism
   assertion on `process.platform` and pin **both** branches — the split is the argument.
2. **Know which of your guards have teeth on which platform.** On a Linux runner the
   behavioural two-append tests go *green against the buggy helper*, because gawk
   accepts the newline. What holds the line on CI is the unconditional structural pair:
   the "no caller text through `awk -v`" ban and the "refusal reachable before the
   mutation" check. Behavioural tests that look sufficient on the machine where they
   were written may be sufficient *only* there.

Also measured while hardening: `${line//\\n/$nl}` substitutes **only** `\n`, so
`C:\path`, `%`, backticks, `$VAR` and quotes all survive verbatim — narrower, and safer,
than the full escape expansion `awk -v` performed on every platform.
