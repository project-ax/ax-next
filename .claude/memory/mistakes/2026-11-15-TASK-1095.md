| 2026-11-15 | **`channel-slack-composition.test.ts` "a held call" failed in CI (`isHold(holds[0])` false), then 4 later tests failed with 409 on connect.** Not a fail-open: `holds[0]` was `undefined`. The test's `invokeScript` pushes the `tool:pre-call` answer AFTER awaiting the real gate (Postgres), but the test read `holds[0]` right after `invokedTurn(1)`, which only waits for `agent:invoke` to be ENTERED. Under CPU load the pre-call took 213-711 ms and the read won; every pre-call later returned a real hold (3/3 loaded repros, with no delay added). The 409s were a cascade: `dropAgent` sat after the `try/finally`, so the failed test left #support-desk bound. Predates TASK-1095 PR B (from #1180). | A value recorded inside a stubbed service is read on the "service was called" signal instead of on "the value exists". A test's cleanup also ran only on success. | Wait on the condition you assert (`vi.waitFor(() => expect(holds).toHaveLength(n))`), never on an earlier event in the same async chain. Shared fixtures (a channel, an install) get freed in `afterEach`, not at the end of the test body. To repro a load race: `for i in $(seq 1 24); do (yes >/dev/null &); done`, then `pkill -x yes`. Above ~16 busy procs on 14 cores, the Postgres container itself often fails to start, so those runs are skips, not evidence. Side note: a `tool:pre-call` fired AFTER kernel shutdown returns `{rejected:false}` (decisions unsubscribed). That's only an artifact of a late test fire, but it's worth knowing when reading logs. |
