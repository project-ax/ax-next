## A shared zod row schema is a trap: `returns` strips, and tsc does not see it

**Seen:** TASK-251 (2026-08-23). The obvious fix for "hook X leaks a storage `id`" was
to delete `id` from the row schema. That schema was shared with a *sibling* hook whose
consumer reads `id` for a React key.

**Why it is silent:** `HookBus.call` returns `returns.safeParse(result).data`,
and a zod object strips undeclared keys. So the sibling hook stops delivering the field
at runtime, while every type still says it is there — the HTTP hop that carries it is an
untyped `get<T>`, so `pnpm build` stays green and the only symptom is
`key={undefined}` in a table.

**The rule:** before narrowing any `*Schema` used in a `returns:`, grep for every other
schema that composes it. Narrow with a *derived* schema (`Base.omit({ field: true })`)
for the one hook, and leave the shared base alone. Then write the test as a **pair** —
one assertion that the field is gone from the narrowed hook, one that it is still
present on the sibling. The second assertion is the one that catches the mistake.
