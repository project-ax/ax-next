- **A Node body reader that only listens for `data` / `error` / `end` can hang forever, in two ways.** (1) The request was destroyed or ended BEFORE the listeners attached: its last event already fired. (2) A bare `destroy()` with no error AFTER attach emits only `'close'`. The fix: before attaching, check `req.errored` (reject with it), then `req.readableEnded`, then `req.destroyed`, and ALSO reject on `'close'` behind the settled latch. Check `readableEnded` before `destroyed`, because a request auto-destroys right after `end` and so is almost always both. Normal flow emits `end` and then `close`, so the late `close` is a no-op. The production shape: the client hangs up while the listener is still awaiting auth. Node then sets `destroyed` + `errored` (aborted/ECONNRESET) with nobody listening. Probed on Node 24: four request shapes (destroyed, errored, ended, bare destroy mid-read) all hung in `@ax/ipc-core` body.ts before TASK-1024. To test it, race the read against a ~500 ms timer, so a regression fails as "hung" instead of as a vitest timeout. `@ax/http-server`'s `readBodyCapped` had the same close-only gap when this was written.
- **Mapping a service-hook PluginError to HTTP: key the 400 off the owning package's exported code list (`MANIFEST_CODES`), never "any PluginError".** Everything else is a host fault. Log it on `ctx.logger` as a structured line, and put `pluginErrorCode` / `plugin` / `hookName` alongside: the logger keeps only name/message/stack of an Error. Answer `{error:'internal'}`, the same body as the http-server catch-all, and never echo `err.message` on that path. Gotcha: `HookBus.call` wraps every non-PluginError a service throws as `PluginError{code:'unknown'}` with the original message inside, so "any PluginError → 400" also turned store crashes into 400s that echoed the DB message. Note too that the @ax/agents admin-route `ctx` is built once per handler set, so its reqId is constant and correlates nothing (TASK-1024, agents promote).
