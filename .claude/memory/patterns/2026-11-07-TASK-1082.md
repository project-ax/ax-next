- **parse5's serializer is not a round trip: it drops the doctype's public/system identifiers (quirks mode flips) and the newline after `<pre>`/`<listing>`/`<textarea>` (the parser eats one, the serializer never writes it back).** Write the doctype yourself from `node.name/publicId/systemId`, quoting with whichever quote the id lacks, and before serializing prepend `\n` to the first text of those elements when it already starts with one. The Chromium DOM comparison (outerHTML, compatMode, innerText, textarea.value, before vs after) over 59 pages and thousands of random benign pages found no other difference but the `<select>` one below, odd foster-parenting in quirks mode, and one behavior change: a `<script>` cut off by the end of the document does not run in a browser, but serialization closes it and then it does (TASK-1082 T4).
- **Real mutation XSS against parse5 and Chromium, usable as test vectors:** `<math><mtext><table><mglyph><style><iframe srcdoc=x>` looks clean (the iframe is style text), serializes to `<math><mtext><mglyph><style><iframe srcdoc=x></style>...`, and the second read makes it an element in both. A one-pass "parse, cut, serialize, ship" leaks it; so does `<math><mtext><table><mglyph><style><!--</style><img title="--></mglyph><iframe srcdoc=x>">` (parse5 does not escape `<`/`>` in attribute values). Search method: mutate known seeds token by token and look for `dirty(parse(serialize(cut(parse(x)))))`; pure random tag soup found none in 400k tries (TASK-1082 T4).
- **Chromium 135+ keeps content inside `<select>` that parse5 7.3.0 and 8.1.0 drop (`<select><iframe>`, `<div>`, `<button><selectedcontent>`, `<table>`, `<img>`).** Safe direction for a sanitize-by-rebuild (the dropped tag is not in the output), but a rendering loss for customizable-select pages, and fatal for any approach that ships the original bytes after parse5 says "clean". Oracle for this kind of claim: Playwright + CDP `Page.getFrameTree` (counts frames inside closed shadow roots, which `window.length` and `querySelectorAll` cannot) plus `DOM.getDocument({pierce:true})` (TASK-1082 T4).
- **parse5 7.3.0 and the browsers read two characters differently, and a fuzz that includes them finds it in seconds:** U+0000 (Chromium 147, Firefox 148 and WebKit 26.4 all skip it while `<head>` is open; parse5 ends the head) and a CR from `&#13;` (parse5's `isWhitespace` omits CR, so it is body text there and whitespace to a browser). Put odd characters (`\u0000 \r \f \u000b &#13; &#0; &#x80; &#xD800;`) in the vocabulary of any parse5-vs-browser fuzz, not just tags. A leading U+FEFF in a fuzz input is an oracle artifact (the browser eats it as a BOM); real flows decode with `TextDecoder`, which does too (TASK-1082 T4).
