- **parse5's serializer is not a round trip: it drops the doctype's public/system identifiers (quirks mode flips) and the newline after `<pre>`/`<listing>`/`<textarea>` (the parser eats one, the serializer never writes it back).** Write the doctype yourself from `node.name/publicId/systemId`, quoting with whichever quote the id lacks, and before serializing prepend `\n` to the first text of those elements when it already starts with one. The Chromium DOM comparison (outerHTML, compatMode, innerText, textarea.value, before vs after) over 59 pages and thousands of random benign pages found no other difference but the `<select>` one below, odd foster-parenting in quirks mode, and one behavior change: a `<script>` cut off by the end of the document does not run in a browser, but serialization closes it and then it does (TASK-1082 T4).
- **Real mutation XSS against parse5 and Chromium, usable as test vectors:** `<math><mtext><table><mglyph><style><iframe srcdoc=x>` looks clean (the iframe is style text), serializes to `<math><mtext><mglyph><style><iframe srcdoc=x></style>...`, and the second read makes it an element in both. A one-pass "parse, cut, serialize, ship" leaks it; so does `<math><mtext><table><mglyph><style><!--</style><img title="--></mglyph><iframe srcdoc=x>">` (parse5 does not escape `<`/`>` in attribute values). Search method: mutate known seeds token by token and look for `dirty(parse(serialize(cut(parse(x)))))`; pure random tag soup found none in 400k tries (TASK-1082 T4).
- **Chromium 147 keeps content inside `<select>` that parse5 7.3.0 and 8.1.0 drop (`<select><iframe>`, `<div>`, `<button><selectedcontent>`, `<table>`, `<img>`).** Safe direction for a sanitize-by-rebuild (the dropped tag is not in the output), but a rendering loss for customizable-select pages, and fatal for any approach that ships the original bytes after parse5 says "clean". - **parse5 7.3.0 and the browsers read two characters differently, and a fuzz that includes them finds it in seconds:** U+0000 (Chromium 147, Firefox 148 and WebKit 26.4 all skip it while `<head>` is open; parse5 ends the head) and a CR from `&#13;` (parse5's `isWhitespace` omits CR, so it is body text there and whitespace to a browser). Put odd characters (`\u0000 \r \f \u000b &#13; &#0; &#x80; &#xD800;`) in the vocabulary of any parse5-vs-browser fuzz, not just tags. A leading U+FEFF in a fuzz input is an oracle artifact (the browser eats it as a BOM); real flows decode with `TextDecoder`, which does too (TASK-1082 T4).
- **A customized built-in element's `disconnectedCallback` runs synchronously inside ANY `remove()` call, including one a defensive script made through a captured native (`Reflect.apply(Element.prototype.remove, el, [])`).** `class X extends HTMLIFrameElement`, `customElements.define('x-bait', X, { extends: 'iframe' })`, `document.createElement('iframe', { is: 'x-bait' })` works in Chromium 147. - **Playwright can see what the page cannot, and can arrive before it does.** `Frame.childFrames()` / `page.frames()` include frames inside CLOSED shadow roots (the count CDP `Page.getFrameTree` gives), where `window.length` and `querySelectorAll` read 0. `page.addInitScript(string)` runs in sandboxed opaque-origin frames before the first byte; a `MutationObserver` created there records parser-inserted nodes whatever the page's own observer purges afterwards. An added node's ancestors arrive in the same batch, so dedupe by node or an iframe is counted once per ancestor (TASK-1082 T6).
- **`document.write` builds closed declarative shadow roots, and `document.open()` does not stop a document MutationObserver (Chromium 147).** After `document.open(); document.write(...); document.close()` the observer still reports every inserted node, so a plain iframe written that way is seen. But `document.write('<template shadowrootmode=closed><iframe srcdoc=...>')` runs the streaming parser, which DOES build the closed shadow root: unguarded it left `window.length` 0, `querySelectorAll('iframe')` empty, one frame in the frame tree and packets at both canaries. The `document.write`/`open` locks are therefore load-bearing for that route and for no other; the guard's comment ("outside the observer's sight") is true of this variant only (TASK-1082 T6).
- **Self-navigation facts (Chromium 147).** A sandboxed (`allow-scripts`, no `allow-top-navigation`) document opened top-level can navigate itself to any http URL; the sandbox flags only restrict other contexts. Renderer-initiated top-frame navigation to `data:` is refused by Chromium (console error "Not allowed to navigate top frame to data URL: ...", meta refresh included). Framed, a parent `frame-src` that excludes the target refuses the navigation BEFORE any request, the frame commits `chrome-error://chromewebdata/`, and the PARENT's console gets `Framing '<url>' violates the following Content Security Policy directive: "frame-src ...". The request has been blocked.` (the URL is blank for a data: target). `top.location = ...` from a sandboxed frame is refused with a message whose wording differs between the default and site-isolated process models, so assert the effect, not the text (TASK-1082 T6).

A page that wants to act after the kill (rebuild itself) has to arm its timer BEFORE the trigger; a short timer is enough, because the guard acts in a microtask and every timer is a later task (TASK-1082 T6).

- **parse5 7.3.0 shapes that cost minutes or gigabytes, and what bounds each (all fixed in `prepare-html.ts`, TASK-1082 review).** (1) Nested open elements (`<div>` x N, `<table><tr><td>`, `<template>`, `<pre>`, `<a><div>x</a>` repeated): every start tag scans the stack of open elements, so O(N^2); bound the stack depth via the tree adapter's optional `onItemPush`/`onItemPop` (they fire for every push and pop, including the adoption agency's `insertAfter`). (2) Formatting elements that come back ("reconstruct the active formatting elements": N `<b x=i>` closed by their parent, then every `<span>` rebuilds all N): ~500 nodes per 17 bytes; bound the node count in `createElement`/`createTextNode`/`createCommentNode` and in `insertText*` (the default adapter's `insertText` makes its text node through itself, not through your wrapper). (3) One tag with thousands of attributes: the tokenizer compares each new attribute with every earlier one and calls nothing of yours; look at `tokenizer.currentToken.attrs.length` from a wrapped `tokenizer.preprocessor.advance` every few thousand characters. (4) `<body a_i>`/`<html a_i>` repeated: the default `adoptAttributes` rebuilds a Set of the recipient's names per call. (5) Foster-parented siblings: the default `insertBefore`/`insertTextBefore` look for the reference with `indexOf` from the front; the reference is the last child, use `lastIndexOf`. (6) Scans that build nothing (500 open spans then a million `</i>`): count adapter calls (every read goes through the adapter). (7) A block with 70,000 children moved by the adoption agency: `detachNode` is `splice(0,1)`, O(n) per child; nothing counts it, only the clock ends it (70,000 elements: 1 s to empty by `splice(0,1)`, 0.3 s by `shift()`, both quadratic in V8 above ~16k elements).
- **Tree depth can exceed the stack of open elements ever held, and the excess composes.** The adoption agency re-parents without growing the stack: `<a href=1><table><em><a><td></a>` leaves the finished tree one level deeper than the stack was, per copy. 110 copies are a stack of 442 and a tree of 552. So a depth limit read only from `onItemPush` is not enough; walk the finished tree too (TASK-1082 review, found by hill-climbing the gap on random tag soup).
- **A V8 string appended to in many small pieces copies the whole buffer each time it is read in between** (`this.html += chunk` in parse5's preprocessor: 1000 appends of a 4 MiB script is ~2 GB of copying; the transform of one took 0.8 s instead of 0.4 s). It is why feeding a tokenizer a page in pieces is not free, and why one long script, comment or text run is the shape that shows it. And serializer output is a rope until something reads it (`includes`, `===`): refuse on `out.length` before anything flattens a multi-GB result.
- **Old-versus-new differential for a rewrite of a security transform that must not change behavior:** compile the old source into a scratch dist (outside the worktree, so `git status` stays empty), then fuzz random tag soup (seeded, 20k pages a run, vocabularies biased to tables, formatting elements, foster parenting, `<body>` repeats) and real files, asserting identical output or both refusing. 195,000 pages and 8 real files agreed exactly; it is also how a chunked parse driver was caught corrupting entities.
- **`process.threadCpuUsage()` (Node >= 23.9, repo requires 24) is the right clock for a budget on synchronous work:** per-thread CPU time, ~0.8 us a call (a wall clock is 0.04 us but refuses good pages whenever the host is busy). `Atomics.wait` on a SharedArrayBuffer is a synchronous sleep that uses no CPU, which is how to test that a clock ignores one.
- **A timing test that has to pass on a loaded machine: keep the best of up to three runs and stop at the first one under the limit.** A refusal that takes milliseconds took 30x as long once in a few dozen runs; a real regression is slow every time. Pair it with a small-scale canary (1/32 of the size, or the size where plain parse5 already takes ~2 s) so a regression fails in about a second instead of hanging the 4 MiB case after it.
