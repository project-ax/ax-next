- **parse5's serializer is not a round trip: it drops the doctype's public/system identifiers (quirks mode flips) and the newline after `<pre>`/`<listing>`/`<textarea>` (the parser eats one, the serializer never writes it back).** Write the doctype yourself from `node.name/publicId/systemId`, quoting with whichever quote the id lacks, and before serializing prepend `\n` to the first text of those elements when it already starts with one. The Chromium DOM comparison (outerHTML, compatMode, innerText, textarea.value, before vs after) over 59 pages and thousands of random benign pages found no other difference but the `<select>` one below, odd foster-parenting in quirks mode, and one behavior change: a `<script>` cut off by the end of the document does not run in a browser, but serialization closes it and then it does (TASK-1082 T4).
- **Real mutation XSS against parse5 and Chromium, usable as test vectors:** `<math><mtext><table><mglyph><style><iframe srcdoc=x>` looks clean (the iframe is style text), serializes to `<math><mtext><mglyph><style><iframe srcdoc=x></style>...`, and the second read makes it an element in both. A one-pass "parse, cut, serialize, ship" leaks it; so does `<math><mtext><table><mglyph><style><!--</style><img title="--></mglyph><iframe srcdoc=x>">` (parse5 does not escape `<`/`>` in attribute values). Search method: mutate known seeds token by token and look for `dirty(parse(serialize(cut(parse(x)))))`; pure random tag soup found none in 400k tries (TASK-1082 T4).
- **Chromium 147 keeps content inside `<select>` that parse5 7.3.0 and 8.1.0 drop (`<select><iframe>`, `<div>`, `<button><selectedcontent>`, `<table>`, `<img>`).** Safe direction for a sanitize-by-rebuild (the dropped tag is not in the output), but a rendering loss for customizable-select pages, and fatal for any approach that ships the original bytes after parse5 says "clean". Oracle for this kind of claim: Playwright + CDP `Page.getFrameTree` (counts frames inside closed shadow roots, which `window.length` and `querySelectorAll` cannot) plus `DOM.getDocument({pierce:true})` (TASK-1082 T4).
- **parse5 7.3.0 and the browsers read two characters differently, and a fuzz that includes them finds it in seconds:** U+0000 (Chromium 147, Firefox 148 and WebKit 26.4 all skip it while `<head>` is open; parse5 ends the head) and a CR from `&#13;` (parse5's `isWhitespace` omits CR, so it is body text there and whitespace to a browser). Put odd characters (`\u0000 \r \f \u000b &#13; &#0; &#x80; &#xD800;`) in the vocabulary of any parse5-vs-browser fuzz, not just tags. A leading U+FEFF in a fuzz input is an oracle artifact (the browser eats it as a BOM); real flows decode with `TextDecoder`, which does too (TASK-1082 T4).
- **A customized built-in element's `disconnectedCallback` runs synchronously inside ANY `remove()` call, including one a defensive script made through a captured native (`Reflect.apply(Element.prototype.remove, el, [])`).** `class X extends HTMLIFrameElement`, `customElements.define('x-bait', X, { extends: 'iframe' })`, `document.createElement('iframe', { is: 'x-bait' })` works in Chromium 147. That puts page code inside a purge loop after it took its mutation records; creating a second iframe there is how to reach the guard's `kill()` honestly. Useful for any test of "what if the cleanup itself is re-entered" (TASK-1082 T6).
- **Playwright can see what the page cannot, and can arrive before it does.** `Frame.childFrames()` / `page.frames()` include frames inside CLOSED shadow roots (the count CDP `Page.getFrameTree` gives), where `window.length` and `querySelectorAll` read 0. `page.addInitScript(string)` runs in sandboxed opaque-origin frames before the first byte; a `MutationObserver` created there records parser-inserted nodes whatever the page's own observer purges afterwards. An added node's ancestors arrive in the same batch, so dedupe by node or an iframe is counted once per ancestor (TASK-1082 T6).
- **`document.write` builds closed declarative shadow roots, and `document.open()` does not stop a document MutationObserver (Chromium 147).** After `document.open(); document.write(...); document.close()` the observer still reports every inserted node, so a plain iframe written that way is seen. But `document.write('<template shadowrootmode=closed><iframe srcdoc=...>')` runs the streaming parser, which DOES build the closed shadow root: unguarded it left `window.length` 0, `querySelectorAll('iframe')` empty, one frame in the frame tree and packets at both canaries. The `document.write`/`open` locks are therefore load-bearing for that route and for no other; the guard's comment ("outside the observer's sight") is true of this variant only (TASK-1082 T6).
- **Self-navigation facts (Chromium 147).** A sandboxed (`allow-scripts`, no `allow-top-navigation`) document opened top-level can navigate itself to any http URL; the sandbox flags only restrict other contexts. Renderer-initiated top-frame navigation to `data:` is refused by Chromium (console error "Not allowed to navigate top frame to data URL: ...", meta refresh included). Framed, a parent `frame-src` that excludes the target refuses the navigation BEFORE any request, the frame commits `chrome-error://chromewebdata/`, and the PARENT's console gets `Framing '<url>' violates the following Content Security Policy directive: "frame-src ...". The request has been blocked.` (the URL is blank for a data: target). `top.location = ...` from a sandboxed frame is refused with a message whose wording differs between the default and site-isolated process models, so assert the effect, not the text (TASK-1082 T6).
- **Scripts after a kill never run.** Once the guard removes `<html>`, the parser keeps appending to a detached tree, and scripts in a detached tree do not execute. A page that wants to act after the kill (rebuild itself) has to arm its timer BEFORE the trigger; a short timer is enough, because the guard acts in a microtask and every timer is a later task (TASK-1082 T6).
- **A real Playwright mouse click can silently never reach an out-of-process frame.** In the site-isolated model (`--site-per-process --enable-features=IsolateSandboxedIframes`) with about 16 pages open, `frame.click()` on a link in plain view in the sandboxed artifact frame delivered NO mousedown, mouseup or click to the page in 5 of 12 runs of one cell (measured by recording the three events from an init script; the frame was visible, `document.hasFocus()` false). Playwright returned success; the hash never changed. When the click is incidental, use `frame.evaluate("el.click()")`, which runs the same activation behavior (fragment navigation, `:target`, scroll). Any extra round trip before the click hid it, so a diagnostic that adds one will not reproduce it: record from the init script and read the record only after the failure (TASK-1082 T6).
- **vitest cuts an interpolated `$label` at 40 characters** (`describe.each(rows)('$label', ...)` named a cell "isolated process model, framed by the a…"), so `-t "...the app"` matched nothing and every test came back skipped. Use `%s` with array rows. Filtering one cell with `-t` is also the cheapest way to loop a flaky cell (about 30 s a run) (TASK-1082 T6).
