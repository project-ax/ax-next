# PR-572 — jest-dom matchers stop typechecking on a vitest major (449 × TS2339)

**Symptom.** Bumping vitest 4 → 5 produced 449 `error TS2339: Property
'toBeInTheDocument' does not exist on type 'Assertion<void, HTMLElement>'` across
`channel-web` — and *only* channel-web, because it is the one package whose tsconfig
`include` covers its `__tests__` (see the existing note on tsc excluding test files).

**Cause.** vitest 5 gave `Assertion` and `Matchers` a leading return-type parameter:

```ts
interface Assertion<R extends void | Promise<void> = void, T = unknown>   // v5
interface Assertion<T = any>                                              // v4
```

jest-dom's `types/vitest.d.ts` still declares the one-parameter v4 shape. TypeScript
merges a `declare module` augmentation **only when the type parameter list matches
exactly**, so the merge is silently dropped and the matchers never land.

**Do not** "upgrade jest-dom to fix it" — check first. 7.0.1 (latest) ships a
`types/vitest.d.ts` **byte-identical** to 6.9.1's. There is no version to move to. Two
minutes with `npm pack <pkg>@<v> && tar xzf` answers this before you plan a migration
around it.

**Fix** — a local augmentation with the *correct* arity, in
`packages/channel-web/src/jest-dom-vitest.d.ts`. Augment `Matchers`, not `Assertion`:
vitest 5 has `Assertion`, `ExpectStatic` and `AsymmetricMatchersContaining` all extend
`Matchers`, so one augmentation covers `expect(...)`, `expect.not` and friends.

```ts
import type { TestingLibraryMatchers } from '@testing-library/jest-dom/matchers';
declare module 'vitest' {
  interface Matchers<R extends void | Promise<void> = void | Promise<void>, T = unknown>
    extends TestingLibraryMatchers<unknown, R> {}
}
```

`T` is unused but must be declared — that is the whole point of the arity rule. eslint
needs `no-empty-object-type` **and** `no-unused-vars` disabled on it; the empty body is
the augmentation.

**Types can't fix runtime.** This shim makes `tsc` pass and changes nothing at runtime —
the runtime half of the same migration is a separate bug, see [[2026-09-19-PR-572]] in
`mistakes/`.
