# TASK-464 — empty vs unknown, spelled so it cannot collapse again

## The shape: a discriminated union whose failure arm has no payload

`egress-allowlist:list` answered `{ sites: [] }` on a store throw — the same
value a person with nothing remembered gets. The fix is NOT a flag beside the
array and NOT a nullable array:

```ts
export type EgressListOutput =
  | { status: 'ok'; sites: EgressAllowlistSite[] }
  | { status: 'unknown' };          // no `sites` key AT ALL
```

with `z.discriminatedUnion('status', […])` as the hook's `returns`. Three things
that buys, in order of how much they are worth:

1. `[]` means "none" and can mean nothing else, because the failure arm has no
   array to be mistaken for an empty one.
2. tsc forces every caller to narrow before it can reach `.sites`. A caller that
   forgets does not compile — as opposed to a flag, which a caller forgets
   silently and keeps the old bug.
3. The bus `returns` re-parse now REJECTS a body with no `status`, so a producer
   that reverts to the old shape is stopped at the bus rather than read as an
   empty list downstream.

The repo's flat `{ status, payload }` precedent (`AgentMemoryRead`) is the other
option and its own docstring says why it chose flat: four flat siblings on one
surface. This hook has no flat siblings (`remember`/`revoke` return bare
booleans), so the union costs no surprise here.

## Carry the distinction across the wire as a STATUS CODE, not a second field

The BFF answers 200 for "this is the list, however short" and **503** for "we
could not read it". `503` is what every other degraded read in `channel-web`
already uses (`workspace-unavailable`, `memory-unavailable`, …). A 200 carrying
`{status:'unknown'}` would be a second discriminant beside the one HTTP already
has, and a monitoring probe would see a failed read as a success.

Two route details that are load-bearing:

- Branch on `r.status !== 'ok'`, never `=== 'unknown'`. The BFF mirror type is
  hand-declared, so tsc cannot warn when the real hook grows an arm — and an arm
  we have never heard of is one we cannot describe to a reader. Unknown is the
  safe reading of a shape we do not recognise.
- Catch a throw from `bus.call` **in the route**. The hook promises not to
  throw; if that promise breaks, "we do not know" is a decision the route owns,
  not one to delegate to whatever the HTTP layer does with an uncaught rejection.

## The UI state is a union too, and the failure REPLACES the list

`sites: T[] | null` plus `error: string | null` can hold `{ sites: [], error }`
— and it did: the catch set both, so a failed read drew the reassuring empty
state with a banner over it. Replace with:

```ts
type ListState = { status:'loading' } | { status:'ok'; sites: T[] } | { status:'unknown' };
```

and render the unknown state **instead of** the list container, not above it. An
alert over an empty card is still showing somebody an empty list.

## Proving it is not vacuous: assert the pair, and inject a logger

A `{status:'unknown'}` assertion alone is weak for the same reason `{ok:false}`
was in TASK-469: some other path might produce it. Two guards:

- **Assert the failing read against the succeeding one of the same shape** — an
  unread list next to an empty-but-read one, in the same test. An implementation
  that collapses them has to make two different assertions true with one value.
- **Inject a logger** (`h.ctx({ userId, logger })`; `Logger` is on
  `MakeAgentContextOptions`) and assert the failure event fired on the broken
  read AND did not fire on the healthy one. That pins WHICH branch ran, not just
  what it returned.

Mutation results, for calibration — 4 mutants, all reddened tests, no total ever
shrank: hook catch → `{status:'ok',sites:[]}` = 4 red/176; route collapses
unknown to 200 `[]` = 2 red/13; panel catch sets an empty list = 5 red/13; route
drops its throw guard = 1 red/13.

## Test-helper narrowing beats a read-before-the-mutation workaround

TASK-469 defended the canary's `expect(sites).toEqual([])` by reading the list
BEFORE the revoke, so `[]` afterwards meant the row went away. Good workaround;
better is making the helper narrow:

```ts
if (out.status !== 'ok') throw new Error(`expected a readable list…`);
```

An unreadable list now stops the test with a sentence about it instead of
quietly satisfying it. Route every list read in the file through that helper —
the one direct `bus.call` left in the canary was the one still unguarded.
