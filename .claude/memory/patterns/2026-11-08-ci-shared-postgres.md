- **A Postgres testcontainer start (~2–4.5 s locally, more on CI plus queueing for the 4 host-wide start slots) dwarfs everything else a DB test does: `CREATE DATABASE` on a running server is ~25 ms and booting the full routine harness with migrations on one is ~0.3 s.** A harness that starts a container per test spends most of its suite booting Postgres (`@ax/routines`: 547 s of CI's ~22 test minutes). Use `createSharedPostgres` from `@ax/test-harness`: one lazily-started server per test FILE (stop it in a module-level `afterAll` in the support module, which belongs to whichever file imports it), one fresh database per test. Keep a private container only for tests that stop the server, terminate other backends or change server settings. Measured on `routines` locally, same conditions: 370 s -> 153 s. Locally (many cores, many vitest workers) both before and after hit 40 s `container-start` slot timeouts on a full parallel run; that is the slot cap, not the change — run a failing file alone before suspecting the code (2026-11-08).
