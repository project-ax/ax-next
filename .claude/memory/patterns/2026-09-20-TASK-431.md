# TASK-431 — clamp at the sink, not at the call sites

## Pattern: when the same bug recurs per call site, fix the sink

TASK-424 (#596) clamped an attachment filename at ONE call site
(`AgentConversation`). TASK-431 existed because the other two call sites of the
same component (`Thread.tsx`'s `UserFilePart` and `LiveAttachmentChip`) never
got it. The card proposed two more call-site one-liners — i.e. the same shape
that had just failed.

The fix went into `AttachmentChip` itself, the component that spends
`displayName` on an `<img alt>` and two `aria-label`s. One clamp, every branch,
every caller, and the hand-clamp in `AgentConversation` came out.

**Rule of thumb:** count the call sites before accepting a "two-line fix at the
call site" brief. If N > 1 and the value flows into one component, the component
is the cheaper and more durable place. If N == 1 and the value is consumed in
several ways, the call site is fine.

**Free proof the consolidation is safe:** the pre-existing test from the earlier
card still passes untouched, and still fails when the new sink clamp is mutated
out. That is the evidence that removing the old hand-clamp lost nothing.

## Where a shared display helper lives in `channel-web`

`packages/channel-web/src/lib/`, not inside whichever component happened to need
it first. `lib/fence-line.ts` moved there out of `server/routes-workspace.ts`
for exactly this reason. `components/AttachmentChip.tsx` is rendered by BOTH
shells (chat's `Thread.tsx`, the agent view's `AgentConversation.tsx`), so it
must not import from `components/workspace/` — at time of writing there were
ZERO imports of that shape in the tree, and it would have been the wrong
direction (shared component depending on the specific one).

## Two clamps, and they are not interchangeable

- `lib/fence-line.ts` `fenceLine(value, max)` — a TRUST boundary. Strips the
  characters that let a string rewrite the surface it is drawn on (bidi
  overrides, controls), flattens whitespace, may return `null`. DESTROYS the
  value.
- `lib/attachment-name.ts` `clampAttachmentName(name)` — a LENGTH bound only.
  Removes nothing, claims nothing about content.
- A CSS `truncate` class — visual only. It does NOT touch the accessibility
  tree, so `alt` / `aria-label` / text nodes still carry the whole string. jsdom
  has no CSS at all, so a test can only assert the attribute, never the
  truncation.

`ATTACHMENT_NAME_MAX_CHARS`, `FILE_LABEL_MAX_CHARS` and
`CONVERSATION_TITLE_MAX_CHARS` all sit at 120 and are all deliberately separate
constants.

## Gotcha: slicing a string by UTF-16 unit can orphan a surrogate half

`name.slice(0, 119)` lands between the halves of a surrogate pair whenever the
boundary is odd and the string is astral — producing ill-formed UTF-16 out of a
function whose output is a display name. `fenceLine` avoided this by counting
CODE POINTS, which changes what the cap means (120 code points can be 240 UTF-16
units). `clampAttachmentName` keeps the UTF-16 bound (so `String.length` matches
the advertised cap) and drops an orphaned leading half instead.
