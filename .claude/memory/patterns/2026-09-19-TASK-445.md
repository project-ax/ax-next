# TASK-445 — ask a hand-maintained guard list whether it is finished

## Solid vs. fractional decides whether a contrast card is real

TASK-428's premise died because its 4.10:1 was read off a token while the painted
class was `bg-warning-soft/40`. TASK-445 reported 4.45:1 for the *same token
family* and survived — because both of its sites (`WorkspaceSidebar.tsx` rail
count badge, `bits.tsx` "Waiting on you" badge) paint `bg-warning-soft` SOLID.

The check that separates the two is one grep, and it is the first thing to do on
any contrast card: find the painted class and look for a `/<pct>` suffix. Token
reading == pixel only when the paint is opaque. A light-only or dark-only report
is a hint that alpha was ignored, not proof — TASK-445 was light-only and real.

## `ACCENT_SOFT_PAIRS` is a list of things-to-check, so it fails by omission

`--warning` was missing from it for the list's entire life while the pairing it
describes rendered at two sites at 4.45:1. The list was never wrong; it was never
asked whether it was finished.

The guard added here derives the soft-tint families from `tailwind.config.ts`,
scans the shipped tree (reusing `sourceFiles`/`paints`/`stripComments`) for files
painting `bg-<f>-soft` with `text-<f>`, and requires the pair to be measured.
Three deliberate fail-closed choices, each one a place the obvious version would
have inverted:

- **File-level, not element-level.** A superset of the real pairings, so it
  cannot miss one. The tighter element parse is the one that can be wrong quietly.
- **No alpha exemption.** Skipping fractional paints because "the solid number
  doesn't describe them" is true and exactly backwards as a rule: the exemption
  is keyed on a SHAPE, and every future unmeasured pairing can wear that shape.
- **The one real exemption — a family nothing paints as text — is anchored.** An
  empty scan would forge it, so the warning family's two sites are pinned by
  name; a scan that stopped seeing the tree reddens there.

## Mutants, and the one that removes tests instead of reddening them

- Revert `--warning` to 36%: 1 red (`4.452 < 4.5`), total stays 83. Real ratio
  arithmetic on hex resolved from `index.css` — not a class-name assertion,
  which jsdom cannot make mean anything.
- Delete `['--warning','--warning-soft']` from the pair list: total SHRINKS
  83 -> 80 (three theme cases vanish with the row) and the completeness guard
  goes red naming both files. This is the shape to test for deliberately — a
  mutant that deletes tests passes a "0 failures" check.
- Break the tailwind parse regex: total 83 -> 79 (four family cases vanish) and
  the parse anchor reddens.
- Drop the per-family `for` loop: total 84 -> 80 and the registration guard
  reddens. This one was a REVIEW FINDING, not something I thought of — see below.

## The guard I wrote had the hole the guard was about

Review caught that my new `describe` had no `casesRegistered` counter, while the
same file defends that exact hazard twice already (`quietTextCasesRegistered`,
`tintCasesRegistered`) with a note calling it a known auto-merge collision point.
A merge that keeps `SOFT_FAMILIES` and both anchors but drops the `for` stays
entirely green — neither anchor depends on the loop running — and the per-family
enforcement silently stops existing. That is this block's own failure mode one
level up, and I missed it while writing the block about it.

The lesson generalises: **when adding an enforcement loop to a file that already
has registration counters, the counter is part of the pattern, not an extra.**
Grep the file for `CasesRegistered` before assuming a new loop is complete.

Two smaller review findings worth the same reflex:

- A comment said 4.47 where everything else said 4.45. 4.47 was the UNROUNDED
  value; this file asserts on integer-rounded sRGB. Numbers in prose here are
  checkable and someone checks them — keep one source per number.
- "A superset, so it cannot miss one" overstated the scan's guarantee. It needs
  both classes in the SAME FILE, so the guarantee is co-location, not existence:
  a parent painting `bg-<f>-soft` and a child painting `text-<f>` meets only in
  the DOM and is exempted. Tailwind forces each class to exist literally; it does
  not force them to co-occur.

## Accent vs. tint: measure the direction, and note warning was worse than primary

TASK-425 moved `--primary` because every text role sits on the far side of it.
Same answer here, more lopsided: darkening `--warning-soft` moves it TOWARD the
accent and makes the text ratio worse (4.45 -> 4.08 at 85%). The only helpful
direction from the tint side is lighter, and matching the accent-side headroom
needs ~97%, where the held tint measures 1.04:1 against the white page. So
`--warning` 36% -> 35%: defect pair 4.45 -> 4.66, white on `bg-warning` and
`text-warning` on page/card both 4.84 -> 5.07, dark untouched at 8.47.

## Two operational traps hit while doing it

- **`git checkout -- <path>` reverts the whole file, not just the mutation.**
  Restoring mutant M1 silently discarded a 25-line `index.css` comment written
  minutes earlier. Commit BEFORE mutating; then the restore is exact.
- **`channel-web` typechecks its own tests.** 76 of 78 packages exclude them;
  this one's tsconfig is `include: ["src"]`, so `src/__tests__` is covered.
  A `matchAll` capture is `string | undefined` under `noUncheckedIndexedAccess`
  and vitest went green on it. Run `tsc --noEmit` here, not just vitest.
