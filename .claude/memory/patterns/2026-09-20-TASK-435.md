# TASK-435 — patterns

## Testing a timezone bug without writing a vacuous test

A test that formats an instant and asserts it matches what the code produced
passes **whichever timezone rule you shipped**. A timezone disagreement only
exists across TWO zones, so a single-zone test cannot see it — and the
single-zone test is the one everybody writes first.

The shape that works, measured on Node 24
(`packages/channel-web/src/__tests__/workspace-timestamp-parity.test.tsx`):

1. `process.env.TZ = 'UTC'` — build the wire through the REAL route handler.
   This is the host.
2. `process.env.TZ = 'America/New_York'` — render the surfaces. This is the
   reader.
3. Assert the two surfaces agree, that what they agree on is the READER's
   reading, and that it is NOT the host's.

`process.env.TZ` assignment takes effect immediately on Node 16+, **including on
`Date` objects constructed before the assignment** (probed: the same object
answered `getHours()` 0 then 20 either side of the flip). No module reload
needed.

Guard the flip with an assertion (`expect(new Date(ISO).getHours()).toBe(20)`).
Without it, a developer machine already sitting in the reader's zone runs the
whole test in one zone and proves nothing — silently.

**Do not pin a locale** when production formats with
`toLocaleTimeString(undefined, …)`. Hard-coding `'8:56 PM'` asserts a formatter
the code never calls, and becomes a different test on any runner whose default
locale is 24-hour. Derive the expectation instead; the three assertions above
are all locale-independent.

`vi.useFakeTimers({ toFake: ['Date'] })` pins "now" for a day-bucket label
without faking `setTimeout`, so React's scheduler and RTL keep running on real
timers. Faking all timers here would deadlock the render.

## Proving a rendering fix reddens, cheaply

The faithful mutation of "the server formatted this" is not "revert the whole
branch". Forcing the ONE renderer to `timeZone: 'UTC'` reproduces the observable
defect exactly and is a five-line edit to a single committed-clean file. It
reddened with the walk's own numbers — `expected '12:56 AM' to be '8:56 PM'`.

## Negative space on a wire-shape change

`expect(msg.at).toBe(INSTANT)` passes perfectly well on a message that ALSO
still carries the old `time: '12:56 AM'`. Pinning `Object.keys(msg).sort()` is
what makes "no display string on the wire" enforced rather than asserted in a
PR description.

## Where the workspace's timestamp rule is actually written down

`ActivityEvent`'s doc comment in `packages/channel-web/src/lib/workspace-types.ts`
holds the project's decision — "a display string is a rendering decision, and
rendering decisions do not belong on the wire" — and it predates this card. A
product question that looks open is sometimes already answered in a type's own
comment; grep the types before escalating.
