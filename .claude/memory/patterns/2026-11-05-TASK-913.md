- **A reader that takes many routine rows at once uses `readRoutineRow` (store.ts, TASK-913), never `rowToRoutine`.** `rowToRoutine` throws on a row today's contract refuses, and one throw sinks every row beside it. That happened to the tick's claim, a run's finish (plugin init at boot), the app-update pump's head-of-queue claim, agent purge and `routines:list`. `readRoutineRow` returns `{ ok, routine } | { ok: false, issue: { path, code } }`. Log a refusal with `reportUnreadable(row, issue, '<fixed consequence>')`, which writes ids, a screened zod path and the zod code, and never a zod message (zod messages quote stored values). Per-row reads of ONE routine (get, edit, fire-now, reply, duplicate, webhook admission) keep the strict throw on purpose.
- **Deleting or purging a routine reads columns, not the parsed row (TASK-913).** `store.findOwnership` (owner_user_id, definition_id) feeds `routinePermissions(...).stop`. `lockRoutineRow` does the lock and revision checks. `cleanupSource(row)` builds the signing-secret cleanup. A new delete-path or purge-path check must read columns too, or an unreadable routine becomes undeletable again.
- **`routines:list` answers `{ routines, unreadable }` (TASK-913).** `unreadable` defaults to `[]` in `RoutineListOutputSchema`. A fake registered with `returns: RoutineListOutputSchema` is typed against the OUTPUT type, so under tsc it needs `unreadable: []` (channel-web `routes-workspace-tasks.test.ts` did). Only Settings draws `unreadable`. `routine_list` (the model's tool) and the Tasks page read `routines` alone, so an unreadable task is silently absent there.
- **A skipped claim must be put off from NOW, not from its stored time (TASK-913).** `claimDue`'s push is `next_run_at + claimWindow`. An overdue row would stay due on every 5 s tick. The skip sets an authored row's `next_run_at = now + claimWindow`, and a default copy's `last_run_at = now`, because its `next_run_at` must stay NULL (`routines_v1_default_next_run_at_chk`).
- **No new or changed routine schedule may use `?` (TASK-913, `repeatScheduleWriteIssue`).** croner fills `?` from the clock on every parse, so the same cron reads at :10 and fails at :40. Saved ones keep reading, and an edit that leaves the schedule unchanged still saves.
