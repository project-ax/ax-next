- **A pooled statement's bound is Postgres's own `statement_timeout`, sent at connect time through pg's `statement_timeout` client option (TASK-1056, measured).** The database cancels with SQLSTATE `57014` ("canceling statement due to statement timeout"), a surrounding Kysely transaction rolls back, and the same backend serves the next query. `@ax/database-postgres` and `@ax/session-postgres` default it to 30 000 ms (`statementTimeoutMs`); it bounds lock waits too (`pg_advisory_xact_lock`, `LOCK TABLE`, row locks). A migration or job that legitimately needs longer runs `SET LOCAL statement_timeout = 0` as the first statement of its own transaction — nothing is exempt centrally. Don't reach for pg's client-side `query_timeout`: it rejects the caller but the server keeps running the statement, and the next query on that pooled connection fails with "Query read timeout" too. A `57014` in a test log is a real >30 s hold, not a flake.
- **To make a SECOND pg client's connect hang while the first works, put a `node:net` proxy in front of the container (TASK-1056).** Forward the first N accepted connections both ways and never answer the rest; to read a connection's connect-time settings, parse its StartupMessage at the proxy (`readInt32BE(0)` length, then `\0`-separated key/value pairs from byte 8). pg Client's own connect-timeout message is `timeout expired`; pg-pool's is `Connection terminated due to connection timeout`, so the message tells you which client timed out. See `packages/session-postgres/src/__tests__/timeouts.test.ts`.
- **Every Postgres client now has a connect bound (TASK-1056).** session-postgres's pool and LISTEN client (`checkoutTimeoutMs`, default 5 000) and eventbus-postgres's LISTEN client (`connectTimeoutMs`, default 5 000; a timed-out attempt logs `eventbus_postgres_listener_connect_failed` and joins the reconnect backoff). This supersedes `patterns/2026-11-05-TASK-1049.md` row 2's "a pool built elsewhere (session-postgres, eventbus-postgres's client) still has the gap". The LISTEN clients get no `statement_timeout`, and need none: an idle LISTEN wait isn't a statement.
