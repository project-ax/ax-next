# TASK-469 — patterns

## An assertion that reads `toEqual([])` after a soft-failing read is vacuous

`egress-allowlist:list` deliberately swallows a store throw into `{ sites: [] }` —
correct for a settings panel, which should degrade rather than break. The consequence
is that **`expect(after.sites).toEqual([])` passes whether the row was deleted or the
read never reached the database.** Proved by construction, not by reading: mutant M13
made `listFor` throw unconditionally and the revoke case stayed green.

The fix is one line and it generalises: **read the list BEFORE the mutation and assert
it is non-empty.** Then the empty read afterwards means the row went away, because the
identical call returned it a moment earlier. After the fix M13 reddens 4 tests instead
of 1.

Rule of thumb: whenever the code under test has a `catch` that returns an empty
collection, an "it's empty now" assertion is evidence of nothing on its own. Pair it
with a "it wasn't empty a moment ago" from the same call.

## A boundary-only test cannot see a STRING/STRING comparison

**This entry was WRONG in its first version and was corrected by review. Read the
correction, because the wrong version is the plausible one.**

JS relational comparison (`<`, `>`, `<=`, `>=`) goes lexicographic **only when BOTH
operands are strings**. With one string and one number it coerces numerically. So:

```js
'6'   >= 512    // false  — numeric coercion, same as Number('6') >= 512
'6'   >= '512'  // TRUE   — lexicographic, and wrong
```

The mistake I made: the db egress cap is `Number(count) >= MAX_USER_HOSTS`, where
`count` is the string pg returns for a bigint and `MAX_USER_HOSTS` is a **number
literal**. I wrote down that dropping the `Number()` "makes it lexicographic". It does
not — the numeric RHS still forces numeric coercion, so that mutant is **equivalent**
and no test can kill it. I had nonetheless recorded it as KILLED, because the mutant I
actually ran added `String()` to the right-hand side too.

**What is actually true, and still worth the entry:** when both operands *can* be
strings, a boundary probe is blind by construction. `'510' >= '512'` is false and
`'512' >= '512'` is true — **agreeing with arithmetic at exactly the values a
boundary test looks at** — while `'6' >= '512'` is true and caps a person at six.

So the rule is narrower than "coercion bugs hide from boundary probes":

- **Both operands may be strings** (a driver value against an env var, two `process.env`
  reads, JSON against JSON) → a boundary probe is not enough. Walk a fresh counter
  through the low single digits; costs milliseconds.
- **One operand is a number literal** → the comparison is numeric whatever the other
  side is. `Number()` there is defensive style, not behaviour, and becomes
  load-bearing only if the literal is later replaced by config or env.

Keep the `Number()` either way. Just do not claim a test proves something it cannot.

Related shape in this repo: `Number(res.numDeletedRows ?? 0n) > 0` on the revoke path.
I nearly wrote here that this one IS load-bearing because mixing BigInt and Number
throws — **checked it, and that is also wrong**, which is the second time the same
reflex caught me in one task. BigInt/Number *comparison* is fine (`1n > 0` is `true`);
only *arithmetic* mixing throws (`1n + 1`). So that `Number()` is defensive style too.

The meta-lesson, and the reason this entry is three paragraphs of correction: **"a
coercion must be load-bearing because coercion is scary" is a vibe, not a fact.** Every
one of these is a one-line `node -e` away. Run it before writing it down — especially
when writing it into memory, where the next agent reads it as ground truth and cannot
tell a measured claim from a plausible one.

## Mutate the test you just wrote to close a mutation gap

Not rhetorical. Six of TASK-469's 23 mutants targeted the case added in response to
review, and three of them survived its first draft: M19b (the string/string compare),
M20 (the cap counting the whole table rather than one person — invisible because only
one user had rows), and M22 (the idempotence assertion, below). A test written
*because* something was unproven is not automatically proven itself.

## `{ ok: false }` proves nothing when a catch returns the same value

The db `remember` is idempotent via an existence check. The obvious assertion —
re-remember the same host, expect `{ remembered: false }` — **survives deleting the
existence check entirely**, because the INSERT then violates the primary key and the
hook's catch turns the throw into the identical `{ remembered: false }`. Mutant M22
proved it: check deleted, suite still 15/15 green.

Generalise: whenever a guard's "no" and an error path's "no" are the same value, an
assertion on that value cannot tell you which one ran. Find the one observable that
differs — here the error path logs `tool_policy_egress_remember_failed`, so the test
injects a capturing logger via `h.ctx({ userId, logger })` (`makeAgentContext` takes
`opts.logger`) and asserts the quiet path.

Same family as the `{ sites: [] }` swallow below: a deliberate soft-fail is good
product behaviour and an assertion hazard, in the same breath.

## An EQUIVALENT mutant is not a surviving one — say which

Two of TASK-469's survivors were equivalent. M21 applied the cap to `global` entries
too: a global entry's owner key is `''`, so the count query becomes
`scope = 'user' AND owner_user_id = ''`, matches nothing, and never caps. M19a dropped
a `Number()` whose right-hand side is a number literal. Neither changes behaviour, so
no test could kill either.

**And "equivalent" is a claim that needs proving like any other.** I got M19a wrong in
the other direction first — recorded it KILLED when the mutant I ran was a different
one. The discipline is: state the mutation exactly as applied, and if the result
surprises you, work out the language semantics before writing the row.

Record equivalent mutants explicitly with the reasoning. An unexplained survivor in a
ledger reads as an open hole, and the next reader either re-investigates it or — worse
— writes a test that cannot fail in order to "close" it.

## Distinguish a Docker daemon that is alive / dead / WEDGED by making it work

`docker version` rc=0 and `docker info` counts are not liveness. A wedged daemon has
been observed answering `docker ps` with rc=0 and empty output while `docker info`
reported 39 containers, and `postgres:16-alpine` sat at `health: starting` for seven
hours. Before planning a testcontainer run:

```bash
timeout 60 docker run --rm alpine:3 echo LIVE
```

An image pull plus an exec is work. rc=0 from a status subcommand is not. This is a
~2 s probe that prevents planning a whole card around a daemon that will hang.

## Mutating a suite: assert the match count, and assert the restore is byte-identical

Two failure modes make a mutation run lie, and both are silent:

1. **The mutation patched nothing** — the `find` string drifted, the replace was a
   no-op, and the mutant reads as SURVIVED. Guard: require the find string to match an
   **exact expected count** and refuse otherwise, then assert `git diff` is non-empty
   after writing.
2. **The restore was not verbatim** — guard by hashing the file before mutating and
   re-hashing after `git checkout -- <path>`, plus `git status --porcelain` empty.

Restore with `git checkout -- <path>`. Never a `cp` backup: it reverts the whole file
including work that was not yours. And **commit before you mutate** — `git checkout --`
reverts the whole file, so anything uncommitted in it is gone.

Also check the **total** each round. A mutant that makes the count shrink has removed
tests rather than reddened them; the question to ask is not "did the total shrink" but
"did something go red when it shrank".

## A canary's own fail direction is mutable, and worth three rounds

For a test suite that talks to a real backend, mutate the *harness*, not only the code:

- point the connection string at a dead port → the suite must go **red**, not skip
- make every read return zero rows → red
- make the read **throw** → red (this is the one that catches soft-fail swallowing)
- disable the real store so the plugin falls back to its in-memory one → red

That last one is how you learn which single test is holding the door. For the egress
canary it is the "survives a restart" case, and nothing else — worth knowing before
someone simplifies it away.
