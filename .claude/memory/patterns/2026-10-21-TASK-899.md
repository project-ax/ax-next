- `2026-10-21` (TASK-899) — **An errno test must inject the shape Node really produces, and on Linux some errnos have no name.** libuv names most errnos but not ESTALE (116), so on Linux Node 24 rejects with `code: 'Unknown system error -116'` and `errno: -116`. A test that injects `{ code: 'ESTALE' }` passes against a rule that never fires: that is how round 1's "ESTALE below the root is absent" rule shipped dead. Check a name with `util.getSystemErrorName(-n)` before writing a fixture, and read the name from `errno` against `os.constants.errno` when `code` is not an `E…` name (the walk's `errnoOf` in `packages/user-files-read/src/walk-read.ts`).
- `2026-10-21` (TASK-899) — **A loopback NFS harness can hide stale handles in two ways, and both look like "it heals by itself".** (1) A fresh process under a new cred for every read (`setpriv … node probe.ts`) makes the NFS client send ACCESS for each directory it passes, since its access cache only trusts entries newer than the process's "login". Measured with `/proc/self/mountstats`: 4 ACCESS calls per read from a fresh uid-1000 process, 0 from one long-lived reader. ACCESS replies refresh the directories' attributes, so a stale entry gets looked up again. Production's host is one long-lived process, so probe from one long-lived reader per scenario. (The reviewer's root probe, a fresh process per read, did reproduce it, most likely because every parent of a root process has the same cred.) (2) A blanket `chown -R` after the agent's move bumps the ctime of every directory, which has the same effect. Make the agent's moves as the agent's uid, touching only what the agent would touch. TASK-899's harness (kernel nfsd exporting a tmpfs, mounted NFSv3 over loopback in a privileged node:24 container) reproduced production's ESTALE only with both fixed.
