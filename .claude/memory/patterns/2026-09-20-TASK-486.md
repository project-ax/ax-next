# TASK-486 — patterns

## "Who originated this apply?" has exactly one honest answer: the code path

Anywhere in this repo where a guard has to distinguish *the sandbox asked for
this* from *the host asked for this*, do NOT look for a field in the payload.
`workspace:pre-apply` fires from two places — the in-process
`workspace:apply` facade (host) and `workspace.commit-notify` (runner) — with
payloads that differ only in `reason`, which the runner supplies. Put the guard
in the handler that *is* the untrusted origin. It is unbypassable by
construction and needs no field to trust.

## Two path lists in `@ax/core/workspace-policy.ts`, two different questions

- `POLICY_PREFIXES` / `POLICY_EXACT_PATHS` / `filterToPolicy` — *what do
  `workspace:pre-apply` subscribers get to SEE*. Also read by
  `agent-runner-core/src/governed-paths.ts`, which re-roots every matching path
  into `/agent`. Widening this is never local.
- `RUNNER_IMMUTABLE_PATHS` / `findRunnerImmutableViolations` — *what may a
  runner-originated apply CONTAIN*. No subscriber, no veto knob, no transform.

A path can be in the second and not the first. That combination is the point:
the human memory tier is defended without becoming visible to validators or
re-rooted by the runner's tool policy.

## `discardPaths` is an `rm`/revert target inside the sandbox

The pre-apply branch re-checks that a rejecting subscriber only named paths the
host actually sent it, and fails closed to a whole-tree reset otherwise —
because a subscriber is plugin code. A guard whose paths come from a fixed
constant needs no such check, and saying so in the comment is worth more than
copying the check: it tells the next reader why the two branches differ.

## Verifying a guard: assert the *effect* never ran, not just the response

`accepted:false` is also what a guard that refuses AFTER landing the write would
return — which is the exact bug class this card fixes. The load-bearing
assertion is a spy on `workspace:apply-bundle` with
`expect(applyBundle).not.toHaveBeenCalled()`. `makePhase3Probe` in
`ipc-core/src/handlers/__tests__/workspace-commit-notify.test.ts` registers the
service inline and hands back nothing, so a spying variant is needed.

## Typechecking test files in this repo

`pnpm build` is `tsc --build` and every package's tsconfig excludes
`src/__tests__/**`, so vitest-green says nothing about test-file types. A
throwaway `tsconfig.tests-check.json` (extends the package config,
`noEmit: true`, `composite: false`, `include: ["src/**/*"]`, no exclude)
typechecks them — but expect a wall of PRE-EXISTING errors (`result.body` on the
`HandlerResult` union is the common one across `ipc-core`). Grep the output for
your own filenames; comparing against the pre-existing baseline is the only way
to read it. Delete the file afterwards.
