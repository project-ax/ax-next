- **2026-09-29 (TASK-696): a credential that must be presented to a server later has to CARRY the identity it was issued under; an index into a mutable shared row is a race and a cross-tenant bug waiting.** `@ax/mcp-oauth` stored the OAuth client (DCR result) in one row per `connectorId|authServerUrl` and every token held only that key, so a later connect (another agent, another user with the same slug, an overlapping begin) silently re-pointed every earlier token at a client that did not issue it; a strict RFC 6749 AS then answers `invalid_grant`. The fix is not a better lock on the row: the blob and the pending row now carry `clientId`/`clientSecret` themselves, and the shared row became a READ-ONLY legacy fallback. When you migrate that way, STOP WRITING the old row in the same PR: a new writer keeps clobbering the legacy tokens that still read it (that is why `putClient` was deleted, not left "for rollback").
- **2026-09-29 (TASK-696): classify a dead OAuth credential by the SDK error's type, not its message — `errorCode` in {`invalid_grant`,`invalid_client`,`unauthorized_client`} (duck-typed, no `instanceof`).** The MCP SDK builds `err.message` from the server's free-text `error_description`, which need not contain the wire code, so `message.includes('invalid_grant')` both misses real rejections (`/status` answered 500 "Couldn't check the connection" instead of offering Reconnect) and can match unrelated text. `OAuthError` exposes `errorCode` (a prototype getter) and names each subclass after itself; use those, and let everything else stay transient (rethrow, never wipe the refresh token). Once a token refreshes as its OWN DCR client, `invalid_client`/`unauthorized_client` mean the AS expired or re-keyed that client: same remedy (Reconnect).
- **2026-09-29 (TASK-696): to prove a fix for a "strict server" bug in-process, fake only `fetch` and DNS and keep the whole real stack, with the fake enforcing the RFC rule.** The probe's `FakeAs` binds codes and refresh tokens to the issuing client, so the SAME tests are red on the unfixed code (11 of 18) and green after, and a lenient-AS control proves the strictness is what matters. An SSRF-guarded plugin cannot use an in-cluster mock AS (http/private-IP rejected), so this shape is the practical one. Label tests that pass either way `[CONTROL]`.
