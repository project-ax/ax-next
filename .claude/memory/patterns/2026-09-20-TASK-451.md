# patterns — TASK-451 (2026-09-20)

## Focus moved from an effect belongs in `useLayoutEffect`, not `useEffect`

React runs a passive `useEffect` in a task of its **own**, after the commit that
put the node on screen. So any `useEffect(() => el.focus())` leaves a window —
one whole task wide — in which the new node is in the document, focusable, and
`document.activeElement` is still `<body>`. A layout effect runs inside the
commit, before paint and before any `MutationObserver` microtask, so the window
does not exist.

That window is what made `consent-focus.test.tsx` a once-a-fortnight red on
`main` (CI run 35484852089). `lib/consent-focus.ts`'s `useResolutionFocus` now
uses `useLayoutEffect`. Same shape still exists, unfixed, in
`src/App.tsx` (settings-close focus restore) and
`src/components/ui/use-opener-restore.ts`.

## Why a focus-after-async test is flaky and not deterministically red

`@testing-library/react`'s `asyncWrapper` (see `dist/pure.js`) sets
`IS_REACT_ACT_ENVIRONMENT = false` for the whole duration of every `findBy*` and
`waitFor`, then drains with a **single** `setTimeout(0)`:

```js
asyncWrapper: async cb => {
  setReactActEnvironment(false)
  const result = await cb()
  await new Promise(resolve => { setTimeout(resolve, 0) })   // one tick, that is all
  ...
}
```

With act off, React schedules through its own MessageChannel instead of act's
queue. So a passive effect is a MessageChannel task racing that one timer.
Node usually runs the MessagePort callback first, which is why these tests pass
locally and in ~99% of CI runs. Under load the timer sometimes wins.

Corollary: assertions driven by `fireEvent` alone are **not** subject to this.
`fireEvent` wraps in synchronous `act()`, which flushes passive effects before
it returns, so `document.activeElement` is settled on the next line. Only the
paths that go through an `await findBy*`/`waitFor` can lose. Do not
blanket-convert the synchronous ones to `waitFor` — it trades an exact
assertion for a retried-until-deadline one and buys nothing.

## A deterministic test for "focus landed with the render, not after it"

`waitFor` can only prove focus lands *eventually*. To prove there is no window
at all, read focus from a `MutationObserver` — its callback runs at the
microtask checkpoint of the very task that did the mutating, i.e. the earliest
instant anything (a screen reader, the paint, the test) can see the node:

```tsx
const focusWhenSaid: (Element | null)[] = [];
const observer = new MutationObserver(() => {
  if (focusWhenSaid.length > 0) return;
  if (document.querySelector('[data-testid="…"]') === null) return;
  focusWhenSaid.push(document.activeElement);
});
observer.observe(document.body, { childList: true, subtree: true });
// … drive the async answer, then:
const line = await screen.findByTestId('…');
expect(focusWhenSaid).toHaveLength(1);   // never vacuous
expect(focusWhenSaid[0]).toBe(line);
```

Red for a passive effect, green for a layout effect, on any scheduler — verified
by mutation both ways. The `toHaveLength(1)` is load-bearing: without it the
case passes vacuously if the observer never fires.
