# TASK-442 — announcing a consent answer (live region beside a focus landing)

## A live region must outlive the branch it announces

`ApprovalCard` and `DecisionRow` each return two completely different subtrees —
the question card and the receipt. A live region rendered inside the resolved
branch is *inserted already holding its message*, which assistive tech does not
reliably announce (same reason `ThreadFind`'s announced count is permanently
mounted). The fix is to hoist it above the branch split: both renderers now
return `<>{announcement}{body}</>`, so React keeps the region node across the
swap.

**The test that catches the wrong version is node IDENTITY, not text.** Capture
the region element before the transition, assert `expect(region()).toBe(before)`
after it. Measured: moving the region inside the branch turns 6 cases red while
the visible text stays correct — a text-only assertion passes against the bug.

## Three more ways this shape goes wrong

- **Speaks on mount.** `InThreadApprovals` draws every receipt resolved in the
  last ten seconds on page load; a region holding its sentence on the first
  render reports a past event as news. Start `seen` AT the current answer
  (React's "adjust state when a prop changes"), not at `null` — measured, 4
  cases red the other way.
- **Shares a node with a countdown.** `role="alert"` implies `aria-atomic`, and
  `useDecisionClock` re-renders a resolved row twice a second. The region gets
  its own node, and the test advances fake timers and asserts the visible
  `Undo · Ns` label DID change while the announcement did not — otherwise the
  case passes on a card that never re-rendered.
- **`hidden` instead of `sr-only`.** `display:none` leaves the a11y tree.
  `sr-only` is `position:absolute`, so it is also not a flex item and adds no
  gap to the `flex … gap-2` containers these cards sit in.

## Focus landing ≠ announcement, but it is not nothing either

TASK-427's landing does get the focused node read. What it cannot carry:
`outcome.note` is a SIBLING of the focused node in both renderers, and the
landing is armed by the person's own click, so an answer arriving any other way
is silent. Worth saying precisely in a PR rather than repeating a card's
"never told what happened".

## Adding a second `role="alert"` breaks `getByRole('alert')`

Two existing consent-focus cases queried the row's shadcn `Alert` that way and
went ambiguous. Scope such queries to the VISIBLE alert and assert the count,
rather than leaning on there being exactly one.
