# TASK-719 — patterns worth reusing (2026-09-29)

- **2026-09-29 (TASK-719): when a plugin owns a directory of per-agent data, it deletes it itself on `agents:deleted`, behind a tombstone, under the same mutex its writers use.** The path comes only from the plugin's own one-way id function, never from the payload. Order inside the subscriber: validate the id (non-empty string, else log and return) -> add the id to an in-process tombstone `Set` BEFORE waiting on the mutex -> `mutex.run(rm)` -> fire a notify hook (`workspace:deleted { agentId }`) only after the removal succeeded -> return `undefined`. Setting the tombstone inside the mutex is wrong: a write queued ahead of the delete would commit first and then be removed. Check the tombstone in ONE wrapper next to every call that can create the directory, and again inside the mutex (a queued write passed its first check before the tombstone existed). Never remove the mutex map entry after a delete: a fresh Mutex for the same id stops serialising against the old one.
- **2026-09-29 (TASK-719): a second plugin that keeps a ledger about the first plugin's bytes releases its row from a notify hook the first plugin fires AFTER removal, not from `agents:deleted`.** The ledger then means "what is on disk": a failed `rm` leaves both. Same shape as `conversations:purged`. It is also order-independent (subscribers run in plugin init order). Make the release wait for any in-flight measurement of the same key before it deletes, or a stale measurement re-creates the row; and make the measured hook THROW for a deleted agent (not report 0) so a late measurement cannot write a fresh row.
- **2026-09-29 (TASK-719): to let a route tell one `rejected` from another, carry a machine code on the veto, not the plugin name.** `reject({ reason, code })` -> facade -> `PluginError.reasonCode`; `PluginError.code` stays `'rejected'` so every existing `code === 'rejected'` caller keeps working. Build only the keys that are present and prove absence with `'code' in x === false`. A plain class field is emitted as an own `undefined` property at ES2023, so `reasonCode` had to be `declare readonly reasonCode?: string` and assigned only when set; vitest and tsc both honour that.
- **2026-09-29 (TASK-719): routes in another package cannot share the recognition helper, so each writes the same three-part check and a fixed sentence, and each pins the exact body in a test.** A veto's own message is written for its original reader (here, the model); a route that passes `err.message` through shows that reader's sentence to a person. Send `413 { error, message }` with the route's own constant, and have the client display the server's `message`.
- **2026-09-29 (TASK-719): a client error reader has to be tested against the shape the SERVER sends, not the shape a mock author guessed.** The routines client read `body.error?.message` while the server sends `{ error: '<string>' }`, so every failure read "HTTP 400" and the existing tests (which mocked `{ error: { message } }`) never noticed.
- **2026-09-29 (TASK-719): a mutation that kills a concurrency test is worth more than the test's first green.** Ten mutants on the delete path found two defective tests (a queued-write test that passed without the in-mutex re-check, and one failed assertion that hung the whole suite).

## Anti-Patterns

- **Do not decide a card is "one PR" because it is one card.** TASK-719 listed five follow-ups; the two that need a reference authority and a race-safe delete (blob GC, blob backfill) were carded, and the part with a clear authority shipped.
