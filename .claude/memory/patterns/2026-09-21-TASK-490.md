# TASK-490 — patterns for a fire-and-forget subscriber

**A `chat:end` subscriber that does real work must detach AND must not throw,
and those are two separate defences against two separate defects in
`HookBus.fire`.**

- `fire()` has **no clock** (`packages/core/src/hook-bus.ts` says so in as many
  words: "`fire` has no timeout — deliberately, since a subscriber's slowness
  must not fail the thing it is observing"). A subscriber that *awaits* a ~30s
  LLM call holds the turn open for as long as the provider takes, with nothing
  outside it able to end the wait. **Detaching is what makes slowness free.**
- `fire()`'s failure log is **unguarded**: `ctx.logger.error('hook_subscriber_failed', …)`
  raises a `TypeError` under a ctx with no logger, and that `TypeError` escapes
  `fire()` — skipping every REMAINING subscriber and reaching the caller under
  the wrong error's name. **A handler that cannot throw cannot reach that
  path.**

The shape: `const work = doTheWork(...).catch(() => {}); return undefined;`
with the work function itself wrapping everything in a try/catch that logs. The
price is that every failure becomes invisible unless it emits an event — so the
tests assert an event on **every** failure path, not only the happy one.

**Test seam for a detached subscriber: hand the promise out, never sleep.** A
config callback (`onObserverDetached?: (work: Promise<void>) => void`) that the
plugin calls with the already-`.catch()`-ed promise lets a test await the chain
deterministically. It cannot make `chat:end` wait, because the subscriber has
already returned by the time it fires. `@ax/memory-strata` uses the same idea
with a per-agent settle map.

**Proving "returns without waiting" needs a gate, not a stopwatch.** Block the
stub provider on a promise the test controls, `await bus.fire(...)`, assert the
store is still empty, then release. If the subscriber awaited its work the test
deadlocks and times out — a timing assertion would have been flaky instead.

**Forcing a mid-batch store fault: a SQLite `RAISE(ABORT)` trigger from a second
connection.** No mocks, no monkey-patching, and the failure lands exactly where
a real constraint violation would. `@ax/memory-facts-sqlite`'s own
`batch-atomicity.test.ts` established it; a consumer can reuse it by taking the
engine's `databasePath` off the harness. Count rows on that second connection
too — `memory:recall` shows only active, owner-scoped rows, and "did the batch
roll back" is a question about every row.

**The mutation battery found the guard no behavioural test covered.** Deleting
`if (result == null || !Array.isArray(result.records))` in the observer reddened
**nothing**, because the real sqlite engine always answers with a records array.
The case that matters is not `null` (which throws a bare `TypeError` a catch
block still reports) but a **wrong-typed** `{records: 'nope'}`, which reports
`recorded: 4` for a batch that wrote nothing. A stub engine is the only way to
reach it — the real one cannot produce it. Predict-then-diff also caught a
prediction of mine that was wrong for a good reason: loosening the role filter
did NOT redden the "nothing but tool output" test, because `hasUserContent` is a
second, independent gate.
