## 2026-09-19 — TASK-426 Allocating a shared id without an atomic counter

- `2026-09-19` (TASK-426) — **Claim optimistically, verify against a fresh read, and let a DETERMINISTIC rule pick who yields.** GitHub Projects v2 has no atomic counter and no uniqueness constraint on a card title, so `[TASK-n]` collisions cannot be *prevented* through that API — and `scripts/board-task-id.sh` does not claim to. What it removes is a collision that **survives**: after creating the card it re-reads the board, and if another card carries the same number, the colliding card with the **lowest item node id keeps it** while every other one renumbers **itself**. Both racers read the same board and compute the same winner, so exactly one moves. The alternative everyone reaches for first — randomized backoff and retry — is a *strictly worse* rule, and a mutant proves it: with "always yield", both parties move, both land on the same `max+1`, and they collide again. Randomness is fine as a desynchroniser; it is not an election.
- `2026-09-19` (TASK-426) — **The invariant that makes two concurrent settles safe is "a process only ever renames its OWN card".** It never edits another session's, which is also why this runs at **creation** rather than at triage: a card seconds old has zero references, while by triage the dispatch prompt and the `Depends on` field are already written. That is the mechanised form of the existing hand-rule "renumber the card with FEWER references" — at creation time the answer is always "mine".
- `2026-09-19` (TASK-426) — **A board-reading guard must treat "parsed fine, zero items" as a FAILED READ, not a clean board.** `check` exits 2 on an unreadable board, an unparseable reply, *and* a reply that parses to an empty array. The ax-next board has never been empty, so "no cards" is the signature of a truncated page, a wrong project number or a revoked token — and "no cards, therefore no duplicates" is the fail-open shape. A mutant that removes only the `length > 0` test (keeping the read-failure guard) reddens exactly one test, which is how quietly that one goes.
- `2026-09-19` (TASK-426) — **For a board read that only needs ids and titles, write the paginated GraphQL query by hand: ~1 point a page instead of `gh project item-list`'s ~102.** Ask for `content{ ... on DraftIssue{ id title } }` and the `DI_` content id arrives in the same read, so a later `--title` edit needs no second lookup hop (the TASK-401 gotcha). Pagination is not optional — the board passed 300 items in Aug 2026 and Done cards never leave, so a lone `first:100` computes the max from the OLDEST cards and hands back a number several live cards already hold.
