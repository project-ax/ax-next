# TASK-489 — patterns

## A lookup table keyed by model output must not be a plain object

`dem-memory/src/slots.ts`'s `synonymNormalizer` is
`SLOT_SYNONYMS[relationToWords(relation)] ?? null` over an object literal. That
is a real bug, not a style point, and it survives a straight port: a plain
object lookup walks `Object.prototype`, so `table['constructor']` is the
`Object` constructor — a truthy **function** — and the `?? null` behind it never
runs.

MEASURED, in this repo, by mutation M3 (revert the shipped `Map` to
plain-object indexing): two cases go red, and on the un-guarded version
`deriveSlot('constructor')` returns a function that `memory:remember` would then
put on the `memory:facts:record` payload as a row's supersession key.

`relationToWords` lowercases and turns `_` into spaces first, which narrows the
reachable set but does not empty it: `constructor` survives verbatim;
`__proto__` becomes `proto` and `toString` becomes `tostring`, so those two are
already harmless. One reachable key is enough.

The fix is `new Map(Object.entries(literal))` — the object literal stays as the
readable audit surface, `Object.entries` copies own enumerable keys only, and
`Map.prototype.get` has no prototype chain. Keep the literal; change the lookup.

## Omitted vs `null` on an optional engine field, and the assertion that tells them apart

`FactStatementInput.slot` is optional and **absent means "no slot"**. Sending
`slot: null` instead is a different claim, and MEASURED (mutation M5, send it
unconditionally) the sqlite engine rejects it — 20 tests red, most of them
unrelated cases that merely happened to record a row.

`expect(row.slot).toBeUndefined()` passes for both spellings. Only
`expect(Object.hasOwn(row, 'slot')).toBe(false)` separates them. When a payload
distinguishes absent from null, assert on the key, not on the value.

## Mutating a lookup table finds the tests you did not write

A lookup table is the shape where every test calls the function directly and
nothing covers its wiring into the write path. Two of the seven mutants here
reddened tests I had not predicted, and both were informative:

- M1 (`?? SLOTS[0]` instead of `?? null`) reddened a **pre-existing** case in
  `engine-contract.test.ts` whose title still read "slot derivation is a later
  card". It had been passing only because its relation `r` is not in the table.
  A mutant is how a stale test premise surfaces.
- M1 also reddened `clamps limit to the configured ceiling`, which records
  several rows and counts them — once every relation maps, they all supersede
  each other and the count changes. A test can depend on "nothing closes
  anything" without ever saying so.
