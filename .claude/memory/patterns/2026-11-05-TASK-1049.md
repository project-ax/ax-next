- **To make a pg checkout genuinely hang without Docker, point the pool at a `node:net` server that accepts and never writes (TASK-1049).** Both pg-pool paths hang: the new connection (`connectionTimeoutMillis` rejects it with `Connection terminated due to connection timeout`) and, with `max: 1`, a second caller queued behind it (`timeout exceeded when trying to connect`). Give each accepted socket an `'error'` listener (the client resets it on timeout), and close the server through a promise — `server.close()` returns the server, not a promise. To hang the QUEUED path against a real Postgres, use `poolMax: 1` and hold the only connection inside `db.connection().execute(async () => { held(); await gate; })`, racing `held` against the holder so a failed connect fails the test at once. See `packages/database-postgres/src/__tests__/checkout-timeout.test.ts`.
- **pg-pool never rejects a queued caller when the pool ends (TASK-1049, measured).** `pool.end()` drops only idle clients, so a caller waiting behind a full pool with no `connectionTimeoutMillis` waits forever, even after the pool has ended. `@ax/database-postgres` now defaults `checkoutTimeoutMs` to 5 000 ms; a pool built elsewhere (session-postgres, eventbus-postgres's client) still has the gap.
- **A routines test that boots `@ax/database-postgres` runs that package's built `dist`, not its `src` (TASK-1049).** Rebuild it (`pnpm --filter @ax/database-postgres build`) after changing its `src`, or the routines test silently runs the old code — which is also how to prove such a test red: mutate the src, rebuild, run, then restore with `git checkout HEAD --` and rebuild again.
- **pg-pool's timeout errors carry no `code` (TASK-1049).** `faultLogFields` on them yields `{ name: 'Error' }` (queued) or `{ name: 'Error', causeName: 'Error' }` (new connection). A code-only log line for a pool timeout is therefore one line with no code; tagging the error is a follow-up.
