## A contrast probe that reads the token is wrong wherever the class is fractional

Tailwind's `bg-<token>/<pct>` paints an alpha-composited surface. No custom property
holds that colour, so a probe (or a test) that pairs `--muted-foreground` against
`--warning-soft` is measuring a surface the product never renders.

`ApprovalCard` is the worked example. Declared token: 4.10:1 in dark. Actually painted
(`bg-warning-soft/40`): 5.03 light, 5.51 dark over `--background`, 4.66 dark over
`--card`. The card reporting the defect and the file denying it were both right — about
different pixels.

Two consequences worth reusing:

- **A dark-only contrast report is a tell.** Light mode's `--card` and `--background` are
  the same white, so compositing barely moves the number; dark mode's backdrops differ by
  11 points of lightness, so ignoring alpha only shows up there. "Light passes, dark
  fails, same element" should prompt "is this surface fractional?" before "which token do
  we move?".
- **Read the alpha out of the component, do not hard-code it in the test.** A literal
  `0.4` in the test keeps measuring 4.66:1 forever, including after someone deletes the
  `/40` and ships the 4.10:1 defect for real. Parsing the class from the source makes the
  assertion track what ships: drop the alpha and the AA row goes red with the true ratio,
  rather than a separate "don't edit this class" guard nobody can act on.

`packages/channel-web/src/__tests__/theme-contrast.test.ts`, section
`ApprovalCard's tinted surface`, has `composite()` and the parser.
