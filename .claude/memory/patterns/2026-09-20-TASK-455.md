# TASK-455 — patterns

## A surviving mutant means "find the second mechanism" — then check the second mechanism's SCOPE

`AgentFiles` below `md` keeps a folder tap off the viewer via
`showViewer = drilledIn && hasSelection`: the folder branch does not set the
latch. Mutating that branch to set it left all nine compact tests green, so I
concluded a second mechanism made it an *equivalent* mutant —
`useAgentUserFiles.openDir` clears the open file on the way into a folder, so
`hasSelection` goes false regardless. I wrote that up as defence-in-depth and
committed it.

**It was wrong, and a reviewer caught it.** `openDir` calls `setFilePath(null)`
— the DURABLE tier's file. It never touches `governed.openPath`; the two tiers
are separate hooks and neither reaches into the other. So the second mechanism
covers only *half* the selections. Open a GOVERNED file, press Back, tap a
DURABLE folder, and the latch is the sole guard — the mutation is single-point
killable and reachable by an ordinary user. Every folder test in the suite had
used a durable selection, which is precisely why the mutant read as equivalent.

Three things generalise:

1. A surviving mutant is evidence about the CODE as often as about the test —
   but "I found the second mechanism" is only half the check. **Ask what the
   second mechanism's scope is.** Here it was one of two tiers, and the tests
   all happened to sit inside that scope.
2. When a guard has two tiers / two sources / two backends behind one boolean
   (`hasSelection = durableSelected !== null || governedSelected !== null`),
   a mutation test that exercises one arm proves nothing about the other.
   Enumerate the arms of the disjunction and cover each.
3. **Do not write an "equivalent mutant" claim into memory from a green run
   alone.** Green under mutation is the *start* of the argument. Trace the
   claimed second mechanism to its source and read what it actually sets.
   `prose claims need verification too` applies to my own mutation analysis.

## Measuring a responsive fix: swap the file, don't build a second worktree

Disk was at 98%, so the "second worktree at origin/main for a true before/after"
recipe was too expensive. Cheaper and exactly as honest, with Vite HMR running:

    git show origin/main:<path> > <path>   # measure "before"
    git checkout -- <path>                 # measure "after"

Same dev server, same harness, same fetch stub, same selectors — strictly fewer
confounds than two checkouts. `git checkout --` is also the restore the
mutation-testing rule demands (never a file copy).

The harness itself goes in `packages/channel-web/harness/` — OUTSIDE `src` AND
`mock`, because that package's tsconfig `include` is `["src", "mock"]` and a
stray entry in either is a `tsc --build` failure. Delete it before committing;
`.git/info/exclude` does NOT work from a linked worktree's gitdir (the worktree
gitdir has no `info/` and creating one is ignored — the shared repo's one is
what applies).
