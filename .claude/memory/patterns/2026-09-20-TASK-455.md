# TASK-455 — patterns

## Defence-in-depth turns single mutants into EQUIVALENT mutants — say so, don't fake teeth

`AgentFiles` below `md` keeps a folder tap off the viewer two independent ways:
`showViewer = drilledIn && hasSelection`, and `useAgentUserFiles.openDir`
already clears the open file on the way into a folder. So each single mutation
— setting the drill-in latch on the folder branch, or routing dir rows through
`selectDurable` — left all nine compact tests GREEN. Only the *combined* mutant
(latch on the folder branch AND `openDir` no longer clearing) reopens the pane.

The wrong reaction is to call the test worthless, or to contort it until some
single mutant dies. The right one is to record which mutants are equivalent and
why, in the test's own comment, so the next reader does not re-derive it and
does not mistake the test for a differentiating guard. A test that only a
2-point mutant kills is still the only thing standing between you and that
2-point mutant.

Corollary for the predict-then-diff habit: a surviving mutant is evidence about
the CODE (two mechanisms enforce this) at least as often as about the test.
Check the second mechanism before editing the test.

## Measuring a responsive fix: swap the file, don't build a second worktree

Disk was at 98%, so the "second worktree at origin/main for a true before/after"
recipe was too expensive. Cheaper and exactly as honest, with Vite HMR running:

    git show origin/main:<path> > <path>   # measure "before"
    git checkout -- <path>                 # measure "after"

Same dev server, same harness, same fetch stub, same selectors — strictly fewer
confounds than two checkouts. `git checkout --` is also the restore the
mutation-testing rule demands (never a file copy).

The harness itself goes in `packages/channel-web/harness/` — OUTSIDE `src` AND
`mock`, because that package's tsconfig `include` is `["src", "mock"]` and a
stray entry in either is a `tsc --build` failure. Delete it before committing;
`.git/info/exclude` does NOT work from a linked worktree's gitdir (the worktree
gitdir has no `info/` and creating one is ignored — the shared repo's one is
what applies).
