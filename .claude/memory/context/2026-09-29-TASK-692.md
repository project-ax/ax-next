# TASK-692 — context (per-user spend and rate limits)

- 2026-09-29 (READ-FROM-CODE): agent model traffic NEVER touches `llm:call:*`. Both runners call the provider from inside the sandbox; the only host hop is the credential proxy, a raw MITM byte pipe (`credential-proxy/src/listener.ts` `handleMITMConnect`) that swaps the `ax-cred:` placeholder for the real key and never parses a response. Its `event.http-egress` audit fires once per CONNECT tunnel (keep-alive tunnels carry many requests), so it cannot count tokens or model requests. `llm:call:anthropic|openrouter` serve only host helper calls (conversation titles, memory extraction, skill safety scan). A card that says "meter at the provider layer" is describing the minority of spend.
- 2026-09-29: the metering seam is `LoopContext.endTurn(EndTurnInput)` in `agent-runner-core`. Each turn emits up to TWO `event.turn-end`s (role 'tool', then role 'assistant'); the assistant one is unconditional, so it is the one that carries `usage`. The host sees it as `chat:turn-end` (fire-and-forget after the ack, payload = the zod-parsed `EventTurnEnd`). `event.turn-end.usage` existed in the schema since Week 10-12 with NO producer until TASK-692.
- 2026-09-29: `chat:start` fires for EVERY `agent:invoke` (web chat, routines, warm-routed turns) and a veto surfaces as outcome reason `chat:start:<reason>`, which channel-web renders through `ERROR_LABELS` in `lib/turn-error-labels.ts`. Each `chat:start` subscriber is bounded at 60 s (`CHAT_START_SUBSCRIBER_TIMEOUT_MS`); a subscriber that has not settled is SKIPPED and the turn proceeds, so a gate on that hook fails open under a database that stalls past 60 s (it fails closed on any error it can see).
- 2026-09-29 (found by review, then verified by grepping every `session:queue-work` producer): `agent:invoke` is NOT the only way a turn starts. `@ax/decisions` `deliverResolution` queues a `decision-resolved` entry onto a warm runner's inbox (on approve, dismiss AND expiry, via `runDueDeliveries`), and the runner starts a new turn from it. `chat:start` never fires for it. Every other `user-message` producer is inside the orchestrator. `deliverResolution`'s `delivered:false` also made `runDueDeliveries` fall back to running the approved tool call HOST-SIDE (`decision_delivery_fell_back_to_replay`), so a gate on the wake-up must return a distinct `refused` reason or the fallback would act for a paused account.
- 2026-09-29: `SDKAssistantMessage.message` is a `BetaMessage` with `id` and `usage` (cache fields nullable); ONE API response reaches the runner as several `assistant` messages (one per content block) sharing the id and usage. Whether `result.usage` / `total_cost_usd` is cumulative across a streaming `query()` cannot be read from the types, so the runner sums per-message usage de-duplicated by id and does not use `result.usage`.
- 2026-09-29: `ai@7.0.70` `LanguageModelUsage.inputTokens` is the TOTAL input (cache reads and writes included) with `inputTokenDetails.{noCacheTokens,cacheReadTokens,cacheWriteTokens}`; `outputTokens` already includes reasoning. Summing `inputTokens` straight would bill every cached token at the full input rate on top of its cache rate.
- 2026-09-29: the k8s preset's `createK8sPlugins` is also the base of `presets/memory`, so a plugin added there loads in both presets' tests. The test-harness stub runner emitted no `event.turn-end` before this card, so no acceptance test exercised runner -> IPC -> `chat:turn-end`; it now has a `turn-end` script entry.
- 2026-09-29: `presets/k8s/src/__tests__/prod-bootstrap.test.ts` already fails `tsc` (TS2741: its fake k8s client lacks `readNamespacedPodLog`); vitest does not type-check so the suite passes. Not from this card.
- 2026-09-29 (KNOWN GAP, returned as a follow-up): user code inside the sandbox can call the provider directly with the placeholder key (`curl` with `$ANTHROPIC_API_KEY`); that spend is gated at the door (a suspended or over-cap user cannot start a turn) but its tokens are not counted, because only the credential proxy sees those bytes. Closing it means response parsing in the proxy.
