# TASK-718 — project facts (2026-09-29)

- **Nothing ever hard-deleted `conversations_v1_*`.** `conversations:delete` is a soft delete (`deleted_at`); `session:terminate` only sets `terminated`. Since TASK-718, `agents:deleted` hard-deletes conversations + events + transcripts (`ConversationStore.purgeForAgent`, keyed on `agent_id` alone, soft-deleted and hidden rows included). User-initiated conversation delete is STILL soft and still leaves events, transcripts and artifacts (follow-up).
- **Deleting an agent now cleans:** conversations (+events, transcripts), attachments files/artifacts rows (via `conversations:purged`), session-postgres sessions/inbox/owner rows (terminated first, which revokes the runner's token), skills x4, connectors_authored, host_grants, decisions, mcp_oauth_pending, memory_facts_v1 (postgres AND sqlite, including the sqlite FTS5/vec0 shadow rows), routines (TASK-680), credentials, the Filestore directory, and the orchestrator's warm sandboxes.
- **NOT cleaned (follow-up cards):** the agent's git workspace repository (no delete hook; `deleteRepo` exists on the git-server client and nothing calls it), blob bytes behind attachments and authored skills (content-addressed and shared; deleting by sha256 needs a reference authority), `routines_v1_fires` history (kept on purpose by TASK-680), `attachments_v1_temps` (TTL janitor), kv leftovers (memory observer cursors, declined-grant markers).
- **Reclaim pod facts:** it uses `config.image` (the runner image), mounts the WHOLE export read-write at `/export`, `activeDeadlineSeconds` 120, label `app.kubernetes.io/component: ax-next-userfiles` (the runner orphan-sweep never selects it). The namespace enforces PodSecurity `baseline`, which allows root and both capabilities used. The delete HTTP request waits for the reclaim pod (~9 s measured on prod).
- **A warm runner outlives its agent's delete.** With `keepAlive: true` the sandbox idles 5 min (+10 s grace). `agents:resolve` is only checked at `agent:invoke` start, so an in-flight turn finishes on its frozen config. The conversations append hooks now refuse a missing conversation (events quietly, transcripts with `not-found`) so a turn that finishes after the purge cannot resurrect orphan rows. The check-then-insert is not atomic: a purge committing in the gap can still leave one unreadable row.
