# Discover OAuth hosts while editing an MCP connector

- The user stopped the requested deployment before any build, registry push, or production mutation. They then requested automatic OAuth host discovery with a visible host list in the connector editor. Deployment remains stopped; production was still on `62155b88` during read-only preparation.
- HTTP MCP connector authoring now debounces a valid HTTPS URL and calls authenticated `POST /api/connectors/oauth/discover-hosts` with only `{url}`. The MCP OAuth plugin registers the route in the running host; no new service-hook or IPC signatures were introduced. The shared discovery algorithm handles resource challenges, path/root PRM and OAuth/OIDC metadata identically in preview and actual OAuth.
- The dialog shows discovered hosts before saving. Save merges only the current URL's completed preview with manual hosts, deduplicates, and persists through the existing owner/admin connector routes. Loading prevents an incomplete save. URL changes, transport/mechanism changes and dialog closure cancel/ignore stale previews. Failure offers retry and manual entry; the preview never stores a connector, registers an OAuth client, accesses the vault or writes pending authorization state.
- Host discovery includes the resource, challenge/metadata/redirect hosts, issuer, authorization endpoint, token endpoint and optional registration endpoint. Unused JWKS hosts are excluded. The new code was exercised against live public Gmail metadata without credentials and returned exactly `accounts.google.com`, `gmailmcp.googleapis.com`, `oauth2.googleapis.com`. A dedicated Gmail client and user consent are still separate configuration steps.
- Draft discovery is a deliberately separate capability from OAuth: authenticated, credential-free GET only to public HTTPS on port 443, no URL userinfo/fragments, public unicast addresses only. It pins the checked address through Node HTTPS's lookup callback while retaining the original URL hostname for TLS and explicitly enabling certificate verification. It revalidates every redirect, cancels resource/SSE probes after headers, and bounds response bodies to 64 KiB, the whole operation to 15 seconds, redirects to five, requests to sixteen and hosts to twelve. Route rate limits are six attempts per user per minute and four concurrent previews, with a bounded/expiring 512-user accounting map. Actual OAuth still requires the explicitly saved connector allowlist at every network hop.
- Verification: root build, all MCP OAuth tests including real plugin route wiring and Docker-backed authorization/refresh integration, all channel-web tests, root ESLint-rule and script suites, changed-file lint, and focused final guard/UI regression runs. Browser checks at 1200px and 390px confirmed visible host lists, saved unions with manual hosts, retry/manual fallback and no dialog overflow. Mechanical UI detector returned no findings. No production OAuth consent or Gmail tool call was performed.

## Security review

- Sandbox: Preview adds bounded public metadata reach for authenticated connector authors before a connector exists. Private, loopback, link-local, reserved and IPv4-in-IPv6 destinations are rejected; validated DNS results are pinned at connection time, TLS verification stays enabled, and each redirect is checked. No filesystem, process, environment or handle capability was added. Preview results do not authorize runtime traffic until the owner saves.
- Injection: Draft URLs, challenges, metadata endpoints and response bodies are untrusted. The shared SDK parsers and resource/issuer checks validate discovery; endpoints are validated before being displayed. The transport sends no secrets/cookies/auth headers, never fetches token or registration endpoints, caps bodies/time/requests, and logs only neutral error names. Hostnames render as React text; stale results cannot enter the saved allowlist. Existing server-side connector validation and OAuth host guards still apply after save.
- Supply chain: N/A: no manifest, lockfile, dependency or install-script changes; the transport uses Node built-ins and the already-pinned `ipaddr.js` dependency.
