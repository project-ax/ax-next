# TASK-505 — facts about the dispatch path and the kind cluster

**Runner pods live in `ax-next-runners`, not `ax-next`.** The host pod, git
server, minio and postgres are in `ax-next`; every `ax-sandbox-*` pod is in
`ax-next-runners`, which the chart does NOT create (`deploy/README.md` step 4)
and which the host's Role is scoped to. `kubectl get pods -n ax-next` will never
show a runner.

**Driving a turn headlessly needs the public-http port, not the IPC port.**
`svc/ax-next-host` exposes `80 → ipc` and `9090 → public-http`. Port-forwarding
80 and calling `/api/chat/agents` answers
`{"error":{"code":"SESSION_INVALID","message":"missing authorization"}}` — that
is `packages/ipc-core/src/auth.ts` refusing a missing `Authorization: Bearer`
header, **not** a bad cookie. Forward `19090:9090` instead and the signed
`ax_auth_session` cookie works. (This cost a round of debugging the cookie,
which was fine.)

**`HookBus.fire()` has no timeout, by design.** `packages/core/src/hook-bus.ts`:
`call()` races the handler against `defaultServiceTimeoutMs` (120 s), but `fire()`
awaits each subscriber unbounded and logs only if one *throws*. So a subscriber
that never resolves burns the enclosing service call's entire budget in silence.
Every hook upstream of sandbox provisioning in `runAgentInvoke` — `chat:start`,
`agents:resolve`, `persistUserDisplayTurn`, `conversations:get`,
`session:is-alive` — sat in that blind spot. TASK-505 added a stall watch to both
`call()` and `fire()` (`hook_{call,subscriber}_{stalled,slow}`), so this is now
observable rather than folkloric.

**`creating_pod` is logged immediately BEFORE `createNamespacedPod`**
(`packages/sandbox-k8s/src/open-session.ts`). That makes it a useful boundary
marker: a hang with `creating_pod` in the log is at or past the k8s API; a hang
with no `creating_pod` is upstream of provisioning entirely.

**`hydrateAgentTier` is O(N) network round-trips on the chat:start path.**
`packages/memory-strata/src/agent-tier-sync.ts` issues one `workspace:list` plus
one `workspace:read` **per memory file**, serially. On the git-server backend
every `read` runs a full `git fetch` against the server
(`packages/workspace-git-server/src/client/git-engine.ts`), and the engine's
`enqueue(workspaceId, …)` serialises them. It runs synchronously inside
`chat:start`, before any sandbox exists — and `bootstrapMemoryTree` only ever
*creates* four files with `O_EXCL`, so after the first turn the whole hydrate
writes nothing. Not shipped as a fix (the hang did not reproduce, so attributing
it would have been a guess) but it is a real per-turn cost on the blocking path.

**Cluster/host facts, 2026-09-20.** macOS data volume 99 % (13 GiB free) —
read `/System/Volumes/Data`, not `/`. The kind node's own filesystem is separate
and was at 44 % (13 G free), so "disk is full" on the mac is not the same claim as
"the cluster is out of disk". Two turns completed end to end in ~4 s each under
that load, with runner pods ready in 2.4 s.
