# Shared GKE pool feasibility

- User explicitly requires shared pools and rejects a pool per agent. Supersedes the WARMPOOL-20261001 proposal; docs/plans/2026-10-01-agent-sandbox-shared-pool-design.md is the current proposed design.
- Upstream examples/latebind-storage-gke-sandbox documents shared Regional Filestore directory bind mounts into an already running gVisor Pod. GKE force-shared emptyDir annotation plus HostToContainer propagation requires 1.36.0-gke.3302001 or newer; our gvisor node is 1.36.4-gke.1247000. New Filestore agent-volume product access conditions do not apply merely because we adapt the shared existing NFS-directory approach.
- Actual synthetic probe used one template and shared warm pool with two Pods. Two synthetic agents adopted original Pod UIDs in 759 and 644 ms, zero runner restarts. Scoped root helpers bound only their fixture emptyDirs; kernel bind calls took 10 and 12 ms. Non-root gVisor runners saw only assigned directories, wrote through to backing directories, and could not see the helper source, sibling directory, or escaping symlink. Temporary mode0600 configuration files reached the waiting runners and were consumed and removed before fixture work. No real tokens, Filestore data, or model calls were involved; these are not first-response or durable-NFS benchmarks.
- Initial normal umount failed EBUSY while the gVisor Pods were alive. Recovery synced and lazily detached the owned fixture mounts, then removed assigned Pods and helpers. Corrected complete probe repeated attachment/bootstrap/isolation checks and this teardown successfully; temporary namespace ax-shared-pool-probe-1790890093111 was confirmed absent. Lazy detach does not prove durable flushing, and API finalizers do not by themselves prove kubelet delays termination or volume cleanup.
- Proposed production flow uses a privileged trusted node helper with authenticated controller-only APIs to attach the authorized agent subtree and deliver a local private bootstrap file. This replaces the earlier separate runner listener plus application-encryption proposal. Requires a full boundary review of node reach, UID-pinned authorization, symlink/mount races, cleanup, NFS durability, and source quota enforcement. Runners remain unprivileged; the full export never enters them.
