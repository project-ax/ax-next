# MCP connector OAuth discovery and Gmail setup

- Production Gmail connector (`gmail`, read-only inspection of the pinned production context on 2026-10-01) had no credential slots and allowed only `gmailmcp.googleapis.com`. Connect cannot start without an OAuth slot and Google's separate authorization/token hosts. No production configuration or deployment was changed during this task.
- The user chose a **dedicated Gmail OAuth client**, superseding an earlier choice to reuse the Google sign-in client. Do not copy sign-in credentials for this task. Google does not advertise dynamic client registration; enter the dedicated client ID/secret through connector settings (the secret goes to the existing vault path).
- Gmail endpoint: `https://gmailmcp.googleapis.com/mcp/v1`. Its unauthenticated GET returns 405; protected-resource metadata is at `/.well-known/oauth-protected-resource/mcp/v1`. PRM advertises `https://accounts.google.com/`, while Google's OIDC metadata issuer is `https://accounts.google.com`. Discovery accepts URL-equivalent root forms, then binds callback `iss` to the metadata's exact issuer identifier.
- Configure an HTTP MCP OAuth slot targeting server `gmail`, with explicit scopes `https://www.googleapis.com/auth/gmail.readonly` and `https://www.googleapis.com/auth/gmail.compose`. Allow hosts `gmailmcp.googleapis.com`, `accounts.google.com`, `oauth2.googleapis.com`. The connector editor now exposes extra allowed hosts for HTTP MCP and shows its callback URI. For production the dedicated Google web client needs authorized redirect URI `https://canopyworks.ai/api/connectors/oauth/callback`.
- Google setup also requires Gmail API and Gmail MCP API enabled in the client project and access to the Workspace developer preview where applicable: https://developers.google.com/workspace/gmail/api/guides/configure-mcp-server . Live user consent and a production Gmail tool call were not tested; client configuration and deployment remain necessary.
- Discovery now probes an unauthenticated resource challenge through the existing HTTPS/allowlist/public-address/per-hop redirect guard, cancels the body (including open SSE streams), and follows challenge metadata URLs before well-known fallback. Explicit connector scopes win; otherwise advertised scopes are used consistently for registration, consent, and pending storage.
- Google consent requests use `access_type=offline` and `prompt=consent` so reconnecting can obtain a refresh token. Callback errors are user-bound, single-use, and return the trusted connector ID to the popup. A supplied response issuer must match; metadata advertising RFC 9207 requires an issuer parameter. The additive `issuer_required` migration defaults legacy pending rows to false.
- Validation: full monorepo build; all 230 MCP OAuth tests including Docker-backed real plugin/token refresh paths; all 3847 channel-web tests; root ESLint rule and script suites; changed-file lint; desktop (1200px) and mobile (390px) browser inspection, with no dialog horizontal overflow. The recursive monorepo test suite was not run. Regression tests include Gmail's real discovery shapes, Google pinned-client code redemption/refresh, challenge-only servers, scope precedence, SSRF rejection, issuer binding, denial cleanup, migration compatibility, and editing HTTP MCP OAuth hosts.

## Security review

- Sandbox: The added resource probe and metadata URLs remain HTTPS-only, limited to connector-declared hosts, public-address resolution, and guarded redirects. No new filesystem paths, process spawning, environment access, or opaque handles cross boundaries. UI host entry makes the existing network capability explicit; it does not auto-allow Google's hosts.
- Injection: Untrusted resource challenges and metadata are SDK-parsed and URL-gated; resource/issuer identifiers are checked before grant use. Callback state is session-user-bound and atomically consumed, including denial; issuer failures precede consumption/token exchange. Query/provider text is never reflected into HTML, shell commands, SQL, or prompts. Secrets stay on the existing vault/token paths and are not added to browser URLs or logs.
- Supply chain: N/A: no package manifests, dependency versions, or lockfiles changed.
