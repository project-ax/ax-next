# TASK-708 — a message folded into a running claude-sdk turn strands its reqId

| Date | Decision | Rationale | Alternatives |
|---|---|---|---|
| 2026-10-03 | Fix in the RUNNER, which observes the fold, and carry it on the existing turn-end as `foldedReqIds?: string[]`; `@ax/agent-activity` drains those ids too. | The plugin cannot tell a fold from real concurrency (the card's own premise). The runner can, but only with the CLI's help — see next row. | A synthetic `event.turn-end` per folded id (the card's "preferred"): every turn-end subscriber (conversations persist, usage-limits meter — an absent `usage` is charged a flat cost, memory, titles, routines, the SSE closer) would act on a turn that never happened. |
| 2026-10-03 | Fold detection = `extraArgs: { 'replay-user-messages': null }` + a shell-minted `uuid` on each SDKUserMessage. The CLI echoes the uuid (`isReplay: true`) when it consumes the message; a fold echoes BEFORE the running turn's `result`, a message that gets its own turn echoes AFTER. Without the flag a fold is silent. | MEASURED against the pinned CLI (0.2.119, darwin-arm64) with a scripted mock Anthropic API, and pinned by `agent-claude-sdk-runner/src/__tests__/fold-replay-real-sdk.e2e.test.ts` so a CLI bump that changes it reddens. | A grace timer after the hand-over ("no chunk within N s means folded"): guesses on model latency. |
| 2026-10-03 | REFUTED the card's alternative ("key by session; on a turn-end drain ids started EARLIER in the session"). | In a fold the turn-end names the EARLIER id (A; TASK-573 keeps the turn's own id) and the stranded one (B) started LATER, so draining earlier ids drains nothing. Draining the whole session instead would read resting through a queued message's own turn. | — |
| 2026-10-03 | Shell rule: every consumed message's reqId is recorded for the turn now running; at that turn's turn-ends everything except the turn's own `reqId` is listed (BOTH turn-ends), and the set clears at the hand-over. Bounded map (64) of shell id to reqId. Filtering at EMISSION, not at consumption, is deliberate (mutation-found): a message pulled after the hand-over but before the next turn's first chunk adopts at once and renames that turn, so a message consumed while its own id was current can still end up answered under another id. | A message that gets its own turn is consumed after the hand-over made its id current, so it is never listed; the CLI's multi-message batch (B and C queued, run as one turn under C) lists B on C's turn. Both turn-ends, like `reqId`, so first-turn-end subscribers see it. | Clearing `parkedAdoption` when the parked id is folded: a behaviour change to the TASK-573 hand-over with no symptom asking for it. |
| 2026-10-03 | Implemented inline rather than one subagent per plan task. | Four small, tightly coupled edits (schema, shell, loop, plugin) whose correctness is one argument; splitting would have cost more context than it saved. | — |
| 2026-10-03 | Left the orchestrator alone: a folded message's `agent:invoke` waiter and any SSE stream opened on its reqId still wait for `chat:end`. | Out of this card's scope (agent-activity's Working). `foldedReqIds` is the signal those need; returned as a follow-up. | Resolve the waiter / close the stream here: scope creep onto TASK-577/578-shaped symptoms. |
