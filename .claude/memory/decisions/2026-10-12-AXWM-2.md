# AXWM-2 — W1 implementation: prompt contributions from several plugins

Spec: `docs/plans/2026-10-12-w1-prompt-contributions-design.md`. Plan:
`docs/plans/2026-10-12-w1-prompt-contributions-plan.md`. Standalone `/yolo-ship` run;
no board card existed for W1, so this shard uses the AX Work Model series id (AXWM-1
was the umbrella design).

| Date | Decision | Rationale | Alternatives |
| --- | --- | --- | --- |
| 2026-10-12 | `SystemPromptAugmentOutputSchema` is strict but carries **no length limit**; the 32,000-char cap is a separate exported constant (`SYSTEM_PROMPT_AUGMENT_MAX_BODY_CHARS`) that the orchestrator checks after the schema passes. | The spec logs oversized bodies as `reason: 'too_large'`, distinct from `'invalid'`; a `.max()` in the schema would fold both into one zod failure. | `.max(32000)` in the schema and parse the zod issue code to recover the reason — brittle. |
| 2026-10-12 | Within a section, bodies are ordered by the **full service name** (string compare), so `…:optional:x` sorts before `…:required:y` when both write `context`/`recall`. | Spec §3.2 says "by service name"; full-name order is deterministic and registration-order independent, which is what keeps the prompt cache warm. Only memory is required today, and it writes no `context`. | Required-before-optional within a section; ordering by the `<name>` suffix only (two classes could share a suffix and tie). |
| 2026-10-12 | When several required providers fail, each logs `system_prompt_contribution_failed`, and `system_prompt_augment_suppressed` is logged once per failed required provider. | The spec's suppressed event carries one `provider`; one line per culprit keeps every cause visible without inventing a list field. | One line with a `providers` array — a shape the spec does not name. |
| 2026-10-12 | Unknown class segment (`system-prompt:augment:<other>:x`) is ignored and logged once per orchestrator instance (`system_prompt_augment_unknown_class`). The old bare `system-prompt:augment` name is not matched by either prefix, so a stale provider registered under it is simply not called. | Spec §3.1. A stale bare provider would be a configuration bug; nothing in-repo registers it after this change. | Throw at boot — the orchestrator cannot see registrations at init time (they can land later). |
| 2026-10-12 | The 32k body cap cannot trip memory: Rules writes are capped at `MAX_RULES_CHARS` = 16,384 (`memory/src/rules.ts:33`) and the recall half is capped at 800 tokens. | Checked so a required-provider `too_large` can't suddenly suppress every agent's prompt. | — |
| 2026-10-12 | `augmentDeadlineMs` validated at plugin init by its own check (finite and > 0), not the shared `validSubscriberBound` (which admits `Infinity` and `0`). | Spec §3.4 / review 1 finding 3: the whole point is a finite deadline. | Reuse `validSubscriberBound` — would accept `Infinity`. |
