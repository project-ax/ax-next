# TASK-812 connector details view stale after sign-in

| Date | Decision | Rationale | Alternatives |
|------|----------|-----------|--------------|
| 2026-10-04 | ROOT CAUSE (two halves). (1) channel-web `ConnectorDetails` took its tool read once, at mount; a sign-in re-reads the LIST (`refresh()` in AgentConnectors) so `row.health` flips `needs-sign-in`→`ok`, and `ConnectionLine` then renders the stale read's `needs-auth` as red "Sign-in needed". Fix: when `row.health` changes, `reload(true)` (forced). (2) mcp-client `connectors:describe-tools`: a forced read inside the 30s TASK-756 cooldown is answered from the cached row — and opening the details view of a never-signed-in connector is itself a check that started the window while asking NO server (pass 1 stopped at the missing credential). So a sign-in finished <30s later still read `needs-auth`. Fix: a check where no server reached pass 2 releases the window, mirroring the existing credential-blip rule | The brief's INFERRED "rail and details derive sign-in from different queries" is CONFIRMED: rail health = `credentials:has` (live), details word = cached inventory status. Kept the list as the trigger (invariant 4: the list's word is the truth; details only refreshes its own read when that word moves). Rate-limit preserved: the window still holds after any check that listed even one server (pinned by a multi-server test) | Pass a `version` prop bumped on each onConnected (more plumbing, misses Retry/Reconnect-driven health changes); make the header ignore `needs-auth` when health is ok (hides a real 401-without-marker case); a new credential-changed hook from mcp-oauth to invalidate the inventory row (new hook surface + boundary review for a 30s window) |
| 2026-10-04 | Re-read is NON-quiet (skeleton, header blank until it lands), not a quiet swap | A quiet reload would keep painting the stale "Sign-in needed" for the length of a real MCP listing (seconds) — the exact bug, briefly. Same shape as the existing Try again | Quiet reload |
