# Decisions — TASK-612 (mid-session Rules + observer self-reports)

| Date | Decision | Rationale | Alternatives |
|---|---|---|---|
| 2026-09-27 | **Refresh, not a UI caveat:** a changed Rules file retires every live session of that agent at its NEXT turn boundary (terminate + fresh spawn, which re-runs `system-prompt:augment`). | The Memory tab already promises "{agent} reads them before every run" (AgentMemory.tsx) — the refresh makes the existing promise true; a caveat would make the UI walk it back. The retire-at-next-routing mechanism already exists and is proven (`respawnSessions`, TASK-74 skills; capability grants). Rules are person-authored and rare, so one cold start after an edit is cheap. | (a) UI note "applies from your next conversation" — also false: a warm sandbox for the SAME conversation keeps the old prompt until reaped. (b) Re-send the prompt per turn over IPC — runner computes the prompt once per spawn; wire change for no gain over respawn. |
| 2026-09-27 | Signal is a new generic subscriber hook `system-prompt:augment-changed` `{ agentId }`, fired by the Rules providers (@ax/memory, @ax/memory-strata) only when a write actually changed the file. | Orchestrator stays ignorant of memory paths (I1/I2); any future augment provider (tenant policy) can fire it. Orchestrator subscribing to `workspace:applied` + a rules path would couple it to storage layout. | Fire from channel-web's saveRules route (one place, but it is not the augment's owner and misses non-HTTP writers). |
| 2026-09-27 | Staleness is a per-agent generation counter compared to the generation snapshotted before the session's augment was built; a session this process did not spawn counts as stale once the agent has any change. | A counter has no clock skew; snapshotting BEFORE the augment call closes the race of a Rule saved mid-spawn. The unknown-session rule is conservative (worst case one extra respawn). In-memory + single-replica, same posture as `respawnSessions`. | Per-session marks at event time (needs a session→agent map the orchestrator does not keep). |
| 2026-09-27 | **Observer drops the agent's self-reports about its own rules/instructions/memory** with a deterministic post-extraction filter, not a prompt change. | `extraction-prompt.ts` is fingerprint-pinned and may not be reworded (measured ~57-pt extractor effect). The runtime context is not a durable fact: Rules have one source of truth (the Rules file) and memory has the store (I4), so a transcript snapshot of either is stale on arrival. | Reword the extraction prompt (forbidden); filter at recall time (the bad row would still be stored and shown in the Facts list). |
| 2026-09-27 | Review round 1 (reviewed 0cd0f04a): fixed first-person negation misses ("I haven't been given any rules"), topic over-drops ("system prompt" as a topic, "rules of thumb"), dropped `ai`/`bot` subjects, added an `only-self-reports` counted skip, moved the per-session generation record to after sandbox open plus a one-shot cleanup, and hardened the malformed-event test against coercion. | All verified against the built classifier or the code path the reviewer named. | — |
| 2026-09-27 | **Deferred, not fixed here:** multi-replica hosts would miss a Rules save handled by another replica, silently bringing back the TASK-607 bug. Returned as a follow-up. | Same documented single-replica posture as `warmSessions`/`respawnSessions`; the k8s chart runs one host today. Fixing it needs a cross-replica event bus path, which is a separate design. | Route the event over eventbus-postgres now (out of scope). |
| 2026-09-27 | No unit test for the one-shot `augmentGenBySession` cleanup. | The maps are closure-private and the leak is only reachable on a long-lived `keepAlive: false` host, which no preset runs. Exposing internals just to count map entries would add surface for a latent case. | Export a test-only size getter. |
| 2026-09-27 | Rounds 3 and 4 (reviewed 91642f77 and 5ea06e96): bounded `(system \|bootstrap ){1,2}` (unbounded `+` measured O(n^2), ~2.6 s at 40k repeats on untrusted text) plus a 1,000-char scan cap; added `provided`/`offered` to the negation verbs; "rules in/against/around/to <topic>" and "memory foam/card/…" are now kept as content. | Each one measured against the built classifier by a reviewer. | — |
| 2026-09-27 | Kept, not fixed: a `knows_rules`/`has_rules` predicate flags regardless of object (reviewer nit). A reviewer also claimed the branch was named for TASK-608; `git branch --show-current` says `auto-ship/TASK-612-midsession-rules`, so that was rejected as a misread. | The extractor is steered toward `stated`/`recommended`-style predicates, so a `has_rules` predicate with a topic object is unlikely. Dropping one hypothetical topic fact beats keeping a real self-report. | Require the object to not be a topic. |
| 2026-09-27 | Filter is scoped to assistant-speaker subjects and phrase patterns that tie rules/instructions/memory to the agent's own context (e.g. "no rules", "rules from the user", "system prompt", "don't remember"), not any fact mentioning "rules". | "assistant listed the rules of chess" is a legitimate assistant fact and must survive. | Drop every assistant fact mentioning rules/memory (too broad). |
