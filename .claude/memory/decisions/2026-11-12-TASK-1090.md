# Decisions — TASK-1090 (Slack channel spike) + the channel memory rule

Design: `docs/plans/2026-11-09-channel-slack-design.md` (§2a, §7). Cards TASK-1090–1099.

| Date | Decision | Rationale | Alternatives |
|------|----------|-----------|--------------|
| 2026-11-12 | **Memory in Slack follows WHO SEES THE REPLY: a new `ctx.audience: 'private' \| 'shared'`, separate from `ctx.source`.** A shared turn (channel, group DM) recalls only statements captured in shared turns (plus instructions/files), stamps what it captures `shared`, and captures NO facts about the speaker. Private → shared never flows; shared → private does. (Vinay.) | Team-agent memory is shared across the team (`memory/src/access.ts`), so a private web-chat fact would otherwise be recalled into a public channel, even for a trusted asker. And `memory/src/subject.ts` records the speaker as `user:<ctx.userId>`, which in an external turn is the channel connector: a passer-by's "I live in Paris" would be pinned on them permanently. | No memory in channels (safest; kept as the fallback). Full memory (leaks). Decide by asker's AX access (same leak: the audience is the channel). |
| 2026-11-12 | **External turns on a team agent run as the person who CONNECTED the channel**, not "the owner". | A team has no user id, and memory refuses made-up owners (`memory/src/owner.ts`); routines already run as their owner (`routines/src/fire.ts:267`). | A synthetic/system user (forbidden: memory, `agents:resolve`). |
| 2026-11-12 | **No Socket Mode; HTTP events.** `apps.manifest.create`/`update` sent NO `url_verification` challenge, and a DM reached the installed bot as a signed `event_callback` with no Verify click, despite the manifest docs saying the Request URL needs manual verification. | Tested in the real Canopy workspace. Socket Mode would need an app-level token that only Slack's UI can create. | Socket Mode (manual token per app). |
| 2026-11-12 | **The only unavoidable human step per app is Slack's OAuth "Allow", by someone with install rights.** Phase 2's "Approve" button creates the app and opens that screen directly, so Allow IS the approval. An admin's install of a manifest-created app showed only the normal Allow screen. | Slack requires install consent; no API skips it. `admin.apps.approve` is Enterprise-only. A member's install path was NOT tested (no member install exists in the design). | A separate AX-side approve step before Allow (dropped: two clicks for one decision). |
| 2026-11-12 | **AX enforces bot-name rules and uniqueness itself.** Allowed: ASCII letters, digits, space, `-`, `_`, `.`. Slack rejects reserved words (`here`, `channel`, `everyone`, `slackbot`), non-ASCII (`Café` → `bad_username`), other symbols. The handle drops hyphens (`ax-spike-a` → `axspikea`). Duplicate names are ALLOWED: the second bot became `axspikea2`, and the tester DMed the wrong bot. | Measured with `apps.manifest.validate` and two installs. | Rely on Slack (it accepts duplicates silently). |
| 2026-11-12 | **A rename uses `apps.manifest.update`: no reinstall** (`permissions_updated: false`), and the bot token keeps working. `real_name` changes; the @handle stays as it was at install. Avatar via `apps.icon.set` with the configuration token works. | Tested. | — |
| 2026-11-12 | **Streaming uses `chat.startStream`/`appendStream`/`stopStream`** (works in channel threads with `recipient_user_id` + `recipient_team_id`), falling back to throttled `chat.update` past the 10-minute stream cap. | Docs; 10 min equals our default chat timeout. | `chat.update` only (Tier 3, ~50/min). |
| 2026-11-12 | **Store only the configuration REFRESH token; Disconnect tells the admin to Revoke on Slack's page.** Access tokens expire after 12 h. `tooling.tokens.rotate` does NOT invalidate the old refresh token or earlier access tokens, and `auth.revoke` kills an access token but its refresh token STILL mints new ones. | Tested. The API cannot retire a leaked refresh token; only the api.slack.com/apps configuration-tokens page can. | Rely on rotate/revoke (they don't retire it). |
