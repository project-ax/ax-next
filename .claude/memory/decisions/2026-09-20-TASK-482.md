# TASK-482 — reclaiming decline markers

| Date | Decision | Rationale | Alternatives |
|---|---|---|---|
| 2026-09-20 | Shape **(a)** — reclaim inside the existing KV shape. No `@ax/grant-declines` plugin, no table. | Nobody has asked to list or revoke declines from Settings, which is the only thing (b) buys. YAGNI, and the card says to default to (a) absent a named requirement. | (b) a first-class plugin + table (TASK-444 deferred it; still deferred). |
| 2026-09-20 | **A marker is reclaimable iff it does not currently suppress a pending card.** Not "its agent no longer exists" — no existence lookup at all. | `raisedAt` is stamped from the host clock every time a card is appended *or replaced*, and the pending-card buffer is in-memory in a single-replica process. So any future raise of the same `(user, agent, kind, subject)` carries a `raisedAt` strictly newer than a stored `declinedAt` and the marker can never win again. "Not suppressing now" therefore means "dead", exactly — not heuristically. | Reclaim by agent/skill existence probe (an N+1 across `agents:*` per read, and still wrong: a marker for a live agent whose card was re-raised is equally dead). |
| 2026-09-20 | Reclaim runs **only on `GET /api/workspace/grants`**, never on the SSE replay. | SSE sees one conversation (`tailPermissionCardEntries`); every *other* conversation's live markers would look unreferenced and be deleted. The grants route reads `pendingGrantsForUser`, which is user-wide across conversations and is the only authoritative set. | Reclaim in `filterDeclinedGrants` (shared by both paths) — would have deleted live markers from the SSE path. |
| 2026-09-20 | **The `rows.length === 0` short-circuit stays**, so reclaim never buys a scan of its own. | TASK-444 regressed exactly this guard and the card requires it to survive. Reclaim piggybacks on a scan that was already going to happen, so it is free: zero added reads on every path. Cost: a user with no pending grants never prunes — but they never scan either, so the cost they pay is zero. | Scanning on every grants read to prune — reintroduces the per-turn scan TASK-444 removed. |
| 2026-09-20 | Add a new **`storage:delete`** service hook (exact key) to `@ax/storage-sqlite` + `@ax/storage-postgres` rather than reusing `storage:delete-prefix`. | `delete-prefix` on an exact key is unsafe for variable-length ids (`…:abc` is a prefix of `…:abcd`) — documented beside `recordGrantDecline` and now pinned by a test. There is no safe way to express "delete exactly this key" with the existing four hooks. Generic infra belongs in the storage plugins, not hand-rolled inside the feature. | (i) terminate every key with `:` so a prefix delete is exact — needs a key-format migration and leaves TASK-444-era markers unreclaimable; (ii) `delete-prefix` the whole user prefix and re-`set` the survivors — non-atomic, and a concurrent decline written mid-reclaim is silently destroyed. |
| 2026-09-20 | Reclaim is **capped per read** (`RECLAIM_MAX_PER_READ = 64`) and awaited. | Bounded latency on the mount read even against a store that grew before this shipped; converges over a few reads. Awaiting keeps it deterministic and testable (a fire-and-forget delete is untestable and risks an unhandled rejection). | Unbounded `Promise.all` (pool exhaustion + an unbounded mount stall on the first prune). |
| 2026-09-20 | Reclaim is **opt-in per call site** via `reclaimAgainstCompleteSet`, and the route passes it only when `buffer !== undefined`. | `WorkspaceHandlerDeps.buffer` is optional; without a buffer the route reads `[]`, which is indistinguishable from "nothing pending" and would reclaim every marker the user owns. Fail closed. | Always reclaim inside `withoutDeclinedGrants` — wrong whenever the caller's row set is not authoritative. |
| 2026-09-20 | The `NOTHING DELETES THESE` paragraph on `recordGrantDecline` is rewritten in this PR, not left behind. | Contract rule 5: the doc comment is what would generate this card again. The prefix-delete trap it documents stays — it is now enforced by a test instead of only by prose. | Leave the comment; a later session re-files the card off it. |
| 2026-09-20 | Resumed after the first builder was reaped mid-mutation-testing. Kept both preserved commits unchanged; re-derived every claim. | The two open items were both settled by running them: **M6** (wire `reclaimGrantDeclines` into the SSE replay at step 3a) **is killed** by `sse.test.ts`'s never-prunes guard — the guard registers `storage:delete` on its bus on purpose, so the assertion is not vacuous. **M7** (drop the `!bus.hasService('storage:delete')` guard in `reclaimGrantDeclines`) **survived**: the outer try/catch swallows the resulting throw, so the read still answers correctly and no test noticed. | Discarding the preserved work and restarting — nothing in it failed re-derivation. |
| 2026-09-20 | The degradation test now asserts the reclaim logged **no** `workspace_grant_declines_reclaim_failed` warning. | That is the only observable difference the `hasService` guard makes: without it a store lacking `storage:delete` logs one warning per grants read forever. Correct answers, infinite noise — the exact shape a `catch` hides. Killed M7. | Leave M7 alive (a surviving mutant on a guard the manifest advertises as a supported degradation). |
