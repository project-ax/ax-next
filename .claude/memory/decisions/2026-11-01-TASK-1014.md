## 2026-11-01 — TASK-1014 streaming download of /files files (planner)

| Date | Decision | Rationale | Alternatives |
|---|---|---|---|
| 2026-11-01 | New host-internal service hook `sandbox:read-user-file-range {owner, relPath, offset, length} → {kind:'file', size, version, bytes} \| {kind:'dir'} \| {kind:'absent'} \| {kind:'unavailable'}`. The caller loops over 1 MiB chunks. Both providers answer with one new `@ax/user-files-read` function, `readConfinedUserFileRange`, which re-walks the path (O_NOFOLLOW per component) on every call. | The bus stays request/response with plain data. Nothing outlives a call, so a client abort or a stalled client holds no file handle and there is no leak class to test around. The per-call bus timeout and the `PluginError` wrapping apply to every chunk. Each fresh open revalidates NFS attributes (close-to-open). It maps 1:1 onto an object store's ranged GET, which is a concrete alternate impl. | A service hook returning an AsyncIterable or handle (rejected: it would be the first live resource across the bus, it leaks if the caller never iterates, it is held outside any bus timeout, and it cannot cross a process boundary). Adding offset/length to `sandbox:read-user-files` (rejected: that mixes prefix-and-listing semantics with range semantics, and the pod realization cannot do ranges). Raising the 1 MiB cap (rejected by the card). |
| 2026-11-01 | Consistency check: `version` is an opaque branded token built from `dev:ino:size:mtimeNs:ctimeNs`. It comes from a fresh fstat taken BEFORE each read. Every chunk, plus one final `{offset: size, length: 0}` validation call, must return the same version and size, and each chunk must be full length. Any mismatch, or an `absent`, aborts the body. | This catches rename-replace (ino), truncation and append (size), in-place rewrites (mtime/ctime) and deletion (absent) right up to the last byte. The final validation covers a change during the last read, which no later chunk would see. | One held fd with an nlink/mtime check at the end (NFS attribute cache; deletion by another client shows up only as ESTALE). A content checksum (costs a second full read). Per-chunk checks with no final validation (a torn last chunk would be served as complete). |
| 2026-11-01 | `@ax/http-server` gains `HttpResponse.bodyStream(source: AsyncIterable<Uint8Array>, {contentLength}): Promise<void>`. It has no contentType option (YAGNI): `header()` sets the type, and the default is octet-stream. It applies backpressure and enforces the exact length. On a source error, a short or long source, or a client abort, it calls `res.destroy()` (never `end()`). On client abort it also calls `source.return()`. The chunk that completes the body is written only after the source reports done. Headers are not flushed before the first byte. | `stream()` (SSE) ignores `res.write()`'s return value, so a slow client makes the whole file buffer in userland. Its error path calls `res.end()`, which turns a truncated chunked body into a complete-looking 200. Holding the final chunk lets the route's final validation run before the client can see Content-Length satisfied. | Add drain/abort to `StreamingResponse` (rejected: every caller would re-implement the pump). Raw socket access from channel-web (rejected: invariant 2, and channel-web only has the duck-typed adapter). |
| 2026-11-01 | Download ceiling: `USER_FILE_DOWNLOAD_MAX_BYTES = 1 GiB`, a constant in channel-web `server/user-file-download.ts`. It is checked against the first chunk's `size`, and a bigger file gets 413 `file-too-large` before any body. Chunk size `USER_FILE_DOWNLOAD_CHUNK_BYTES = 1 MiB`. | It bounds both bytes and wall time per download. The Files tab still buffers the whole file in a Blob, so the 10 GiB agent-files quota is too large a bound for that client. 1 GiB is far above the 50 MiB acceptance and above the 100 MiB artifact-chip cap, and TASK-1012 imports the same constant. A 1 MiB chunk is the same per-request memory as today's capped read. | The agent-files quota (it is a per-owner storage budget, it needs a disk-quota call, and it is too large for the Blob client). An env-configurable max (YAGNI). A 100 MiB cap to match artifact chips (too small for /files work product). |
| 2026-11-01 | k8s realizes the range hook ONLY through the read-only host mount (`userFilesHostReadRoot`). Unset, it throws `PluginError{code:'user-files-download-unavailable'}`, creates no pod and is not handed the k8s API. Downloads then answer 503, and previews still go through the one-shot pod. | This is the TASK-993 precedent (`sandbox:user-files-usage` is host-mount-only). Production and kind both set `hostReadPath`. A pod per chunk is absurd, and a ≤1 MiB pod fallback adds code to a path TASK-915 wants to retire, along with its check-then-read gap. | A pod-per-chunk range read. A pod fallback for small files only. |
| 2026-11-01 | Error mapping before headers: a thrown read is answered 503 `file-read-failed` with a warn log of the codes only. That covers any error: `PluginError{code:'unknown'}` wrapping EACCES/EIO, `timeout`, `user-files-download-unavailable`, and the pod path's `userfiles-read-failed`. `unavailable` and a missing range service → 503 `user-files-unavailable`; absent → 404; dir → 400 `not-a-file`; over the ceiling → 413. After headers: destroy, plus an info log `{agentId, reason}`. The client's 503 sentence becomes a transient one. | Today the route does not catch, so EIO is a 500 (the test at routes-workspace-download.test.ts:561 pins that). The card wants 503. The client's 503 copy ("not set up to hand files over") would be false for EIO, and the deployment case it describes cannot be reached from a listed file, because the listing 503s first. | Map only `code:'unknown'` (misses the pod and timeout codes). Parse the error code client-side to keep two 503 sentences (more code for a case nobody can reach). |
| 2026-11-01 | Headers stay as today: `application/octet-stream`, `nosniff`, `attachment` with the sanitized filename. Added: `Cache-Control: private, no-store` and `Content-Length = size`. No HTTP Range/resume. The client keeps fetch+Blob. Its stale "host caps a read at a megabyte" comment and its 413/503 copy are fixed, and streaming to disk is deferred. | The card asks for exactly these headers. The 50 MiB acceptance works with Blob buffering. YAGNI on resume and on client streaming. | `window.open`/navigation download (rejected in file-download.ts for showing JSON to people). File System Access API (Chromium-only). |
| 2026-11-01 | Invariant 3: extend the presets/k8s F4 canary (subprocess + localdir, real route over a socket) with a 50 MiB byte-identical download, a symlink download that 404s, and a mid-stream deletion with a paused reader that must end incomplete. It needs Linux plus Docker (Postgres testcontainer), so CI runs it. | The canary today covers listing and preview but not the download route, and the new hook has to be reachable from it. | Unit tests only (they would not prove the real wiring). |
