| 2026-11-01 | **The idle timeout lives in `@ax/http-server`'s `bodyStream()` pump.** It is armed only while the pump waits on the client, in two places: the `'drain'` wait after a `res.write()` that returned false, and the `'finish'` wait after `end()`. Each wait gets a fresh window. If no `drain`/`finish`/`close` arrives within the window, the pump rejects `client-stalled` and the existing teardown runs (destroy, `source.return()`). The timer callback only rejects. It never touches `res`, so a late fire after the promise has settled does nothing. | Only the pump knows when it is parked on the client. `sendUserFileDownload` is the source, so it runs only when the pump pulls and cannot act while the pump waits on `drain`. The brief named one wait (`drainOrClose`). `endAndAwaitFinish` waits on `'finish'` with no timer either, so a stall while the final chunk flushes hung too. Source waits are already bounded by the bus's 30 s per-call timeout. | `sendUserFileDownload` (cannot see a stall). Node's `server.timeout` socket-idle timer, server-wide (it would also cut quiet SSE streams and slow JSON handlers that write nothing for a while). `res.setTimeout` (persists onto the kept-alive socket's next request). |
| 2026-11-01 | **Default window is 60 s (`BODY_STREAM_IDLE_TIMEOUT_MS`). `CreateHttpServerPluginOptions.bodyStreamIdleTimeoutMs` is the config and the test seam. A value that is not a positive safe integer throws a TypeError from `createHttpServerPlugin`. No env var.** | The plugin's existing timeouts (`HEADERS_TIMEOUT_MS` 30 s, `REQUEST_TIMEOUT_MS` 60 s, `KEEP_ALIVE_TIMEOUT_MS` 5 s) all bound receiving the request. None bounds writing the response, and `server.timeout` is 0. 60 s matches the longest of them. Tests need a window of about 200 ms. | Per-call `SizedBodyOptions.idleTimeoutMs` (the route knows nothing about sockets). An env var (YAGNI). |
| 2026-11-01 | **Accepted residual: progress is measured one write at a time.** Node fires `'drain'` only once a whole write (1 MiB for a /files download) has reached the OS, so at 60 s the window also works as a speed floor of about 17 KiB/s. Splitting writes into 64 KiB slices would bring that floor down to about 1 KiB/s, but is deferred. | No real browser link at MVP is that slow. A deterministic test of "slow but moving" is not possible on loopback, because kernel buffer autotuning absorbs several MiB, so slicing would ship untested. | Slice writes into 64 KiB now. A 120 s default (a lower floor, but a stall holds its chunk twice as long). |
| 2026-11-01 | **`BodyStreamFailureCode` gains `'client-stalled'`. channel-web logs it at info, like `client-gone`.** | The logs say who ended the body (we cut a stalled reader, or the client left). channel-web reads the code duck-typed (invariant 2). | Reuse `client-gone` (the server-cut case would be logged falsely). |
| 2026-11-01 | **`http:response-sent` gains a required `incomplete: boolean`. The `status` stays the status the response was given.** `incomplete` is true exactly when `bodyStream()` cut the connection (any failure, including a client gone before the head). It is false for `stream()` (no promised length) and for the single-shot terminators (Node gets the whole body at once, and they are not tracked after that). | The card said "incomplete or aborted". A new status value would also lie: a torn download's 200 head really went out. Access logs follow the same convention (nginx: status plus bytes; envoy: response flags). There are no production subscribers today (`git grep` hits tests only), so the field is required and every fire site has to state it. **Boundary review:** an alternate impl, such as an HTTP/2 or serverless adapter, knows a cut-off body as a stream reset. The field name leaks nothing (no `destroyed`/`socket`). Subscriber risk: none yet, and future ones must read `incomplete` rather than infer success from `status`. Not an IPC action. | A status of 499 or 0 (nginx-only vocabulary, and wrong once the head is out). An optional `aborted?: true` (an easy-to-miss presence check). |
| 2026-11-01 | **"Send a status if headers haven't gone out" is met in the route, not by reopening `bodyStream()`.** `sendUserFileDownload` checks before its first `res.header()`: (a) the first range's byte count must equal `min(CHUNK, size)`, and (b) for a one-range file (`size <= CHUNK`, including 0) the final validation call runs before the head. Failures are answered. A file that is not the same file is 409 `file-changed`. Any other answer is mapped as the first answer is: absent 404, dir 400 `not-a-file`, unavailable or invalid 503. A throw is 503, with the first read's handling and log. A one-range body is then the bytes already in hand. A multi-range body keeps `wholeFile`, with its post-head teardown and held last chunk. After this, the only failure before the head is a client already gone (nobody to answer). `bodyStream()`'s contract on failures before the head is unchanged. | `bodyStream` has one caller. For a multi-range file the head goes out with the first chunk, which is now pre-checked, and a one-range file's only other read is the final check. Answering before any `header()` means no download header (agent-authored filename in `content-disposition`, octet-stream type) can land on an error body, so no header-reset rule is needed. In a check made up front, absent and changed stay distinct, while `wholeFile`'s throw cannot tell them apart. | Make `bodyStream` hand the adapter back after a failure before the head (reset status and headers, decide what happens to cookies, add an `answerable` flag). That breaks the single-shot adapter and adds contract surface for one caller, and the route could then only answer 409 for a deletion. |
