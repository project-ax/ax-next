## Measured, so nobody re-derives it

- Radix `ToggleGroup type="single"` (installed version): root `role="group"`, items
  `role="radio"` + `aria-checked`. So the radios had **no radiogroup owning them** — a
  second ARIA defect the card did not mention.
- Radix's roving focus moves focus inside a **`setTimeout`**. A synchronous
  `fireEvent.keyDown` + `expect(document.activeElement)` sees no movement and reads as
  "arrow keys do nothing". Wrap focus assertions in `waitFor`.
- channel-web's tsconfig `include: ["src"]` covers `__tests__`, and
  `noUncheckedIndexedAccess` is on: `const [a, b] = getAllByRole(...)` fails `pnpm build`
  even though vitest is happy. The tempting fix — a bare `const working = () => …`
  accessor — puts a **function** where the element belonged, and `expect(working)` then
  passes against any DOM at all.

## Correction — the "stands Radix down" row above was WRONG, and here is what is true

The row "Own the arrow keys in `Segmented` and `preventDefault()` to stand Radix's
RovingFocusGroup down" described a mechanism that does not exist **at the group level**.
The `ax-code-reviewer` pass caught it; re-verified here directly against
`@radix-ui/react-roving-focus@1.1.11` and `@radix-ui/react-slot@1.2.3` in
`node_modules/.pnpm`. (**1.2.3**, not the 1.2.4 also present in the store: every
primitive in this chain resolves through `react-primitive@2.1.3`, whose `react-slot`
symlink is 1.2.3. Their `mergeProps` are byte-identical, so the conclusion stands — but a
durable note that names a package not on the path is a note the next agent cannot check.) Left in place rather than edited away, because the wrong version is
the one a future agent would otherwise re-derive.

- The roving group's **Root installs no `onKeyDown`** — only `onMouseDown`, `onFocus`,
  `onBlur`. Arrow handling is on each **Item**: `composeEventHandlers(props.onKeyDown,
  rovingHandler)` — `dist/index.js` line 201, `dist/index.mjs` line 162. Cite the build
  as well as the line: the CJS one is what the test run loads.
- So a **group-level** `onKeyDown` runs *after* Radix's, on the bubble. `preventDefault()`
  does not stop propagation and cannot un-run a handler that already ran. Both fire, and
  Radix's `setTimeout(focusFirst)` lands last.
- An **item-level** `onKeyDown` does preempt it, by a different route than the original row
  claimed: `RovingFocusGroup.Item` wraps the button with `asChild`, and Radix's `Slot`
  merges handlers as `childPropValue(...); slotPropValue(...)` — child first — where the
  slot's value is the composed handler that skips its own half on
  `event.defaultPrevented`.
- The original row's scenario ("Radix's `focusFirst` wraps from `indexOf(activeElement) =
  -1` and lands on item 0 when focus is on the track") was wrong twice: with the track as
  the keydown target Radix's item handler does not run at all, and the `-1` path it cites
  is the Root's `onFocus` entry-focus, not the keydown path.

**The general lesson, which is the part worth carrying:** "my handler and the library's
compose, so `preventDefault` wins" is a claim about *which element each handler is
attached to*, and in Radix that is frequently not the one the API suggests. Read the dist
before writing it into a comment — a wrong mechanism is invisible whenever the two
handlers happen to agree, which is exactly the LTR / all-focusable / no-`dir` case every
test runs in.

## One thing this fix does NOT do (a conscious call, not an oversight)

`detail` is written ONTO the Decision row at hold time (`pre-call.ts`), not read through a
template at render time — which is deliberate, so a rule edited after the fact cannot
rewrite the sentence somebody was asked to agree to. The cost is that decision rows
already **pending** when this deploys keep the old copy, tool id and all. Not migrated:
the population is whatever is open at deploy time, it drains on its own as rows are
answered or expire (`EXPIRED_RECEIPT`, TASK-447), and a backfill that rewrites stored
consent prose is a worse idea than a few stale rows.
