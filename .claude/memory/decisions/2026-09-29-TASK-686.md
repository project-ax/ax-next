# TASK-686 — "Working" after the agent has replied (warm runner)

| Date | Decision | Rationale | Alternatives |
|---|---|---|---|
| 2026-09-29 | The fix lives in `@ax/agent-activity`, which now also subscribes to `chat:turn-end`. No orchestrator change, no new hook. | `chat:turn-end` already exists and already carries the turn's `agent:invoke` reqId in its payload — the same id the orchestrator resolves its per-turn waiter by (`resolveWaiterFor(payload.reqId, …)`). So no hook surface changes and no boundary review is owed. | A new per-turn "turn-complete" hook from the orchestrator: a second name for a signal that exists already. |
| 2026-09-29 | The record keeps a `turns: Set<reqId>` filled by `chat:start` (`ctx.reqId`) and drained by `chat:turn-end` (`payload.reqId`, NOT `ctx.reqId`, which the IPC boundary restamps). The record goes when the set empties. | This covers both acceptance cases: a lone turn clears on its turn-end, and a second in-flight turn keeps the agent at working. | Forgetting the whole agent on any turn-end: simpler, but a routine fire beside a chat would then read resting on every reply. |
| 2026-09-29 | `chat:end` / `chat:turn-error` STILL forget the whole agent, and the TASK-498 characterization tests are unchanged. | This is the safety argument for the "never pinned on Working" direction. The set only ADDS deletions, so wherever the new code has a record, the old code had one too. A stranded id (a start whose turn-end never came) cannot outlive the end that used to clear it. | A true refcount gating `chat:end`: that fails the pinned direction TASK-498 warned about. |
| 2026-09-29 | A turn-end with no `reqId` forgets the whole agent. A turn-end for an unknown id on a record with an EMPTY set (one `tool:pre-call` recovered) also forgets it. | Both fail in the under-report direction ("we don't know" reads resting). The second case stops the post-`chat:end` recovery record from pinning Working until the reaper. | Matching FIFO by session, as the orchestrator does: that needs session bookkeeping for a case no current producer hits (every orchestrator user-message carries a reqId). |
| 2026-09-29 | `useAgentRail` re-reads when the roster's (`/state`) working/resting word for its agent CHANGES. It reads this through a new non-throwing `useOptionalWorkspace()`. | Only the rail was fetched once per agent: the pill, sidebar and Today strip already re-read on the done frame (AgentView `onDone` → `load()` + `onChanged` → board refresh). Keying on the roster word avoids editing `AgentRail.tsx`, which TASK-685 is working in, and it costs no poll. | Pass `agent.state` into `useAgentRail` from `AgentRail.tsx`: cleaner, but it collides with TASK-685. Polling the rail: a standing cost for a transition signal. |
| 2026-09-29 | Ordering check: agent-activity's turn-end subscriber runs BEFORE the SSE done frame. | `HookBus.fire` runs subscribers in insertion order, and the SSE handler subscribes per connection, long after plugin init. So the client's refetch on `done` already sees resting. | — |

Correction to `decisions/2026-09-20-TASK-498.md` ("sets on `chat:start` and clears on
`chat:end` AND on `chat:turn-error`"): since TASK-686 the record also clears on the
turn's own `chat:turn-end`. Under keepAlive that is the event that matters, because
`chat:end` waits for the idle reaper.
