| 2026-10-04 | The MITM "leaves an established tunnel alone" flake (CI run 37250931997, `read ECONNRESET`) is a TEST race, not a product race; no `listener.ts` change. | Reproduced 5/5 by busy-waiting 300ms right after the 200: the audit row was `502 tls_error: upstream connect timed out after 150ms`, i.e. the timer fired BEFORE the proxy saw `secureConnect`. A loop stall longer than the window runs the timers phase before the poll phase that would deliver the handshake I/O, so the tunnel was never established from Node's view. Once `secureConnect` runs, `clearTimeout` cancels the timer even if it has already expired, so an established tunnel cannot be torn down by it. The production outcome is fail-closed (a 502) and the 30s default makes it moot. | Changing the listener (e.g. re-checking handshake state inside the timer callback) — rejected: it would not change any outcome a client can observe. Widening the window again (100 → 150 → 1000ms) — rejected: still wall-clock, only rarer, and slower. |
| 2026-10-04 | The test fakes only `setTimeout`/`clearTimeout` (`vi.useFakeTimers({ toFake: [...] })`). It waits until the upstream holds the request (the tunnel is established), advances the clock 4x the window, and only then lets the upstream answer. | Faking just these two leaves socket I/O, `setImmediate` and `Date` real. A spy guard checks that the listener armed exactly one timer at `CONNECT_TIMEOUT_MS` on the fake clock and that it is already cleared, so a future `node:timers` import cannot quietly turn this test vacuous. Proven with mutants: dropping the `secureConnect` clear fails it (both at the timer-count guard and, with that guard removed, at `late-reply`), and a `node:timers` timer fails the spy guard. Ran 50/50 green with a 300ms forced stall. | Swapping the elapsed-time assertion for nothing — rejected (that would weaken it). The clock advance replaces it by construction. |
