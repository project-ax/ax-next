# Decisions — TASK-1112 + TASK-1113 (frame-guard pool: the shared busy limit, documented and pinned)

Parent: TASK-1108. Shipped together in one PR.

| Date | Decision | Rationale | Alternatives |
|------|----------|-----------|--------------|
| 2026-11-10 | **The frame-guard HTML preparer pool's busy limit (`maxBusyMs` 5000 of `busyWindowMs` 10000) stays HOST-WIDE: one pool per host process (`startContentOrigin` in `@ax/attachments` makes the only one), one count shared by every user. No behaviour change.** (Vinay, 2026-11-10.) | Load shedding. The worker's CPU budget is 1.5 s a page (`WORKER_BUDGET_MS`), so a worker held 5 of the last 10 s means the host is starved, and turning new uncached previews away then is correct for everyone. Cached pages are answered by the content origin's own cache without asking the pool, and `busy` is never remembered (`REFUSALS.busy.remembered: 'never'`). | A limit per person (declined for now: `prepare()` would take an owner key; earns its keep only when many-user self-hosters report lockouts). |
| 2026-11-10 | **The rule as the code actually behaves (now in the `prepare-pool.ts` header, `busy`, `busyWindowMs`, `maxBusyMs`, `busyTime` comments):** a finished page counts for its WHOLE duration until `busyWindowMs` after it ENDED (pruned by `endedAt`, not prorated); the page in hand counts from `startedAt`, which is set when it leaves the line, so starting a worker is included. One 6 s page (the wall deadline) refuses every user's next page from 5 s into it until 10 s after it ended. `busy` also covers a full line, too much queued text, and the `failureLimit` cool-down. | Card's claims checked against `busyTime()` / `prepare()` / `next()`; all held. The "whole duration until 10 s after end" detail is the one the card's wording ("until that time leaves the window") left vague. | — |
| 2026-11-10 | **TASK-1113: the defaults are pinned behaviourally in `prepare-pool.test.ts` ("by default …"), via the `now` clock option, not by exporting the private constants.** Each pinned from both sides: 4999 ms passes / 5000 refused; still busy at end+10 000, served at end+10 001. Mutation-checked: 5001, 4999, 10_001, 9999 each redden. | Every other busy test passes explicit `BUSY` options, so the defaults could drift silently (TASK-1108's flake came from them). Exporting constants would pin a name, not the behaviour. | Export and `expect(DEFAULT_…)` (rejected: pins a constant, not what the pool does). |
