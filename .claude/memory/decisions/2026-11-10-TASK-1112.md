# Decisions — TASK-1112 + TASK-1113 (frame-guard pool: the shared busy limit, documented and pinned)

Parent: TASK-1108. Shipped together in one PR.

| Date | Decision | Rationale | Alternatives |
|------|----------|-----------|--------------|
| 2026-11-10 | **The frame-guard HTML preparer pool's busy limit (`maxBusyMs` 5000 of `busyWindowMs` 10000) stays HOST-WIDE: one pool per host process (`startContentOrigin` in `@ax/attachments` makes the only one), one count shared by every user. No behaviour change.** (Vinay, 2026-11-10.) | Load shedding. The worker's CPU budget is 1.5 s a page (`WORKER_BUDGET_MS`), so a worker held 5 of the last 10 s is saturated (hostile pages, ~15 heavy ordinary ones at up to 0.35 s each, or a slow machine), and turning new uncached previews away then is correct for everyone. Pages still in the content origin's cache (16 most recent / 32 MiB, host-wide, in memory) are answered without asking the pool; one that dropped out is asked of the pool like any other, and `busy` is never remembered (`REFUSALS.busy.remembered: 'never'`). | A limit per person (declined for now: `prepare()` would take an owner key; earns its keep only when many-user self-hosters report lockouts). |
| 2026-11-10 | **The rule as the code actually behaves (now in the `prepare-pool.ts` header, `busy`, `busyWindowMs`, `maxBusyMs`, `busyTime` comments):** a finished page counts for its WHOLE duration until `busyWindowMs` after it ENDED (pruned by `endedAt`, not prorated); the page in hand counts from `startedAt`, stamped after `start()` returns, so a new worker's boot-until-ready is included (the synchronous fork is not); `spent` keeps only the last 1024. The limit is checked only in `prepare()`, never in `next()`: pages already waiting when the count hits 5 s still run and add to it, so the lockout lasts until the count is back under 5 s. One 6 s page with nothing behind it refuses every user's next page from 5 s into it until 10 s after it ended; with a line behind it, longer. `busy` also covers a full line, too much queued text, and the `failureLimit` cool-down (which answers already-waiting pages `busy` late, not at once). | Card's claims checked against `busyTime()` / `prepare()` / `next()`. The card's "cached pages unaffected" holds only while a page is in the 16-entry cache, and "until that time leaves the window" ignores the waiting line; both corrected by ax-code-reviewer. | — |
| 2026-11-10 | **TASK-1113: the defaults are pinned behaviourally in `prepare-pool.test.ts` ("by default …"), via the `now` clock option, not by exporting the private constants.** Each pinned from both sides: 4999 ms passes / 5000 refused; still busy at end+10 000, served at end+10 001. Mutation-checked: 5001, 4999, 10_001, 9999 each redden. | Every other busy test passes explicit `BUSY` options, so the defaults could drift silently (TASK-1108's flake came from them). Exporting constants would pin a name, not the behaviour. | Export and `expect(DEFAULT_…)` (rejected: pins a constant, not what the pool does). |
