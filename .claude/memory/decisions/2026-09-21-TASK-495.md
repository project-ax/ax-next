# TASK-495 — shared team knowledge on shared agents (2026-09-21)

The user explicitly chose "shared team knowledge when using shared agents." This
overrides the earlier assumption that every memory read is owner-filtered: that
rule still holds for **personal** agents only.

- Personal agent: the resolved owner alone may use memory; product recall and
  forget keep `ownerUserId` in the engine scope.
- Team agent: all currently authorized members share all memory **of that one
  agent** — sharing is scoped to the single resolved agent, not to every agent
  in the team. Product recall/forget omit the owner filter after
  `agents:resolve` succeeds.
- `ownerUserId` on writes is attribution — on **team agents** it carries no
  read/forget filtering at all; on personal agents it is still the read filter.
  `agents:resolve` is the only ACL boundary; it is called on every product op,
  augmentation, and observer run (and re-checked inside the observer's record
  callback, so revocation during a slow extraction lands before the write) —
  no cached membership, no caller/config flag, no fallback. A revoked member
  is denied on the next call before any engine access.
- `about: 'user'` still rewrites to `user:<actual caller>` so two members do
  not collapse into one speaker. Profile recall is **subject-scoped to the
  caller** (`about: user:<caller>` + slot whitelist), not writer-filtered —
  on a team agent a member's profile is their own `user:` rows even though
  the underlying read is agent-wide.
- Provenance precedence (`human > agent > extracted`) and the automatic engine
  slot-chain algorithm are unchanged — engine slot settlement is already
  owner-blind at the `(agent, about, slot)` level, and the page-scoped
  `visibleIds` check is what keeps a foreign `closedBy` id out of the payload.
- UI discloses scope from the server-resolved `factsVisibility`
  (`personal`/`team`), never inferred from request data; unknown scope renders
  no privacy claim.
