# Decisions — TASK-579 (docker-preflight `bounds hang-info` flake)

| Date | Decision | Rationale | Alternatives |
|---|---|---|---|
| 2026-09-26 | Root cause is the TEST's `runInNewContext(..., { timeout: 1_000 })` vm watchdog, not the preflight. Both CI failures (runs 36253712450, 36260485665; both `bash stub > bounds hang-info`) threw "Script execution timed out after 1000ms". The vm timeout bounds only SYNCHRONOUS evaluation, and the checked start ran inline in it, so its sync prefix (config read + `execFile` spawn of the first docker probe) was under a 1000ms wall clock equal to the hang tests' preflight budget. | Brief's hypothesis ("two timers with the same 1000ms budget race") was right about the two clocks, wrong about the shape: they did not race over the same event. The vm clock covered only a ~2ms window that CI stalled past 1s. A 1500ms `Atomics.wait` stall in the checked start's sync prefix reproduces the exact CI message deterministically. | — |
| 2026-09-26 | Fix: the context's `startTestContainer` shim returns `Promise.resolve().then(() => checked(...))`, so the whole preflight (and its `AbortSignal.timeout`) starts after `runInNewContext` has returned and its watchdog is destroyed. Also split the vm budget into `VM_SYNC_BUDGET_MS = 10_000`. | The ordering guarantee is structural (the clocks never overlap), not numeric. The budget only has to cover pure JS: ~2ms idle, 10ms max locally under load; 10s < the 30s `testTimeout` so a genuine sync hang still names itself. | Only bump the vm timeout: rejected, the brief warns against it and the clocks would still overlap. Drop the vm timeout: rejected, it is the guard against a consumer expression that never returns. |
| 2026-09-26 | Regression test pins `vmBudgetMs: 1_000` (the old value) with a 1500ms sync stall, so it goes red on "inline call" and cannot be turned green by raising the number. | A test with the default 10s budget would pass under a bump-only fix, which is exactly the fix we rejected. Mutant (inline call restored) → 2 red (bash + zsh). | — |
| 2026-09-26 | Load evidence: 88/88 file-runs green (5×8 parallel + 16 CPU burners; 3×16 parallel + 28 burners, file duration ~83s vs ~16s idle), 0 vm timeouts. Baseline (unfixed) was also 0/24 locally. | Honest: macOS spawns with posix_spawn and never stalled the window past 10ms, so local load does not DISCRIMINATE this bug; the deterministic stall test does. The load runs show the fix holds, not that load reproduces the bug. | — |
| 2026-09-26 | Implemented inline, no per-task subagents. | One test file, ~30 lines. | — |
