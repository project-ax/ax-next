# Decisions — TASK-887 (pointing a connector somewhere new signs everyone out of it)

Plan: `docs/plans/2026-11-06-task-887-retarget-signs-out.md`. Planner rows (Phases 1–2), written before any code.

| Date | Decision | Rationale | Alternatives |
|------|----------|-----------|--------------|
| 2026-11-06 | **Two card claims are stale, so the plan builds from the code instead.** (1) "TASK-758 resets per-tool permissions when the endpoint, allowedHosts or credential slots change". Measured: `resetMovedEndpoints` resets only when a server keeps its name and changes its url (`connectors/src/plugin.ts:884-923`). (2) "Every agent's row then shows Sign in again". Measured: a purged row shows "Sign in" ("Not signed in yet") or "Add key". It shows "Sign in again" only where a needs-reconnect marker already existed (SIGNINS-5 labels; mcp-oauth `status-batch` reads markers and tombstone-free `credentials:list`). | Building from the card text would under-detect (url only) and promise a label nobody renders. | Take the card at its word. |
| 2026-11-06 | **A "retarget" is an edit whose new definition has a *reach fact* the old one lacks.** The facts are: (a) one per credential slot, top-level and per server: `[slot, derived ref, kind, address of the server it names (transport+url), headerName, authServerUrl, tokenUrl, clientSecretRef as own/other]`; (b) one per top-level allowed host, emitted only when the connector has an env key (api-key without headerName). Removals never count. Facts are raw strings; nothing is parsed. | This mirrors where stored credentials are actually bound. `connector-union.ts:902-915`: OAuth and header keys go to their server's hostname, env keys to top-level allowedHosts. Host-side, `connector-headers.ts` sends to the server url. Sign-in reads the url, allowedHosts, authServerUrl and clientSecretRef. Comparing sets never misses a new destination. Comparing raw strings means a respelling over-purges and never under-purges. The derived ref is included because removing one of two env slots collapses the other onto `account:<id>` and an older row (explorer-traced). | (a) TASK-758's rule, url only: misses rebound slots, AS pins and host additions. (b) "Any capabilities change": signs everyone out on scope or package edits. (c) An exact per-credential host-set model: tighter, but restates another plugin's binding rule wholesale. |
| 2026-11-06 | **Host additions count only for connectors with an env key.** | Only env keys are substituted for top-level hosts. OAuth tokens and header keys bind to their server host alone. The remote editor merges discovered sign-in hosts into allowedHosts on every save (`remote-mcp-form.ts:223-231`), so counting every host addition would sign everyone out on a no-op save whenever discovery returns a host the row didn't store. | Count every host addition, as the card's literal "or allowedHosts" says (rejected: a mass sign-out on an unchanged save). |
| 2026-11-06 | **A path-only url change counts.** | The same "address" definition as TASK-758's reset and the editors' `addressChanged`, so one trigger drives one warning. No URL parsing, so no parser differential. | Compare origins (fewer sign-outs, but it parses URLs and diverges from the tool-permission reset). |
| 2026-11-06 | **These are not reach: OAuth scopes, clientId, clientRegistration, packages, services, display fields, clientSecretRef going between absent and the canonical `account:<id>:OAUTH_CLIENT_SECRET`, a server added that no slot names, server-level hosts.** | None of them moves a stored credential to a new host. A refresh uses only the token blob's own endpoint and client (`mcp-oauth/src/resolver.ts:186-203`, TASK-696). Packages only add registry egress. Service sidecars get no placeholders. Nothing consumes server-level hosts. Server-level slots are kept as facts (dead today, free; the TASK-712 precedent). | Sign everyone out on a scope change too (capability-minimizing, but not what the card asks). |
| 2026-11-06 | **A retarget clears every stored credential of the connector:** every agent's rows (`credentials:purge-account {connectorId, scopes:['agent']}`); global plan refs from the old ∪ new definition (`credentials:delete`); and the connector's own client secret when either side has an OAuth slot. | One rule that's easy to explain: "signs everyone out, clears its shared key and client secret". It mirrors the delete purge. The union covers a ref the edit renamed. The client secret goes to whatever token endpoint the new address discovers. purge-account already reaches per-agent API keys, and those carry the same leak, so they go too. | Clear only the credentials whose destination moved (mixed outcomes, hard to word in a warning). Widen purge-account to global scope (refused since SIGNINS-1/7, invariant 5). |
| 2026-11-06 | **"Sign everyone out" means that connector's rows on every agent, never an agent's other sign-ins** (the orchestrator's open question). | purge-account with `connectorId` matches `account:<id>` and `account:<id>:*` only. Not a human decision: the code supports exactly this reading. | Sign agents out of everything (no basis). |
| 2026-11-06 | **The clear is the LAST pre-write gate in `connectors:upsert`** (after TASK-758's reset and TASK-809's ceiling sources, before `store.upsert`). A throw refuses the edit with the new `@ax/core/error-codes` `CONNECTOR_SIGN_OUT_FAILED = 'connector-sign-out-failed'`, which the routes answer as 503. There is no authority flag. | The TASK-758 pattern. A post-commit clear that fails leaves the leak live, and re-saving the same address detects nothing. Running last means an earlier gate failing never signs anyone out for nothing. If the clear lands and the write fails, people are signed out of an unchanged connector: a UX cost, not a leak, and Save retries. A flag would let a caller retarget *without* the clear; the clear is the consequence of the retarget, not a privilege. | Post-commit clear. Reuse `tool-permissions-reset-failed` (wrong copy). A subscriber event (the bus swallows throws). |
| 2026-11-06 | **No post-commit repeat purge.** | The gap between the clear and the commit is one DB write. The realistic stale-token path, a popup begun before the retarget, is closed in mcp-oauth instead (next row). The remaining sub-second races are logged as follow-ups. | Repeat the purge after the commit (narrows a millisecond window only). |
| 2026-11-06 | **The mcp-oauth callback refuses a sign-in when the connector's OAuth server url no longer equals the address it began for (`pending.resource`).** The refusal is `sign-in-failed` with log stage `connector-changed`. | A popup open across a retarget (pending TTL 10 min) would write a token minted for the old resource after the clear. The runtime sends a token to the current url, and nothing compares `blob.resource` with it (explorer-traced). That is the exact leak this card closes, so it ships here. The callback already re-reads the connector (`routes.ts:955-986`). | Accept the 10-minute window. Check at use time in the resolver (it doesn't know the current url). |
| 2026-11-06 | **Needs-reconnect markers are left alone.** | A leftover marker only makes that agent's row say "Sign in again", which is accurate. Clearing or setting markers for every agent would need a new mcp-oauth hook for one label. | A new hook to clear or write markers for all agents. |
| 2026-11-06 | **Both editors, on an edit, write the connector (PATCH) first and its secrets after. Creates are unchanged.** | The server clears secrets inside the PATCH, so a key typed in the same save must land afterwards. Flipping every edit, not only the ones the client copy calls a retarget, means drift in that copy can never wipe a typed key. A refused PATCH (403/503) then writes no secret, which makes the existing "Your saved settings are unchanged" copy true; today a Replace overwrites the live key even when the PATCH is refused. This supersedes L's "M3" ordering for edits: a connector that names a missing secret already has its own copy ("The client secret is missing…", SIGNINS-7). The secret's ref is deterministic, so the PATCH can name it before the write. | Flip only when the client copy says retarget. Carry secrets in the PATCH body (puts secrets through the connectors routes). |
| 2026-11-06 | **The remote editor asks for saved shared header values and a saved custom-client secret again on a retarget (Remove lifts the secret requirement), and its "Send saved headers to {host}" confirmation is removed.** | The card says the editor asks the admin to re-enter the key in the same save. The checkbox confirmed sending saved keys to a new host, which no longer happens; keeping it would contradict the server. | Keep the checkbox. |

| 2026-11-06 | **The rule emits one slot fact per server that shares the slot's server name** (not "first server named X"). | Server names are not unique, and `@ax/mcp-client` `connector-headers.ts` sends a slot's token/header to EVERY server whose name matches, so adding a same-name server at a new url would leak with a first-match rule (found by the Task 3 implementer).
