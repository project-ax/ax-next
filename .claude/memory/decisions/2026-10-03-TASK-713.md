# Decisions — TASK-713 (MCP OAuth follow-ups from TASK-696, items 1+2)

| Date | Decision | Rationale | Alternatives |
|---|---|---|---|
| 2026-10-03 | **Item 1's premise was wrong. `@ax/mcp-client` `transports.ts` `resolveCredentials` (which wraps every failure as `credential-resolution-failed`) is NOT on the chat path for OAuth connectors, so it is left unchanged.** It only serves `/admin/mcp-servers` configs connected once at plugin init with a system ctx, the admin `/test` route, and the CLI. In chat, a connector's OAuth credential is resolved by `proxy:open-session` (`credential-proxy`), and a dead one terminated the turn as `proxy-open-failed`, which the UI shows as the generic "The agent stopped unexpectedly". | Read the path: `chat-orchestrator/src/connector-union.ts` `foldConnectorCaps` → `proxy:open-session` → `credentials:get` → `credentials:resolve:mcp-oauth`. This corrects TASK-696's review row ("mcp-client resolveCredentials wraps the resolver's needs-reconnect error … so in chat a dead OAuth connection gives no reconnect prompt"), which was read in code but never traced. | Change `transports.ts` as the card said: it would not change anything a chat user sees. |
| 2026-10-03 | **The orchestrator's proxy-open catch now reports `connector-needs-reconnect` when the error, or its `.cause`, is NAMED `NeedsReconnectError`. channel-web maps it to "One of this agent’s connectors needs you to sign in again. Open Connectors, reconnect it, then retry."** | It matches by name rather than by import (no cross-plugin import), using the same NeedsReconnectError name check as `describe-tools` `noUsableCredential` (TASK-756). It is narrower than that classifier: `credential-not-found` is NOT treated as reconnect here, because `proxy:open-session` resolves the whole merged set (provider keys included) without saying which ref failed. A missing provider key would otherwise tell someone to reconnect a connector. So a connector whose account row is absent still reads as `proxy-open-failed` (review finding, accepted; follow-up: carry the failing ref out of open-session). HookBus wraps once, and credentials/credential-proxy pass a PluginError through, so `.cause` is one level deep. A vault blip, a decrypt failure or a missing provider key keeps `proxy-open-failed` (TASK-756's transient-vs-needs-auth split). The rail already shows the connector as "Your sign-in expired" or "Team sign-in expired", because the resolver writes the marker on this same failure. | Name the connector in `detail`: this needs credential-proxy to rethrow with the failing ref. Deferred, because the rail already names it. An in-chat Reconnect button: deferred as a follow-up. |
| 2026-10-03 | **`mcp-oauth` `errFields` never logs a message, at any of its call sites. It logs `name`, `code`, `causeName` and `causeCode` (the SDK OAuthError's `errorCode`, an RFC 6749 wire code).** | Item 2 was INFERRED in the brief and is now verified by reading and by a test: when a refresh fails transiently, the resolver rethrows the SDK `OAuthError`, and HookBus wraps it as `PluginError{code:'unknown', message:"service hook '…' threw: <error_description>"}`. The old comment said "a PluginError's message is author-facing and carries no secret", which is false for every bus wrapper. The new test builds the wrapper with a real `HookBus` and an SDK `ServerError`. | Fix only the `/status` site: the other six sites can log the same wrapper (begin's client-secret `credentials:get`, the callback vault write). |
