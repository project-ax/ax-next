| 2026-11-25 | **Which clock wins: the readiness budget (it carries the diagnosis and deletes the pod). A flat 240 s would let a larger programmatic `readinessTimeoutMs` push the prep pod past the backstop. | (A) one fixed backstop sized for 16 services (2220 s): no kernel change, but a hung service-less spawn would sit 37 min instead of 5. | 2026-11-25 | **Mechanism: `HookBus.registerService`'s `timeoutMs` may be a function of the call's input (`ServiceTimeoutMs = number \| ((input: unknown) => number)`).** The bus resolves it in `call()` before the stall watch and the handler; a policy that throws, or returns NaN / a negative / -Infinity, fails the call with `invalid-payload` and never runs the handler. | Today the bus has no per-call timeout and no handler signal (per-registration only, `hook-bus.ts:389`). | 2026-11-25 | **"Delete the pod when the open gives up" is structural, not new plumbing.** With the backstop above the budget, the open gives up AT the readiness deadline, where the existing catch (`open-session.ts:602-645`) kills the pod and terminates the session before it throws. | 2026-11-25 | **Also name a service that never became ready without crashing (diagnosis fallback, independently droppable).** When no sidecar is crashing, walk `initContainerStatuses` in order to the first one that is not `ready`, not `started` and not exited 0. `started` counts as done so a started container is never blamed: a probe-less sidecar's `ready` is not relied on, and a job still running is missed instead, because a miss is safer than a wrong name.
