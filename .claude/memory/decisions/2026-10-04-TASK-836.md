# TASK-836 — Blob GC: make S3 retire/restore crash-safe

| Date | Decision | Rationale | Alternatives |
|------|----------|-----------|--------------|
| 2026-10-04 | Card premise corrected: a crash between S3's CopyObject and DeleteObject cannot lose data. Both moves copy first, so a kill leaves BOTH copies, never none. The real defect was that the both-copies residual was never repaired: a row said `retired` over live bytes until retention, and a retired duplicate under a `live` row was never purged at all (a leak). SECURITY.md's documented data-loss residual is a CONCURRENCY race (retire racing restore), not a crash | Read `S3BlobStore.retire`/`restore` (copy-then-delete) and the sweep; proven by store tests that kill the process at each DeleteObject | Reorder the moves (no safer order exists without a rename) |
| 2026-10-04 | Repair lives in the GC sweep's DISCOVER step, enforce only, backend-agnostic (no store or hook change): listed-live + row retired → `reviveListed` (row live, fresh grace); listed-retired + row live → `claimLive` (refresh grace), `blob:stat {restore:true}`, then `blob:purge` only if the stat found a copy | Discovery already pages both namespaces, so the signal is free. "Live wins" is the only rule that is safe for every crash point: a retire residual and a restore residual look identical (row retired, both copies), so the GC cannot tell which move to finish; reviving is never destructive, and a wanted retire happens again a grace window later | Finish the interrupted move (undoes reader restores, ambiguous); stat every retired row each sweep (O(retired) requests); a new hook to report which namespaces hold a sha (boundary change for no gain) |
| 2026-10-04 | `claimLive` is the mutual exclusion for the one destructive repair step: it bumps `last_put_at` before the purge, and `markRetired` only flips rows with `last_put_at < cutoff`, so no retire (this sweep's, or a second sweep that lost the advisory lock) can start moving the live copy while the retired one is being purged | The advisory lock is "for efficiency, not safety" per the store's own doc; a purge of the retired copy racing a retire of the live copy is exactly the drop-both-copies shape | Trust the advisory lock |
