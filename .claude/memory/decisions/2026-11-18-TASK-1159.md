| 2026-11-18 | **Planner: the card's premise holds; no blocker. Connect stores the pasted refresh token untried (`admin-routes.ts:458-459`), so a dead one shows up only at the first Rename (502 `slack-config-token`) or Disconnect (`appDeleted:false`, then a leftover). Plan: Connect rotates the pasted refresh token once, right after `apps.manifest.create` and before any vault or store write, and stores the refresh token Slack mints in its place. Any rotate failure takes the new app back with the pasted access token and answers 502 (`slack-refresh-token` when Slack refused the token, else `slack-error`); if Slack won't delete the app either, it goes onto the leftover list through a new store method. 5 tasks (2 mechanical, 2 integration, 1 sensitive), one PR. security-checklist required (Task 2). No boundary review: no hook, IPC action or manifest change; `POST /admin/slack/connect` gains one 502 error code on an HTTP admin route channel-web mirrors by shape.** | The card's "Also: TASK-1128 should delete leftover apps under the same admin lock" is a forward note: TASK-1128 isn't built (no replace route in `admin-routes.ts`; design §3:286 "isn't built yet (TASK-1128)"), and TASK-1132's handoff already passed that note on. | 2026-11-18 | **The rotate goes right after `apps.manifest.create` succeeds and before anything is stored: no vault write, no install row, no icon, no OAuth state exists when it runs.** | A failed create (expired access token, refused name, unconfirmed) never spends the pasted pair, so the admin can fix the name and retry with the same pair (TASK-1132 row 6's stated aim; the existing createApp-failure test already pins `slackMethods == ['createApp']`). Rotating before any write makes a refusal's undo exactly one Slack call (delete the app): no row to remove, no secret to tombstone, no pending row a concurrent `GET /admin/slack` (which takes no lock) could see without a token. The `config-refresh-token` put that exists today simply stores `minted.refreshToken` instead of the pasted one. | Rotate before `apps.manifest.create` (no app to undo on a refusal, but every create failure spends the pasted pair). Rotate last, after the pending row and secrets (two writes of one secret, a bigger undo, and a pending row briefly visible without a usable token). |
| 2026-11-18 | **Every rotate failure takes the app back, not only a refusal. Contradicts the brief's lean ("a transient fault should probably not delete the app").** Refused (`invalid_refresh_token` or a `TOKEN_ERRORS` code) → 502 `slack-refresh-token`. Anything else (`timeout`, `network`, `http-5xx`, `bad-response`, `too-large`, `ratelimited`, `redirect`, another Slack code, a non-Slack throw) → 502 `slack-error` ("Try again in a minute"). | Most transient codes can't tell whether Slack rotated: `timeout`, `network` and a 5xx may have spent the pasted token, and `bad-response` means Slack DID answer ok but we couldn't read the successor (the pasted token is spent for sure). Storing the pasted token in those cases is exactly the card's bug, delayed by minutes to hours, and it surfaces at a Rename or Disconnect after channels are connected, where the only fix (Disconnect, then Connect) costs every channel binding. Undoing costs one retry of a one-time setup step before Allow. Only `ratelimited` proves the token unspent; a third branch for it buys nothing "try again in a minute" doesn't. A retry soon after works even if the lost rotate spent the token, because Slack honours a rotated token for a while (18 s to 3 h, TASK-1129 row 26). | Keep going with the pasted token on transient faults (the card's bug, rarer). Special-case `ratelimited`. Retry the rotate once inside the request (doubles the lock hold, may mint a second live pair; the client never retries by design, TASK-1132 Task 2 walk). |
