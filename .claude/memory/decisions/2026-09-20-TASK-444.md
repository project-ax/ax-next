## 2026-09-20 — TASK-444 "Not now" is a durable, need-triggered deferral

- `2026-09-20` (TASK-444) — **The card's technical claim CONFIRMED, with one correction worth carrying.** `GrantRow.reject()` really does send nothing: it clears the draft and calls `onResolved`, and the file's own comment asserts that is correct (*"Turning a grant down is PURELY LOCAL — no network call … There is nothing to tell the server"*). That sentence is the stale line this card was filed against and it is rewritten in this PR, not worked around. The correction: the grant that "comes back on reload" can only ever be a **skill or connector** one. `ChunkBuffer.pendingGrantsForUser` deliberately excludes `host` cards (they are turn-scoped, and `proxy:add-host` widens only the LIVE session), so a host "Not now" is *already* unreachable by the read-back. Making a host decline durable would be actively WRONG — a later session that hits the same wall is a genuine new need, which is exactly what the product decision says must re-ask.

- `2026-09-20` (TASK-444) — **Need-triggered was implementable with no new trigger, because the two re-raise paths already differ in kind.** `chat:permission-request` → `appendPermissionCard` → SSE is the agent asking *now*; `GET /api/workspace/grants` → `pendingGrantsForUser` is a replay of an already-answered question on every workspace mount. So the whole deferral is "the decline suppresses the replay, and a newer raise outranks an older decline": stamp `raisedAt` on the buffered card (on insert **and** on the replace-in-place branch — a re-proposal is a fresh need), store `declinedAt` durably, and filter the read-back when `declinedAt >= raisedAt`. *Alternatives:* (a) clear the marker on append — rejected, it puts a durable write on the permission-request path and destroys the record of refusal the product owner explicitly asked for; (b) evict the pending card on decline — rejected, it satisfies both acceptance tests while leaving the durable marker **half-wired**, and it loses the refusal instead of recording it; (c) any `deferred_until`/timer — explicitly ruled out by the clarification.

- `2026-09-20` (TASK-444) — **The marker lives in the generic `storage:*` KV, NOT in a new `@ax/grant-declines` plugin.** Key `grant-decline:<enc(userId)>:<enc(agentId)>:<enc(kind)>:<enc(subjectId)>`, value `{declinedAt}` as encoded JSON — the same substrate `@ax/branding` (`'settings:branding'`) and `@ax/audit-log` already persist through, and present in **both** presets (`@ax/storage-sqlite` in the CLI, `@ax/storage-postgres` in k8s). *Alternative, and it is the conventional one:* a new plugin modelled on `@ax/host-grants` with a `grant_declines_v1_declines` table. REJECTED for cost, not for taste — it needs a migration, a testcontainers suite, and **ten** registration points (root + preset tsconfig, preset package.json, preset index, the exhaustive `preset.test.ts` name list, two `PLUGINS_TO_DROP` sets, `prod-bootstrap.test.ts`, a changeset) to persist one timestamp. Survey finding that made the call easy: **nothing in the repo records a negative verdict today.** `skills_v1_approved_caps`, `connectors_v1_authored`, `host_grants_v1_grants` all record allows only, and `connectors:clear-authored` *deletes* rather than records — so there was no existing owner to extend, only a new one to invent. Left as a follow-up for the day declines need listing or revoking from Settings.

- `2026-09-20` (TASK-444) — **No storage key and no timestamp crosses the wire.** `POST /api/workspace/grants/decline` takes `{agentId, kind, subjectId}` and the server builds the key and reads its own clock. Two reasons, and the second is the one that nearly went the other way: (1) invariant 1 — the payload has to survive the alternate impl, and it does, because a `grant-declines:record` hook would take the same three fields; (2) a client-supplied `declinedAt` is an untrusted far-future value that would suppress a consent prompt **permanently**. The route additionally refuses to record a decline for a grant that is not genuinely pending for the authenticated caller (404, never 403 — same no-oracle posture the `grants` read already takes), so the forgeable surface is "suppress a question you are already being asked".

- `2026-09-20` (TASK-444) — **Security note: `storage:list-prefix` is the sharp edge, not `storage:set`.** The same KV holds `@ax/credentials-store-db`'s encrypted credential rows, so a prefix that took any part of its value from the request would be a cross-namespace read. The prefix is built **server-side from the authenticated userId only**, every segment `encodeURIComponent`'d so an id carrying `:` cannot forge a segment boundary or another user's namespace, and `storage:delete-prefix` is deliberately not called at all. Fail direction: a forged or duplicated marker can only SUPPRESS a prompt, never grant a capability.

- `2026-09-20` (TASK-444) — **The half-typed secret goes on the decline whether or not the POST lands, and the row does NOT.** Those two pull in opposite directions and both are deliberate. The draft is cleared first and unconditionally (`clearGrantDraft` **and** `setValues({})`) because the person's intent is withdrawal — TASK-389 made the draft outlive the component on purpose, and this is the one exit where it must not. But a failed decline leaves the ROW on screen with the error, because a refusal the server never heard is a refusal that will come back, and dropping the row would be the same silent lie this card is about.
