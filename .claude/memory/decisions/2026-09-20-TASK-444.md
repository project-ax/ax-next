## 2026-09-20 — TASK-444 "Not now" is a durable, need-triggered deferral

- `2026-09-20` (TASK-444) — **The card's technical claim CONFIRMED, with one correction worth carrying.** `GrantRow.reject()` really does send nothing: it clears the draft and calls `onResolved`, and the file's own comment asserts that is correct (*"Turning a grant down is PURELY LOCAL — no network call … There is nothing to tell the server"*). That sentence is the stale line this card was filed against and it is rewritten in this PR, not worked around. The correction: the grant that "comes back on reload" can only ever be a **skill or connector** one. `ChunkBuffer.pendingGrantsForUser` deliberately excludes `host` cards (they are turn-scoped, and `proxy:add-host` widens only the LIVE session), so a host "Not now" is *already* unreachable by the read-back. Making a host decline durable would be actively WRONG — a later session that hits the same wall is a genuine new need, which is exactly what the product decision says must re-ask.

- `2026-09-20` (TASK-444) — **Need-triggered was implementable with no new trigger, because the two re-raise paths already differ in kind.** `chat:permission-request` → `appendPermissionCard` → SSE is the agent asking *now*; `GET /api/workspace/grants` → `pendingGrantsForUser` is a replay of an already-answered question on every workspace mount. So the whole deferral is "the decline suppresses the replay, and a newer raise outranks an older decline": stamp `raisedAt` on the buffered card (on insert **and** on the replace-in-place branch — a re-proposal is a fresh need), store `declinedAt` durably, and filter the read-back when `declinedAt >= raisedAt`. *Alternatives:* (a) clear the marker on append — rejected, it puts a durable write on the permission-request path and destroys the record of refusal the product owner explicitly asked for; (b) evict the pending card on decline — rejected, it satisfies both acceptance tests while leaving the durable marker **half-wired**, and it loses the refusal instead of recording it; (c) any `deferred_until`/timer — explicitly ruled out by the clarification.

- `2026-09-20` (TASK-444) — **The marker lives in the generic `storage:*` KV, NOT in a new `@ax/grant-declines` plugin.** Key `grant-decline:<enc(userId)>:<enc(agentId)>:<enc(kind)>:<enc(subjectId)>`, value `{declinedAt}` as encoded JSON — the same substrate `@ax/branding` (`'settings:branding'`) and `@ax/audit-log` already persist through, and present in **both** presets (`@ax/storage-sqlite` in the CLI, `@ax/storage-postgres` in k8s). *Alternative, and it is the conventional one:* a new plugin modelled on `@ax/host-grants` with a `grant_declines_v1_declines` table. REJECTED for cost, not for taste — it needs a migration, a testcontainers suite, and **ten** registration points (root + preset tsconfig, preset package.json, preset index, the exhaustive `preset.test.ts` name list, two `PLUGINS_TO_DROP` sets, `prod-bootstrap.test.ts`, a changeset) to persist one timestamp. Survey finding that made the call easy: **nothing in the repo records a negative verdict today.** `skills_v1_approved_caps`, `connectors_v1_authored`, `host_grants_v1_grants` all record allows only, and `connectors:clear-authored` *deletes* rather than records — so there was no existing owner to extend, only a new one to invent. Left as a follow-up for the day declines need listing or revoking from Settings.

- `2026-09-20` (TASK-444) — **No storage key and no timestamp crosses the wire.** `POST /api/workspace/grants/decline` takes `{agentId, kind, subjectId}` and the server builds the key and reads its own clock. Two reasons, and the second is the one that nearly went the other way: (1) invariant 1 — the payload has to survive the alternate impl, and it does, because a `grant-declines:record` hook would take the same three fields; (2) a client-supplied `declinedAt` is an untrusted far-future value that would suppress a consent prompt **permanently**. The route additionally refuses to record a decline for a grant that is not genuinely pending for the authenticated caller (404, never 403 — same no-oracle posture the `grants` read already takes), so the forgeable surface is "suppress a question you are already being asked".

- `2026-09-20` (TASK-444) — **Security note: `storage:list-prefix` is the sharp edge, not `storage:set`.** The same KV holds `@ax/credentials-store-db`'s encrypted credential rows, so a prefix that took any part of its value from the request would be a cross-namespace read. The prefix is built **server-side from the authenticated userId only**, every segment `encodeURIComponent`'d so an id carrying `:` cannot forge a segment boundary or another user's namespace, and `storage:delete-prefix` is deliberately not called at all. Fail direction: a forged or duplicated marker can only SUPPRESS a prompt, never grant a capability.

- `2026-09-20` (TASK-444) — **The half-typed secret goes on the decline whether or not the POST lands, and the row does NOT.** Those two pull in opposite directions and both are deliberate. The draft is cleared first and unconditionally (`clearGrantDraft` **and** `setValues({})`) because the person's intent is withdrawal — TASK-389 made the draft outlive the component on purpose, and this is the one exit where it must not. But a failed decline leaves the ROW on screen with the error, because a refusal the server never heard is a refusal that will come back, and dropping the row would be the same silent lie this card is about.

- `2026-09-20` (TASK-444, review round 1 — **CHANGES REQUESTED**, 1 Important + 2 Minor + 2 Nit) — **The Important one is the lesson: I fixed ONE of the two server paths that put a pending card in front of a person, and the one I missed is the commoner.** `GET /api/workspace/grants` (the mount read-back, TASK-373) was filtered; the TASK-82 replay at `sse.ts` — `tailPermissionCards(conversationId)` on stream open — was not. Because the decline deliberately does **not** evict the card (the marker is the record, not the deletion), the card sits in `skillCards` with its original `raisedAt`, and the replay hands it straight back the next time a stream opens on that conversation. That is not a reload: it is *declining a skill and then sending one more message to the same agent*. The generalisable rule: **"do not delete, suppress instead" is only half a design — it obliges EVERY reader of the thing you did not delete to apply the suppression.** Enumerate the readers before you pick suppression over deletion. `grep` for the accessor, not for the feature.
- `2026-09-20` (TASK-444, review round 1) — **The fix is one shared `withoutDeclinedGrants` in `grant-declines.ts`, called by both paths**, plus a second buffer accessor `tailPermissionCardEntries` (cards *with* `raisedAt`) so `tailPermissionCards`'s browser-facing shape stays a list of cards. Two copies of the comparison would have been the same defect with a longer fuse.
- `2026-09-20` (TASK-444, review round 1, Minor — taken as a comment, not a change) — **wall clocks are not monotonic.** The need-trigger is `declinedAt < raisedAt` between two readings of one process's `Date.now()`; a backward NTP step after a decline can stamp a later genuine re-raise BELOW the stored `declinedAt` and suppress a needed grant until the clock catches up. Stated at the comparison rather than fixed: the repairs are a monotonic source that cannot survive a restart, or an expiry — and an expiry is exactly what this design must not have.
- `2026-09-20` (TASK-444, review round 1, Minor — deferred with a trap noted) — **decline markers are never reclaimed**, so a heavy user accumulates dead rows re-scanned on every workspace mount. Deferred to the `@ax/grant-declines` follow-up, with the obvious wrong fix written down beside `recordGrantDecline`: do **not** reach for `storage:delete-prefix` with an exact key, because `subjectId` is variable-length and `…:abc` is a prefix of `…:abcd` — a "delete this one" would silently take a sibling grant's refusal with it.
- `2026-09-20` (TASK-444, review round 1, Nit — taken) — **two independent `now` seams that MUST read one clock.** `ChunkBufferOptions.now` stamps `raisedAt`, `WorkspaceHandlerDeps.now` stamps `declinedAt`; production injects neither, so both are the system clock, but nothing structural says so and a test stubbing one would compare two clocks and get an answer that means nothing. Each seam's doc now names its twin: stub both or stub neither.
- `2026-09-20` (TASK-444, review round 2 — **CHANGES REQUESTED**, 1 Important) — **My own fix for round 1 broke a documented synchronous-setup guarantee, and the comment that documented it was the only thing that said so.** `sse.ts`'s handler is synchronous from `res.status(200).stream()` to the last `subscribe()`, and its step-4a comment spells out what depends on that. Turning the replay into `await withoutDeclinedGrants(...)` dropped an `await` through the middle of that span: a `chat:stream-chunk` fired in the gap was appended after the drain and handed to a subscriber not yet attached (spurious TASK-23 "lost frames"), a `chat:permission-request` in the same gap vanished **silently** (no seq, no gap net) — the exact TASK-82 class the buffer exists to prevent — and a client disconnecting in the gap ran `cleanup()` against six not-yet-attached subscribers, after which the handler attached them anyway plus a keepalive nothing would ever clear. **The generalisable rule: when a function's comment states a timing invariant, adding an `await` inside that span is a behaviour change even though nothing in the types moves.** Fix: read before the stream opens, filter (synchronously) where the cards are. `grant-declines.ts` split into async `readGrantDeclines` + a synchronous TOTAL `filterDeclinedGrants`.
- `2026-09-20` (TASK-444, review round 3 — **CHANGES REQUESTED**, 1 Minor + 2 Nit) — **Splitting the read from the filter also left the empty-list short-circuit behind, and nobody noticed because the test comment still described it.** `withoutDeclinedGrants` skips the store when there are no rows; the SSE path stopped calling it, so every stream open scanned the person's markers — including the common case of a conversation with no pending card, and the turn-error replay that returns before the filter is reached. One `list-prefix` per grants read quietly became one per turn. **Lesson: when you split a function in two, enumerate the guards that lived in the seam — a short-circuit is behaviour, not an optimisation detail, and it does not survive the split by itself.** Restored as an explicit gate on a snapshot taken before the read (safe in both directions, for two different reasons), with two tests: the store is untouched when nothing is pending, asked exactly once when something is. Mutation-verified — deleting the gate reddens exactly the first of those and nothing else.
- `2026-09-20` (TASK-444, review round 3, Nit — taken) — **a totality test that plants its hostile input in the wrong segment is testing the mechanism, not the threat.** The lone-surrogate case used `agentId`, which is server-derived on BOTH call paths (the conversation lookup on the SSE side, the card's recorded owner on the workspace side). The genuinely untrusted segment is `subjectId`, straight out of an agent-authored manifest. Same code path, but only one of the two spellings documents what we are actually defending against.
- `2026-09-20` (TASK-444) — **Three review rounds, and all three findings were in code I had just written to fix the previous round's finding.** Round 1: the read-back was filtered, the SSE replay was not. Round 2: filtering the SSE replay put an `await` in the one span that must not have one. Round 3: hoisting that read out of the span dropped the empty-list short-circuit. Each fix was correct about the thing it fixed and wrong about the thing next to it. *Meta-lesson worth more than any of the three: after moving a call across a boundary — a span, a function, a file — re-read what the OLD site was doing besides the call itself. Twice running, the thing lost in the move was a guard nobody had written down as a requirement, only as a comment.*
