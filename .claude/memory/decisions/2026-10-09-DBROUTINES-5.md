# DB-backed routines — Task 5 consent boundary

- Tool-policy owns durable routine consent keyed by `(agentId, ctx.userId)` and an idempotent delivery ledger keyed by decision ID with the same scope. No memory fallback or permission cache. Missing database/ACL providers and read outages leave eligible tools held; get/revoke/grant fail explicitly rather than claiming disabled success.
- The grant hook's only payload is `{decisionId, expectedRevision}`. Before any DB work it requires the host-only `ctx.state` key `decisions:routine-consent-grant`, strict shape `{decisionId,agentId,userId,toolName:'routine_create'|'routine_update',expectedRevision}` matching payload and real context. Task 6 must mint this fresh delivery context from its stored, approved `agent-routines` intent only when release is due, and remove the marker after awaited delivery. Session naming, ordinary replay/turn state and sandbox input grant nothing. The marker is invocation capability, not durable authority.
- Grant serializes shared agent fence → decision ID → agent/person scope. Duplicate ledger hits return `{delivered:true}` with CURRENT consent, never write enabled again. Revoke always writes disabled with a new revision, including when the row was absent. If revoke wins before first delivery, code `consent-revision-conflict` is terminal for that intent; Task 6 settles it failed rather than retrying forever. New approval uses a new intent/decision and current revision.
- Purge takes the exclusive agent fence, adds a same-plugin durable retired-agent marker, then deletes both consent and scoped delivery rows. Late preauthorized grant/revoke cannot recreate data. Absence/retired data reads disabled/revision `0` internally; actual public get still resolves real agent access, so a deleted agent returns the agent directory's not-found.
- Tool-policy invokes `agents:resolve` and `agents:can-manage-routines` at runtime under an explicit, controller-approved reverse-edge exception: agents already depends on tool-policy for connector snapshot, so manifest declarations would introduce a boot cycle. Runtime guards deny missing providers/outages. A real agents+teams+policy+DB bootstrap/ACL/deletion test pins this; Task 12 must keep actual agent ACL producers in the preset/canary.
- Static rules retain create/update hold and the explicit `routineConsent:'create-update'` opt-in. Only a matched opted-in create/update hold can relax; denied/unopted rules, delete and fire-now never inherit consent. Fire-now is held, irreversible, with spends/outward disclosures. Runtime rail rows show granted create/update as allow with grant provenance while preserving the rule ID, capability and conditional/effect disclosures.
