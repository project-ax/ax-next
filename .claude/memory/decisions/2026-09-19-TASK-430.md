# TASK-430 — a failed command must not be published as a success

## The five outcomes, and which we can tell apart

Enumerated before touching code, because collapsing any two of them is how this
bug got here. For the aisdk runner's `Bash` tool:

| outcome | how we know | published |
|---|---|---|
| succeeded | `exitCode === 0`, no flags | clean |
| exited non-zero | `exitCode` is a non-zero number | `is_error` |
| killed by a signal | `exitCode === null` + `signal` | `is_error` |
| timed out | our own `timedOut` flag, set before we kill | `is_error` |
| cancelled | our own `aborted` flag | `is_error` |
| never started | `child.on('error')` rejects — no exit status at all | `is_error`, by the SDK's own throw path |

`timedOut` / `aborted` are **our** flags, set before we send SIGKILL, so they
never have to be inferred from the signal — a command killed by an outside
SIGKILL stays distinguishable from one we timed out.

## Decision 1 — the aisdk runner: report the failure, don't throw, don't parse

`ai@7` has exactly one failure channel, the thrown executor. `Bash` cannot use
it: `ai@7` discards a thrown executor's return value and the failing build's
output is the thing the model needs. So a runner returns `{output, failed:true}`
(`ToolFailure`), `wrapWithPolicy` reports the id through `onToolFailure`, and a
per-turn `FailedCallRegistry` — the same shape and lifetime as TASK-270's hold
registry — is read by BOTH the live chunk and the persisted block, so they
cannot disagree.

Rejected: `tool.toModelOutput` mapping failures to `error-text`. It works
(verified in `ai@7.0.70`'s `createToolModelOutput`), but it changes what the
MODEL is handed, and the claude-sdk runner can't match that — the two runners
are meant to be host-indistinguishable. The registry keeps the model-facing
bytes identical and puts the new fact only where it was missing: the host
record.

Rejected: reading the exit code out of the output text. It is command-authored,
so `echo "exit code: 1"` would be marked failed and a silent failure would not.
Same rule that governs `held`.

Also fixed on the way past: `formatBashOutcome` rendered a **signal-killed**
command with no output as `(command produced no output; exit code: 0)` — an
exit code we never observed, invented for a process that was shot. And
`isErrorOutput` keyed on `error-text` only, while `ai@7` picks `error-text` or
`error-json` per call site (`errorMode`), so "did this fail?" depended on which
SDK path built the message. Both now accepted.

## Decision 2 — the CLI half (claude-sdk runner): PIN AND REPORT

The card offered two options: carry a separate exit-status signal, or pin the
behaviour and report it. **Measured, not inherited:** the first option has no
signal to carry.

`@anthropic-ai/claude-agent-sdk@0.2.119`, `sdk-tools.d.ts` → `BashOutput`:

```
stdout, stderr, rawOutputPath?, interrupted, isImage?, backgroundTaskId?,
backgroundedByUser?, assistantAutoBackgrounded?, dangerouslyDisableSandbox?,
returnCodeInterpretation?, noOutputExpected?, structuredContent?
```

There is **no exit-code field**. `returnCodeInterpretation` is a string, and its
own doc says it is for *non-error* exit codes with special meaning.
`grep -Ei 'exit[_ ]?code|returncode'` across `sdk-tools.d.ts` / `sdk.d.ts` /
`agentSdkTypes.d.ts` finds only that, plus `SDKHookResponseMessage.exit_code`
(a *hook's* own exit code, unrelated) — so `PostToolUse.tool_response` cannot
tell us either. The only remaining source is the text inside the tool_result
(`…command not found\nexit:127`), and parsing that is exactly what the card
forbids.

So: the claude-sdk runner keeps forwarding the CLI's `is_error` verbatim
(`main.ts` ~line 789). It is faithful; the CLI is the one that says `false`.

**Revisit when** `BashOutput` grows an exit-status field, or the CLI starts
setting `is_error` on a non-zero exit. Both are one grep on a version bump.
Do not "fix" this by string-matching in the meantime.

## Consequence for TASK-419

TASK-419 fixed the `channel-web` half it owns (a failed step was the same grey
as a success). The walk's headline symptom is fixed **for the aisdk runner
only**. On the claude-sdk runner it persists, and it is upstream of us.
