# TASK-1185 decisions — a bot's @handle is its display name, not Slack's legacy `name`

| Date | Decision | Rationale | Alternatives |
|---|---|---|---|
| 2026-11-21 | `handleFrom` (bots.ts) reads the bot user's display name first: `profile.display_name`, then `profile.real_name`, then top-level `real_name`, and only then the legacy `name`. Each display-form candidate must pass `checkBotName` unchanged (the same rule a bot name passes: `[A-Za-z0-9 ._-]`, ≤35, not reserved by its handle key); `name` keeps HANDLE_RE. An empty or unusable candidate falls through to the next. | MEASURED in the TASK-1174 walk: asking for `fern-walk` gave `users.info` `name` = `fernwalk`, while people type and autocomplete offers `@fern-walk`; after a rename to `fern-two` autocomplete offered `@fern-two` and `name` stayed `fernwalk`. The @-mention follows the manifest's `bot_user.display_name`. INFERRED (not probed): which users.info field carries that display name for an app's bot user — `profile.display_name` may be empty for bots, with `real_name` holding it — so all three are read, in that order. For AX's own apps `display_information.name` and `bot_user.display_name` are both the bot name, so either field gives the same answer. | Store `name` (today's bug). Use the row's `botName` instead of asking Slack (drops "only Slack's word is stored" and the user-mismatch check). Fall back to `botName` when Slack gives no usable display name (would make `unusable-handle` near-unreachable and silently invent a handle Slack never said). |
| 2026-11-21 | Legacy rows (handle = old `name`) are fixed by the re-read after the bot's next rename, NOT by a backfill migration. | Dedicated bots (TASK-1167..1173) are not deployed to prod yet (memory: prod rev90 = phase-2 prereqs only), so legacy rows exist only where phase 2 ran before this fix (the kind walk). A rename (even to the same name) re-reads the handle. | Every-boot targeted UPDATE (`bot_handle = bot_name` where it equals the legacy derivation): rejected as above. Re-read in `status`: rejected, status takes no lock and never writes. |
