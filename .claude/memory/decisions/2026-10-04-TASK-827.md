## 2026-10-04 — TASK-827 shared-key connectors (admin enters one key; anyone may add it)

| Date | Decision | Rationale | Alternatives |
|---|---|---|---|
| 2026-10-04 | **Deleted the attach-time keyMode guard entirely (the former `@ax/agents` connector-guard module, its skill-attachments twin, and the rail's up-front 403) rather than narrowing it.** | The guard was never the security boundary. Who may READ a global `account:` key is decided at read time by `credentials:authorize-global:account` (TASK-697): the reader must resolve a live shared definition whose owner is an admin. Measured: `credential-authz.test.ts` "shared workspace keys are authorized against the definition owner, never the reader role" already allowed a non-admin reader before this card. With the owner decision ("anyone may add it") the guard had nothing left to refuse; a non-admin-owned workspace row (model-approve path, legacy) is attachable but its global key stays unreadable (owner-not-admin). | Narrow the guard to "workspace AND owner not admin" — duplicates the read rule at a second site that could drift; rejected. |
| 2026-10-04 | **A skill that pulls in a shared-key connector is allowed for anyone too.** | Anyone may attach the connector directly, so blocking it via a skill would be an inconsistent half-rule. | Keep the skill-route guard — rejected for the same reason. |
| 2026-10-04 | **Mode switch: REFUSED at `connectors:upsert` (invalid-payload → 400 on both route surfaces), not reset.** | A reset can't purge every person's user-scope key (delete only purges the caller's own), and a leftover personal key would SHADOW the shared one because `credentials:get` walks user → agent → global — a functional bug, not just an orphan. Refusing at the hook covers every writer (admin route, user route, legacy dialog, model-approve). A deleted id may return in the other mode (delete purges its keys). | TASK-758-style reset — can't reach other users' keys; rejected. |
| 2026-10-04 | **Non-admin attaching a shared-key connector whose key is missing → 409 `connector-needs-shared-key` ("ask a workspace admin"); the presence check reads the key AS that person.** | Keeps the TASK-761 "never attach something that can't work" line and lets the vault's read rule decide exactly as at run time. The rail shows "Add" (a non-admin can't read global presence) and surfaces the ask-an-admin line with no Retry, avoiding a recheck→add→409 loop. | Attach anyway and let health say ask-admin — rejected, contradicts TASK-761. |
| 2026-10-04 | **Editor: the shared/per-person choice is offered only when an ADMIN CREATES a non-OAuth MCP connector; an existing connector shows its mode read-only ("create a new connector" to change).** | Matches the server refusal; OAuth stays per-person (no choice). | Editable radio with server-side refusal — a control that always fails; rejected. |
| 2026-10-04 | **Review round 1 (ax-code-reviewer, APPROVE at 7e83e18582bdc1a4b2b05f3ec7ca27e369c7561c): two Minors declined, returned as follow-ups.** (1) AddConnector infers the shared-key 409 from `!isAdmin && keyMode === 'workspace'` instead of the server's `error` code — `HttpError` carries no body code today, so keying on it means plumbing the code through `workspace-api`'s `req`; the two conditions are the same predicate today. (2) A non-admin-OWNED workspace row (model-proposed `keyMode: workspace`, approved by a non-admin) attaches to a 409 "ask a workspace admin", which no admin can fix — a dead end before this card too (403). | Neither is a regression; both are copy/robustness polish outside the card's acceptance. | Fix in this PR — would void the reviewed sha for UX polish. |
