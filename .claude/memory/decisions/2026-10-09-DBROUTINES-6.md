# DB-backed routines Task 6 — approval and execution authority

- Routine pre-call evaluates current deny first and leaves final consumption to the registered host authorization service. Authenticated approval binds ctx.userId to the stored owner, validates the exact routine call/fingerprint, defaults scope to once, and allows agent-routines only for create/update. Current agents:can-manage-routines is a declared optional dependency whose absence denies routine approvals/execution; tool-policy evaluate alone is not an ACL proof because unavailable consent/access can yield hold.
- Decisions owns durable routine authority keyed uniquely by (agentId, real person, requestId), with immutable fingerprint, optional decision linkage, expiry and outcome. Exact active/succeeded retries reuse the same authorization; changed input under that request conflicts; settled failed requests require a new proposal. A shared authorization/exclusive purge fence plus same-plugin retired-agent marker prevents late already-checked calls recreating authority after deletion. No cross-plugin FK, authority cache or decisions-to-routines manifest backedge.
- Authorization mints host ctx.state key decisions:routine-execution with strict {authorizationId,requestId,fingerprint}; settle checks that binding against the durable row and real ctx agent/person. Task7 must create a fresh host invocation context for each concurrent tool call, copying needed metadata but not another call's marker; never expose the marker over IPC. Settle has the fixed failureCode-only input; safe receipt fields default to input and messages are rebuilt through core safeToolMessage, never error.message. Routine replay uses joined executor calls and reconciles already-settled success after response loss.
- Chosen permission scope, expected consent revision, delivery state and release instant are durable. Undo clears unsent intent. Only a released approved eligible intent mints the fresh grant context decisions:routine-consent-grant; remove its marker after awaited delivery. Outage/lost ack stays pending, consent-revision-conflict is terminal, and duplicate delivered:true/enabled:false records revoked permission without restoring it. Both policy consent hooks are manifest-declared.
- Controller-approved expiry ruling: first consent delivery claim must be release-due and precede decision expiry; persist its first consentDeliveryClaimedAt. Only that accepted intent may reconcile idempotently after expiry. Unstarted expired intent grants nothing. Execution checks expiry independently: a recovered permission does not execute an expired call, and the API retains distinct consentGranted versus routineOutcome facts. Exact failed/expired released proposals cannot acquire fresh authority merely because permission subsequently became enabled.
- Routine success receipts require durable succeeded settlement, not consumedAt or approval status. Safe failures and unknown/returned error outputs cannot become successful replays. After a 15-minute stranded flight, recovery retries the same recorded logical request; Task7 must use routines' durable mutation/dispatch receipts and joined effect settlement so a retry never blindly repeats an external fire. Intermediate cutover slice only; real routine executor wiring is Task7.
