| 2026-11-19 | **BLOCKED (Q1): card Decision 1 ("an outsider's turn runs as the AGENT'S OWNER, read at turn time") has no single-user referent.** Dedicated bots exist only for team agents, and a team agent's owner is a TEAM: `Agent.ownerType 'team'`, `ownerId = teamId` (`agents/src/types.ts:44-47`), and the agents plugin says so itself ("a team agent has no single owning person", `agents/src/plugin.ts:1180-1181`). `teamId` can't change (`agents/src/store.ts:376-389`), teams have only `admin`/`member` roles (`teams/src/types.ts:13`, no owner role), and `teams:list-members` needs an admin actor (`teams/src/plugin.ts:283-293`), so channel-slack can't even list a team's admins without a new hook. TASK-1090 (11-12) already rejected "the owner" for exactly this reason (`decisions/2026-11-12-TASK-1090.md` row 2). Planned with the run-as isolated in one router step and one channel-store branch; options A/B/C in the plan. | A turn must run as a real user (memory refuses synthetic owners, `memory/src/owner.ts`; `agents:resolve` has no system actor, `feedback_no_synthetic_actors_through_agents_resolve`). | 2026-11-19 | **BLOCKED (Q2): per-bot configuration-token storage breaks any approver who already gave AX a token.** MEASURED facts combine: one configuration token per person per workspace (TASK-1163 decisions row 3); a rotated-from refresh token dies within minutes to hours (§7); and TASK-1163 check 4: after Vinay revoked his original token, AX's stored refresh token (rotated from it) failed at `rotate` with `invalid_refresh_token` (`deploy/kind/walks/2026-11-19-TASK-1163/REPORT.md` check 4). So to self-approve, a person whose chain AX already holds (the shared install's admin, or anyone approving a second bot) must revoke and generate, which kills the token AX holds for their other app: it can no longer be renamed, re-synced or deleted (agent delete and Disconnect then leave it on the leftover list). | The card's Storage section and design §4 step 3 ("each bot has its own token") are Vinay's decisions; changing them, or knowingly shipping the trap, is his call. | (a) one stored chain per PERSON, shared by every install they created (redesign of `secrets.ts` keying plus a migration of the shared install's token: recommend a prerequisite card); (b) ship per-bot storage as decided, with form copy that says pasting a new token ends the one AX holds for their other Slack apps; (c) something else. |
| 2026-11-19 | **Refuted card claim: `removeAll()` must NOT be scoped to `kind = 'shared'`.** Its only caller is the bootstrap reset (`plugin.ts:511-544`), and `ax admin reset-bootstrap` first wipes every credential, `slack:*` included (`cli/src/commands/admin/reset-bootstrap.ts:162-200`, credentials-store-db) and TRUNCATEs every agent without firing `agents:deleted` (`agents/src/plugin.ts:770-776`). A bot row left behind would point at a deleted agent with no secrets. The reset removes every install (bots too), logs each one's app id with `kind`, and deletes leftover secrets as today. Disconnect is scoped by `current()` alone. | Keeping dead rows serves nothing, and logging the app id is the only way an operator learns the app is still on Slack (its token was wiped). Consistent with Decision 6 (an agent's delete deletes its bot) and Decision 4's intent (Admin › Slack Disconnect leaves bots alone). | Scope `removeAll()` to shared (leaves secretless rows for deleted agents). |

| 2026-11-19 | **Added beyond the card: `POST /settings/slack/:agentId/bot/cancel` for a PENDING bot, any team admin who manages the agent.** Deletes the app with the bot's stored token (same helper as agent delete), else leftover list; removes the row and secrets. | Without it, one failed or cancelled Allow (likely for a team admin who can't install Slack apps) blocks the agent from ever getting a bot, short of deleting the agent: the partial unique index allows one bot per agent, pending included. | 2026-11-19 | **One app lock for every Slack-app create/rename/delete: the existing admin mutex, created once in `plugin.ts` and shared by the admin routes, the bot routes, the bot OAuth callback and the agents-deleted bot removal.** The bot request re-checks manage rights INSIDE the lock before it creates anything. | The card's "that agent's lock" doesn't exist. | 2026-11-19 | **Bot callback checks, in order: signed in (else home), state shape, kind-scoped peek, state user = actor (refused WITHOUT spending), consume, expiry, `access_denied`, then: row is a pending bot, the actor still manages the row's agent, client secret, `oauth.v2.access`, app id match, not enterprise, and the granted team equals the active shared install's team.** | The state binds the user (login-CSRF), the rights re-check stops a demoted admin, and the team check stops a configuration token from another workspace from putting the agent in that workspace. | Fewer checks (the card lists the first group only). |
