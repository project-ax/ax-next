## 2026-10-25 — TASK-944 plan (ax-planner): byte caps on remote response bodies

Plan: `docs/plans/2026-10-25-task-944-remote-body-caps-plan.md`. Numbers marked MEASURED were measured by the planner at 4718946da (darwin, node 24.19.0) against the installed packages, from scratch scripts outside the repo. `node_modules` was only read.

| 2026-10-25 | **Card premise refuted for place 3: in the AI-SDK runner a byte cap alone does not bound memory.** The runner's MCP SDK resolves zod 4.6.7 (upstream semantics, not the TASK-938 patch), so "the zod patch caps the issue list" does not hold there. MEASURED with the runner's SDK copy: `CallToolResultSchema` over a 400 KB body of 200,000 junk content elements keeps 306 MB after GC, and reading the error's `message` builds a 224 MB string (RSS 1.24 GB). A scope's callback does nothing once its operation has settled. | MEASURED with SDK 1.32.1: when the cap errors an `text/event-stream` answer (the SDK server's default framing), the SDK sends the stream error to `onerror` and never rejects the request, so the call waits out its timeout ("MCP error -32001: Request timed out" after 4 s in the probe; 300 s in production). | Date | Decision | Rationale | Alternatives |

| 2026-10-25 | **A declared Content-Length over the cap fails on the first read, not when the response is wrapped.** `capResponseBody` cancels the original body at once and returns a response whose body errors with `ResponseTooLargeError` on its first read; `onOversize` fires on that read. A bodiless response comes back as it is, whatever it declares. | A per-task review found the plan's throw broke the MCP SDK 1.32.1: it treats any error thrown by `fetch` that is not a `TypeError` as fatal. So `discoverAuthorizationServerMetadata`, which reaches a 404 with a declared body over 64 KiB at the first well-known URL, failed the whole sign-in instead of trying the next URL. The resource probe, which reads only headers, failed the same way. Reproduced with the SDK; pinned by two new `oauth-flow` tests that were red before the fix. In the runner, an answer the SDK only cancels (a 202, a redirect hop) no longer aborts its operation. | Throw at wrap time, as the plan said (breaks callers that only read headers). Fire `onOversize` at wrap time (would abort a runner call over a body nobody reads). |
| 2026-10-25 | **The capped response drops a status text that `new Response` would refuse, and a status outside 200–599 cancels the body and throws `RangeError`.** | MEASURED on node 24.19.0 with undici 7.29.0 and 6.29.1: fetch decodes the reason phrase as UTF-8, so Cyrillic, an emoji, or a lone Latin-1 byte (decoded as U+FFFD) makes `new Response` throw a `TypeError`. That would fail every request to that server, and the MCP SDK would take it for a CORS failure. Statuses 600–999 pass through fetch, and `new Response` refuses them; the body is now cancelled before throwing, so the socket is not held. MEASURED: fetch returns a null body for 204, 205, 304 and HEAD even when the server sends one, so the null-body `TypeError` cannot happen. | Copy `statusText` as it is (a TypeError on answers of any size). |
| 2026-10-25 | **The runner's `renderMcpResult` stops joining parts once it passes the 100 KB output cap, and prints `structuredContent` only when it is a plain object.** | MEASURED on the built dist: the loose `ResultSchema` parse of an 8 MiB junk answer costs +40 MB, and the old map, filter and join render added another +32 to +54 MB. With the early stop, the whole path costs +24 to +44 MB, and the output is byte-identical. `JSON.stringify` throws `RangeError` at about 10,000 levels of nesting (about 50 KB of JSON), so that renders as `[structured content omitted]`. That throw existed before this change. | Render everything and then cut (doubles the peak). |
| 2026-10-25 | Tasks 2, 3 and 4 were built at the same time in one worktree, each committing only its own paths. | They touch separate packages, and each depends only on Task 1. Each implementer committed with an explicit pathspec, so nothing another implementer had staged was picked up. | Build them one after another (about 30 minutes slower). |
