# TASK-776 — blob:collect-refs holders + per-owner ledger release (Blob GC 1/5)

| Date | Decision | Rationale | Alternatives |
|------|----------|-----------|--------------|
| 2026-10-04 | The payload type, the holder-side `answerBlobCollectRefs` and the caller-side `readBlobCollectRefsAnswers` live in `@ax/core` (`blob-collect-refs.ts`), not in each plugin | Three holders plus two callers (disk-quota now, blob-gc in TASK-777) need the same untrusted-shape validation; plugins may import only `@ax/core`, and `registerBlobPutFacade` set the precedent for shared blob-hook logic in core | One private copy per plugin (five copies of a fail-closed parser that must agree) |
| 2026-10-04 | The caller judges answers against ITS OWN candidate list, and an answer it cannot read counts as `failed` (or `malformed` with no holder name), never as "no refs" | A transform subscriber can rewrite the payload; reading a malformed answer as empty is the fail-open direction for a release | Trust the returned payload's `candidates` |
| 2026-10-04 | A sha with ANY unattributed ref (`userIds: []`) releases no ledger row for that sha | Card acceptance "Unattributed refs release nothing", design D2 "nothing is released from the ledger for it"; a user whose skill became a global catalog skill stays charged, which errs toward over-charging, never toward data loss | Treat `[]` as "nobody", releasing every owner's row |
| 2026-10-04 | Batches abort independently: a batch whose answers fail releases nothing and stops the pass; earlier batches' releases stand | Each earlier batch was decided on complete answers; the design's sweep says the same ("a sweep that aborts partway leaves every earlier step's work valid"). Holding all decisions until the end would need every stale row in memory | Two-phase: decide all batches, then delete |
| 2026-10-04 | The DELETE re-checks `updated_at < cutoff` (and `kind = 'blob'`) | A re-put between the candidate read and the delete refreshes `updated_at`; that row must not be released | Delete by key only |
| 2026-10-04 | The static guard counts `calls` AND `optionalCalls` entries for `blob:put` | `@ax/ipc-http` (spreading `@ax/ipc-core`'s dispatcher dependencies) declares `blob:put` as an optionalCall; checking only `calls` would let a future optional blob writer skip being a holder. Strictly stronger than the card's wording | `calls` only |
| 2026-10-04 | `graceMs` joins `settings:disk-quota` (default 24 h, bounds 1 h..30 d), editable through the existing admin PUT; no channel-web field | Card: admin-editable setting, no env var. The client sends only changed fields and tolerates extra keys, so the API change is safe; a UI field is not asked for | Separate setting key; a UI field now |
| 2026-10-04 | Branding's holder parses `settings:branding` STRICTLY (corrupt record → `ok: false`) instead of reusing `parseRecord` | `parseRecord` is tolerant for the public GET and turns a corrupt record into "no logos", which a holder would report as "holds nothing" — fail-open | Reuse `parseRecord` |
| 2026-10-04 | The guard's exception is `@ax/ipc-http`, not `@ax/ipc-core` as the card and design said; the design doc is corrected in this PR | Probed `createK8sPlugins`: the blob writers are `@ax/branding`, `@ax/skills`, `@ax/attachments` (calls) and `@ax/ipc-http` (optionalCalls). `@ax/ipc-core` is a library whose dispatcher dependencies `@ax/ipc-http` spreads into its manifest; it is never a plugin in the preset | Keep the card's name (an exception for a plugin that is never loaded, and a guard that would fail on ipc-http) |
| 2026-10-04 | Every reconcile fires `blob:collect-refs` at least once, with `candidates: []` when nothing is stale, and upserts the answering holders into the roster | Otherwise the roster only grows on a pass that already has candidates, so a holder that crashes on the first stale pass was never in it and the pass would not abort | Only fire when there are candidates |
| 2026-10-04 | Only ledger rows whose source is `blob:<64 lowercase hex>` become candidates; other blob rows are never released | `recordBlobStored` accepts any sha string up to 128 chars and tests insert `blob:seed`; holders reject a candidate list WHOLE on one bad entry, so one odd row would abort every pass forever | Pass every row through |
| 2026-10-04 | SECURITY FIX (flagged by a background commit review as "quota-bypass in disk-quota/service.ts"): a stale charge is released only if (a) no holder holds the sha unattributed, (b) no holder lists that owner, and (c) either a listed holder-user is still charged for the sha (any age), or nobody holds it and `blob:stat` answers exactly `{found:false}` (optionalCalls; absent/throwing stat keeps the charge) | Nothing frees blob BYTES until TASK-778, so releasing the last charge for bytes that still exist let a person upload, delete, wait out grace and repeat past their limit; dedup let B reference A's bytes uncharged. The invariant: the pass never leaves stored bytes charged to nobody. Once TASK-778 purges, `blob:stat` says found:false and the charge goes | D6 as written (release whenever no answer lists the owner) |
