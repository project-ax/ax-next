| 2026-11-21 | **Planner: premise holds.** `connectors:call-tool` returns only `{outcome[, reason]}` (mcp-client `types.ts:201-233`). It reads the reply through `client.request` with a passthrough `{isError}` view and drops the content (`call-server-tool.ts:77-78, 205-213`). Every hook the spec names exists with the signatures used in the plan: `auth:find-user-by-email {email} → {userId}\|null` (auth-better `types.ts:77-116`); `agents:resolve {agentId,userId} → {agent}`; `agents:can-manage-connectors {actor:{userId,isAdmin},agentId} → {allowed}`; `agents:list-for-user {userId,teamIds?} → {agents}` (personal agents only when `teamIds` is empty, `agents/src/scope.ts:29-50`); `tool-policy:evaluate {call:{name,input},agentId} → {verdict: allow\|hold\|deny, …}`. 15 tasks: 10 sensitive, 4 integration, 1 mechanical. | Read in code, not taken from the card. | Return blocked (nothing here needs the owner before planning). |
| 2026-11-21 | **The bridge gets its own `node:http` listener** (default 9092, bound on `AX_HTTP_HOST`, own container port and Service port, never on the Ingress; a NetworkPolicy rule admits the host namespace plus `appsBridge.allowFrom`). Its cookie routes (settings, approve) stay on `@ax/http-server`. | The spec asks for a listener the operator can keep off the public ingress. `@ax/http-server` is one listener and can't load twice, and the chart's Ingress sends all of `/` on 9090 to it with no prefix exclusion (`templates/host/ingress.yaml:30-46`). Its own listener also lets the bridge authenticate from headers BEFORE reading a body (http-server buffers the whole body first). Precedent: artifacts' content origin (`attachments/src/artifacts/content-origin.ts`, decisions shard ARTIFACTS-20261105). | A `bypassCsrf` route on 9090 (can't be kept off the Ingress; reads up to the body cap before auth). `X-Requested-With: ax-admin` from the platform (same, plus couples the platform to an AX-internal header). A second http-server (impossible). |
| 2026-11-21 | **The wire contract lives in a new zod-only package, `@ax/apps-bridge-contract`.** `wire.ts` holds the external v1 shapes and imports only `zod`, so the platform can vendor the one file. `settings.ts` holds the AX-internal settings and approve shapes that `@ax/apps-bridge` and channel-web both parse. It joins the eslint allow-list. | `@ax/routines-contract` is the precedent for one schema used by a plugin's routes and the browser (with a browser-bundle test). CLAUDE.md's `@ax/ipc-protocol` rule is scoped to IPC actions, and that package is the runner↔host boundary with a Node-only entry. Keeping the schemas inside the plugin would make the outside consumer depend on kysely, jose and the hook bus. | `@ax/ipc-protocol` (wrong boundary). Inside `@ax/apps-bridge` (heavy for an outside consumer; channel-web can't import a plugin). Client-side copies in channel-web (two sources for one shape). |
| 2026-11-21 | **Factor, don't copy: `createConnectorCallHandler` (steps 1–9 + the budget, catch-all and one log line) in `connector-call.ts`, and `sendOneCall` in the transport.** `connectors:call-tool` and `connectors:call-tool-result` differ only in the log event name and how the success reply is read. The two existing suites are the regression net and must stay byte-unchanged in Task 1, and additions-only after. | The spec says factor the steps out. TASK-1046 took four review rounds to get these checks and the outcome classification right (its decisions shard), so one copy of them is the point. | Copy `call-tool.ts` into a second file (two drifting copies of a security check). A flag on `connectors:call-tool` (changes a hook whose output is deliberately text-free). |
| 2026-11-21 | **Content cap = the transport's existing per-reply cap, `CALL_LIMITS.maxResponseBytes` (2 MiB). An oversize reply stays `unknown/interrupted`. No second cap.** Content is read through a local schema, `z.array(z.object({type: z.string().min(1).max(64)}).passthrough())`. An absent `content` is `[]`, and an unreadable one is `unknown/interrupted`. The reply's own array is returned, never zod's copy. `isError` stays `failed/tool-error` with no content. | The spec says "content cap inherited from the connector call limits". Content is a subset of the reply, so a second cap could only refuse a reply the transport already accepted, and it would need a new outcome code. `unknown` is the honest word for "it ran and we can't hand you the result". | A smaller content cap (needs a new reason code, contract churn). `CallToolResultSchema` / `callTool()` (validates and can compile server-supplied schemas: the thing TASK-1046 avoided). Returning `structuredContent` (spec says content blocks; MCP servers mirror it in a text block). |
| 2026-11-21 | **JWT verification: `jose` 6.2.8, exact pin, direct dependency of `@ax/apps-bridge`.** Algorithms: the asymmetric set `RS*`, `PS*`, `ES*` and `EdDSA` only. Clock tolerance 30 s. Caller: exact `iss`, `aud` and `sub`, and `exp` required. Viewer: `iss`, `aud`, `maxTokenAge` (default 600 s, 30–3600), `exp`, `iat` and `email` required, and an `email_verified` claim, if present, must be true. `jwksUrl` must be https, or http on loopback only. A JWKS fetch failure is `keys-unavailable` → `503 unavailable`, never `401`. | `jose@6.2.8` is already the only resolved version (via better-auth and the MCP SDK), has zero dependencies and no install script. So the lockfile gains an importer entry, not a package. No AX code verifies a JWKS-signed JWT today (mcp-oauth only decodes, `identity.ts:67-75`), and a hand-rolled verifier is how alg confusion ships. Loopback http lets the canary and composition tests fetch a real JWKS with no seam. | `node:crypto` by hand (alg confusion, kid handling, claim rules to get right ourselves). `openid-client` (pulled by @kubernetes/client-node; far more surface). A key-resolver test seam instead of loopback http (keeps the JWKS fetch path untested). |
| 2026-11-21 | **Two refusal codes added to the closed set: `invalid_request` (400) and `unavailable` (503, `Retry-After: 5`). `deny` maps to `tool_not_allowed`.** Statuses are pinned in `REFUSAL_STATUS`. `rate_limited` is 429 with `Retry-After` 60, or 1 for the in-flight cap. The spec's contract section is updated to match (Task 14). | The spec's table has no code for a malformed body or for AX's own transient faults (JWKS or database down), and none for a tool the agent's owner turned off. Mapping a pre-auth JWKS outage to `401` would tell the platform its token is bad. | `200 {outcome:'failed', reason:'unavailable'}` for AX's own faults (an outcome for a call that was never attempted, and for unauthenticated callers too). A new `tool_denied` code (one more for clients to handle, same remedy). |
| 2026-11-21 | **Link and grant rights: `agents:can-manage-connectors` asked with `actor.isAdmin: false`, always.** That means a personal agent's owner, or an admin of a team agent's team. Builder calls run as `(linker, agent)`, re-checked per call only through `agents:resolve` (a linker who left the team → `agent_unavailable`). No per-call re-check of manage rights: other managers see and can unlink every link. | Lending an agent's sign-in to an outside app is the agent owners' call. TASK-813's rule is "whose account a team acts as is not a workspace admin's decision", and channel-slack asks as a non-admin too. With `isAdmin: true` a workspace admin could link any agent they can reach. Links are agent configuration, like attachments, which also outlive a demotion. | Pass the real admin flag (the spec's hook as is, but wider than TASK-813). `agents:can-set-shared-credential` (refuses every personal agent). Re-check manage rights on every call (an app dies when its linker is demoted, while other admins already hold the remedy). |
| 2026-11-21 | **Viewer mode borrows only the viewer's personal agents** (`agents:list-for-user` with no team ids; at call time also `ownerType === 'user' && ownerId === viewer`). | "One of that person's own agents". A team agent's sign-in is the team's account, so a call through it isn't "as the viewer". | Any agent the viewer can reach (would act as a team account in "viewer's access" mode). |
| 2026-11-21 | **Each viewer approval stores a snapshot of the grant's tool keys. A tool outside it answers `viewer_approval_required`.** Grant upserts never delete approvals. Removing a grant or unlinking cascades them. | Without the snapshot, a builder adding a write tool to a viewer-mode grant would ride consent people gave for a read-only list. With it, previously approved tools keep working and only the new tool asks again. A removed tool is outside the grant, so it is `tool_not_allowed`. | Delete every approval on any grant edit (forces re-consent for narrowing edits too). No snapshot (consent widening). |
| 2026-11-21 | **Grants store canonical tool keys (`mcp.<namespace>.<tool>`); the wire speaks tool names.** A save validates each key's namespace against the connector's `toolNamespaces` and needs names unique within a grant. At call time the bridge maps `tool` to the grant's one matching key. | The key is what `tool-policy:evaluate` and `connectors:call-tool-result` take, and it disambiguates a connector with two MCP servers. Every connector is shared since SIGNINS-9 and credential reads need a sole live id, so the key is the same for builder and viewer. A server rename leaves stale keys that fail closed (`not-connected`); the Apps section marks them "no longer offered". | Store names and resolve keys per call through `connectors:describe-tools` (a possible network listing on every call). Subscribe to `connectors:tool-namespaces-changed` to move keys (deferred: fails closed today; listed as a follow-up). |
| 2026-11-21 | **Storage: Postgres only.** Three tables, `apps_bridge_v1_links (platform_id, app_id)`, `apps_bridge_v1_grants (…, connector_id)` and `apps_bridge_v1_viewer_approvals (viewer_user_id, platform_id, app_id, connector_id)`, with FKs that cascade inside the plugin (no cross-plugin FK). `createLink` is `INSERT … ON CONFLICT DO NOTHING` (first link wins). `agents:deleted` purges links to the agent and approvals that borrow it. `connectors:deleted` with `idStillLive: false` purges that connector's grants. `apps_bridge_v1_` joins the `no-bare-tenant-tables` prefixes. | Every plugin that owns tables is Postgres-only, and the CLI preset (the only sqlite one) has no Postgres, http-server, agents or connectors. `agent-keyed-tables-are-cleaned.test.js` requires the agent cleanup. A grant for a deleted connector id must not quietly come back if that id is reused (TASK-755's "don't hand stored choices to a different service"). | sqlite support (no preset could load it). A `connectors:deleted` no-op (dangling grants revive on id reuse). |
| 2026-11-21 | **Limits: 120 calls/min per app, 600/min per platform, 32 calls in flight per platform. Sliding 60 s windows, 10,000 tracked keys, in memory.** | The spec allows in-memory single-replica limits, and the chart pins the host to one replica (`ax-next.validateHostReplicas`). The in-flight cap bounds host memory, since each call can hold a 2 MiB reply for up to 45 s. The numbers are a builder's estimate for internal apps (a page view calls 1–3 tools). | No in-flight cap (600/min × 45 s is up to 450 concurrent replies on the shared host). A database-backed limiter (multi-replica isn't allowed yet). |
| 2026-11-21 | **App and platform ids are DNS labels (`^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?$`). The approve link is path-only: `/apps/approve/<platformId>/<appId>/<connectorId>`. A strict, exact-segment parser keeps the allowlist from becoming an open redirect. | `?app=&connector=` (lost at sign-in). A free-form callback (open redirect). |
