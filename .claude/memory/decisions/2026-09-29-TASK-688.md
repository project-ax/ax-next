## 2026-09-29 — TASK-688 Stop cancels the in-flight turn (both runners)

| Date | Decision | Rationale | Alternatives |
|---|---|---|---|
| 2026-09-29 | **A NEW inbox entry `{type:'interrupt'}`, not a reuse of `cancel`.** The card body said "queue `cancel`"; that was a hypothesis and reading refutes it. `cancel` means "stop pulling messages and EXIT the runner" (`nextMessage()` -> null -> loop drains -> `event.chat-end` complete -> exit 0). The claude-sdk loop pulls ahead, so a mid-turn `cancel` today closes the SDK's input stream but never stops the in-flight model call or tool (the card's 45 s marker file still appears); the aisdk loop does not even read the inbox mid-turn. Overloading `cancel` would also make the idle reaper's cancel (queued into a warm session, racing a new message — see the orchestrator's "narrow race" comment) abort a running turn. | A distinct entry keeps "end the session" and "stop this turn, stay warm" from being confusable at the one place they race. Costs one arm in a closed wire union + two session backends (session-postgres has no CHECK on `type`, so no migration). | Reuse `cancel` and let the runner decide by whether a turn is running (rejected: the reaper race turns a graceful shutdown into a mid-turn abort); a separate IPC action `session.poll-interrupt` (rejected: a second long-poll to keep ordered against the first). |
| 2026-09-29 | **Host hook `agent:interrupt {conversationId,userId} -> {interrupted:boolean}` registered by `@ax/chat-orchestrator`; channel-web calls it from `POST /api/chat/conversations/:id/interrupt`.** Precedent: `agent:apply-capability-grant` (same payload family, same "resolve the conversation's live session" helper). The route does the ACL (`conversations:get` with the authenticated userId; foreign and unknown both 404); the hook re-checks with the same userId. | channel-web should not queue raw inbox entries (`session:queue-work` is the orchestrator's vocabulary), and only the orchestrator knows the reqId-in-flight and cold-spawn state. | channel-web calling `session:queue-work` directly (rejected: leaks the inbox vocabulary into a channel, no cold-spawn handling); `session:terminate` (rejected: kills the warm sandbox and errors the turn instead of stopping it). |
| 2026-09-29 | **Stop during a COLD SPAWN is deferred, not dropped.** `active_req_id` is bound at POST time, so the Stop button can be clicked for a full pod-spawn (10+ s) before any session exists. The orchestrator keeps an in-process `pending-message` set (reqId whose user message is not yet queued) and a `stopRequested` set; after `session:queue-work` of the user message it queues `interrupt` behind it if the reqId is in `stopRequested`. The runner then reads `[user-message, interrupt]`, starts the turn, and aborts it at once. | Without it the most likely first Stop click ("oops, wrong message" while the agent is still 'Getting set up') does nothing and the turn runs. Same single-replica in-memory posture as `waitersByReqId`. | Skip queueing the message entirely (rejected: needs a synthetic turn-end/chat-end for a turn that never ran). |
| 2026-09-29 | **Runner shell owns ONE inbox reader (`pump`) and routes `interrupt` to loop-registered handlers (`ctx.onInterrupt`); loops never see the entry.** aisdk does not poll the inbox during a turn, so the shell keeps a read outstanding while a turn is active; entries other than `interrupt` are buffered and handed to `nextMessage()` in order. An `interrupt` with no turn active is a no-op (also the idle-runner case); an `interrupt` that arrives before the loop registered its handler is latched. | Two concurrent `inbox.next()` calls share a cursor and would both deliver the same entry, so the only safe shape is a single reader. `idle-timeout` produced by a watcher-started read (a long turn, nobody waiting) is discarded and re-armed; a waiter only honours a read that STARTED after it began waiting, so a 14-min turn does not shorten the idle floor. | Make aisdk pull ahead like claude-sdk (rejected: re-materialises uploads mid-turn and inherits the >15-min-turn idle-exit bug). |
| 2026-09-29 | **claude-sdk: `Query.interrupt()`; nothing else.** MEASURED-BY-PROBE 2026-09-29, real `claude` binary 0.2.119 (darwin-arm64) against a scripted local Anthropic-compatible server, no key needed: `interrupt()` during a `sleep 30 && touch` Bash call kills the command (`Exit code 137`, tool_result `is_error` "[Request interrupted by user for tool use]"), yields `result{subtype:'error_during_execution', terminal_reason:'aborted_tools'}`, and the marker file never appears in 36 s. During text streaming it keeps the partial assistant text and yields `terminal_reason:'aborted_streaming'`. The same `query()` accepts the next user message afterwards (2nd model call carried the partial + `[Request interrupted by user]`). The loop's existing `result` branch already calls `endTurn`, so partial text and the stopped tool_result land in the durable turn with no new code. | Probe scripts live only in the session scratchpad; the unit tests fake `query()`. | `Options.abortController` (rejected: aborting it tears the whole query down, not the turn). |
| 2026-09-29 | **aisdk: pass a per-turn `AbortController` signal to `agent.stream`; on abort KEEP the partial assistant text (transcript + durable turn), DROP unfinished tool calls, append the completed steps as usual.** Bash already kills its process group on the tool's `abortSignal`; host tools (30 s IPC ceiling, no cancellation token) and sandbox catalog tools ignore the signal — the turn still ends immediately because the loop stops consuming and the stream is aborted, but a host tool already dispatched runs to completion. | What the user saw streaming must not vanish when the durable thread is re-read after Stop. An unfinished tool call without a result would make the next provider call invalid, so it is dropped rather than half-kept. | Discard partial text (rejected: text vanishes on `load()`); synthesise a tool_result "interrupted" (kept as a follow-up if the probe shows the model re-runs the dropped call). |
| 2026-09-29 | **The "Stopped" notice is SPA-local (set when Stop was clicked and the route answered `interrupted:true`); no persisted marker, no new turn-end reason.** After a reload the partial reply reads as a finished reply. | A persisted marker needs a new display-event kind in `@ax/conversations`, a `ThreadMessage` kind and a turn-end reason, all of which sit on the redisplay SoT; not needed to stop the work. Returned as a follow-up. | `reason:'interrupted'` on `event.turn-end` + SSE `stopped` flag (rejected for this card: 5 more touch points for a nicety). |
| 2026-09-29 | **aisdk gives a stopped turn a 1.5 s grace, then stops waiting for `fullStream`.** Test-measured: with a 4 s host tool the stream did not close until the tool returned (`ai@7` awaits dispatched tools). The loop races `parts.next()` against a timer armed at abort time and abandons the stream; the turn is built from `onStepEnd`-collected steps, never `await result.steps`. | The person must not wait up to the 30 s IPC ceiling for work the runner cannot take back. A host tool already dispatched still runs on the host — documented, not fixable without a cancellation token on `tool:execute:*`. | Wait for the stream (rejected: 30 s "Stopping…"); race `result.steps` (rejected: rejects with zero finished steps). |
| 2026-09-29 | **The hand probe of the real `claude` binary is kept as a committed e2e test** (`interrupt-real-sdk.e2e.test.ts`, ~4 s, skips when the platform binary is absent). | The claude-sdk loop's whole implementation is "call `Query.interrupt()`"; the unit tests fake `query()` and so cannot notice the pinned SDK changing what it does. Stable over 8 consecutive runs and 3 full-suite runs after replacing a fixed sleep with a server-side progress counter. | Leave it as a scratch script (rejected: the claim would rot). |
| 2026-09-29 | **The shared kind cluster was not touched.** It had a sandbox pod 6 minutes old and a host pod 62 minutes old (someone else's walk), and `kubectl`'s default context here is the production GKE cluster. The card's `sleep 45` probe is covered at the runner level (aisdk: real Bash + scripted model; claude-sdk: real binary + scripted server) and a cluster walk is added to `deploy/MANUAL-ACCEPTANCE.md` for the serialized walk lane. | Redeploying a host image under another session's feet, or pointing kubectl at the wrong context, is the failure to avoid; the orchestrator's brief said not to deploy anything. | Rebuild the image and `helm upgrade` kind (rejected: disrupts a live session). |
| 2026-09-29 | **`compactor.turn` (rung-3 summarizer, up to 120 s) is not interruptible.** A Stop pressed during it is latched and takes effect the moment `agent.stream` starts (aborted signal -> immediate abort). | Rare (only when the ladder decides to summarize) and the person sees "Thinking…" not a reply; threading a per-turn signal into a once-built closure is a separate change. Returned as a follow-up. | Pass `stop.signal` through `summarizeText` now (deferred). |
| 2026-09-29 | **Known, accepted edges (reviewer nits, no code change):** (1) a Stop landing in the turn-end commit window (after the stream, before `endTurn` hands over) is consumed with no effect but the route already answered `interrupted:true`, so the note "You stopped this reply" can sit under a reply that finished; (2) a Stop for an approval-CONTINUATION turn that lands between the approve and the `decision-resolved` queue can be queued ahead of it and is dropped by the idle runner (Stop no-ops, never stops the wrong turn); (3) `interrupt` rows are not backward-readable: rolling a host back to a pre-TASK-688 build while a session holds an unread `interrupt` row makes that old `fetchEntry` throw `corrupt-inbox-row` for that session — drain (or terminate) sessions before a rollback. | All three are narrow races/edges with a benign failure mode and were reviewed as such (ax-code-reviewer, APPROVE at bd9e5a38). Per-reqId targeting was cut deliberately (plan, YAGNI). | Thread a reqId through the entry to make (2) exact (deferred). |
