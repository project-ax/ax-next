|---|---|---|---|
| 2026-09-19 | **Built on the spike's finding that TASK-423 needed no FTS/vector decision at all.** The card was un-gated from Backlog on that basis (PR #615). | `runFactsContract` — the whole of what a second backend must satisfy — has no free-text and no dense search; `recall` *rejects* `query` with `invalid-payload`. The gating premise stopped holding when TASK-421 cut the channels, and asking postgres to match a channel that does not exist on the sqlite side is designing against `dem-memory` rather than against the contract. The sparse/dense decision went to TASK-457, where there will be a sqlite implementation to match. | Decide `tsvector`/pgvector here anyway — REJECTED: TASK-457 may change the shape when it builds the channels for real, and this card would have shipped a guess. |
| 2026-09-19 | **`valid_start`/`valid_end` are `TEXT`, not `timestamptz`**, sentinel included. | Every ordering comparison in the closure rules runs in JavaScript inside `settleArrival`; the SQL only ever compares the sentinel by equality. The rules are collation-immune by construction, so the usual "postgres TEXT ordering is collation-dependent" worry is not load-bearing here — I raised it myself early and it was wrong. `timestamptz` costs a re-derived `until` predicate (`rowToFactRecord` compares `valid_end !== INFINITY_SENTINEL` as a *string*; get it wrong and every active row reports `until`) and a byte-exact `.000Z` round-trip, for a benefit the contract cannot currently use. Revisit trigger lives in a code comment, not only in the docs. | `timestamptz` — REJECTED for now; correct the day a card pushes ordering or range comparison down into SQL, which TASK-457's temporal channel plausibly will. |
| 2026-09-19 | **The plugin borrows the Kysely via `database:get-instance` at `init` and has NO `shutdown()`.** The `store-unavailable` contract cases are satisfied in the test *factory*, by a per-test `@ax/database-postgres` instance whose teardown really destroys the pool. | The pool belongs to `@ax/database-postgres`; `memory-strata-index-postgres` deliberately has no `shutdown()` for that reason and this must match. The contract nonetheless tears the store down mid-test and requires all five hooks to reject rather than return empty — that case IS design §4.4's rule that a failed store is never a quiet empty answer, so it must not be weakened for postgres. The spike framed this as needing a new factory shape; it does not — strata-postgres's factory **already** creates a per-test db plugin and shuts it down. Only two things are new: the facts contract actually calls hooks *after* that teardown, and teardown runs twice for those cases so it must be idempotent. | (a) Give the plugin a `shutdown()` — REJECTED: it would destroy a pool it does not own, breaking every other plugin sharing it. (b) Relax the contract for postgres — REJECTED: it is the one case that proves a failed store is not an empty table. |
| 2026-09-19 | **Wire into `presets/k8s` UNCONDITIONALLY, not behind `config.hostLlmTools`.** | That gate exists because the strata indexer is part of the host-LLM-tools bundle and needs an `ANTHROPIC_API_KEY`. A facts engine has no LLM dependency, and the CLI pushes its sqlite twin unconditionally — gating it would leave `memory:facts:*` unreachable on any deployment without an API key, which is the exact window this card exists to close. | Copy the `hostLlmTools` gate because it is the nearest postgres precedent — REJECTED: the precedent to copy is the *plumbing* (borrowed Kysely, no shutdown), not the gate. |
| 2026-09-19 | **Tenancy is load-bearing in a new way here, and the pinned derivation vectors are what prove it.** | This is the first time facts data lands in the **shared production postgres** rather than a per-deployment sqlite file, so `agentScopeKey` stops being defence-in-depth and becomes the only thing separating agents' rows in one table. The contract's isolation cases cannot catch derivation drift — they vary `userId` and `agentId` together, so they pass under any partition containing either (the TASK-257 lesson). Only the pinned literal digests catch it, and this package carries its own copy under Invariant 2. | Rely on the contract's isolation cases — REJECTED on the measured TASK-257 finding. |
| 2026-09-19 | **Memory rows for this card go to a SHARD (`.claude/memory/decisions/2026-09-19-TASK-423.md`), not `decisions.md`.** | TASK-415 (#623, merged today) froze the five root files as archives and added `scripts/memory-append-check.sh` + a CI job enforcing R1 (no line under `.claude/memory/` may be deleted) and R2 (root archives untouched). Appending to `decisions.md` the way every earlier card in this session did would now fail CI. Caught by reading the CLAUDE.md diff before writing, not by tripping the guard. | Append to `decisions.md` out of habit — would have failed CI and cost a rebase plus a fresh ~10-minute run, which is exactly what TASK-415 was filed to remove. |
| 2026-09-19 | **Task A found a real contract leak and fixed it IN THE CONTRACT: the two "colliding group key" cases used a literal U+0000, which postgres `TEXT` cannot store.** The fixture character is now U+0001 (`COLLIDING_CHAR` in `runFactsContract`). | `runFactsContract` is supposed to be storage-agnostic (Invariant 1). Those two cases hid a NUL inside `about`/`slot` to prove the group map is keyed structurally rather than by a NUL join (the TASK-448 bug). sqlite `TEXT` stores an embedded NUL happily; postgres rejects the parameter server-side with SQLSTATE 22021 (`invalid byte sequence for encoding "UTF8": 0x00`), so on the postgres backend both cases died at the INSERT, three statements before the map was ever consulted. The contract was demanding a capability only one backend has — invisible until a second backend existed, which is precisely what the two-backend test is for. U+0001 keeps the property (an in-band delimiter is not injective; only `JSON.stringify([about, slot])` is) and is storable anywhere. | (a) Skip the cases on postgres via a factory capability flag — REJECTED: an escape hatch that lets a backend opt out of the contract, and it would have dropped the shared case count from 91 to 89. (b) Reject NUL up front with `invalid-payload` on postgres — REJECTED: the two backends would then disagree about a payload the contract calls valid, a worse divergence than the one it replaces. |
| 2026-09-19 | **Knowingly given up with that change: the contract no longer regresses the NUL join *specifically*.** Documented at `COLLIDING_CHAR`. | It cannot be kept: constructing a collision for a delimiter-`d` key requires `d` inside a field, and no field on postgres can hold U+0000. That also means a NUL-joined key would in fact be injective on postgres — the original bug is reachable only on sqlite. The general claim ("any in-band delimiter is unsafe") is the one both backends can be held to, and it is what both implementations' comments actually assert. | Keep the NUL fixture and add a postgres-only skip — REJECTED, see above. |
| 2026-09-19 | **A NUL-bearing `about`/`value`/`relation`/`slot` is the one input where the two backends genuinely differ at runtime**, and it surfaces as `store-unavailable` on postgres. Left as-is, documented on `inStore`. | `about` is free text carrying model output, so this is reachable in production, not theoretical. It is the same collapse `inStore` already documents for any constraint violation ("the store is fine, your row isn't"), so the labelling is consistent with the design rather than a new wart. Fixing it properly is a decision for BOTH engines — reject at the shared write door, or escape on the way in — not a local patch in the postgres copy. | Silently strip NULs — REJECTED: that is data corruption dressed as robustness. |
| 2026-09-19 | **`insertWithSlotClosure`/`resettleSlotGroups` take a `Transaction` in the TYPE and never open one.** | The sqlite twin opens an inner `driver.transaction(...)` that better-sqlite3 degrades to a SAVEPOINT, which is free and buys atomicity for a caller outside a batch. Kysely has no implicit nesting — `trx.transaction().execute()` would `BEGIN` on a connection already in a transaction. Requiring the handle in the type is the honest version of the same guarantee: the function is unreachable without a transaction. | Emulate with explicit savepoints — REJECTED: `record` and `reindex` already own the only transactions, so the savepoint would protect nothing. |
| 2026-09-19 | **Trap fixes, all three, and how each is pinned.** (1) `supersede`'s retraction and `reindex`'s slot resolution both use `RETURNING`, never a row count — Kysely's `numUpdatedRows` is a **bigint**, so `=== 0` against a number is always false. (2) `pendingStatus` counts with `count(*)::int` so node-postgres parses `int4` to a JS number; uncast, `count(*)` is a bigint rendered as the STRING `"0"`, which is truthy and `> 0`, inverting `degraded` forever. (3) `rebuildBatch` fetches the `closed_by` inverse for the WHOLE batch in one `IN (...)` read instead of the sqlite twin's per-row query inside `.map()`. | Each would pass a careless test: (1) is partly caught by the contract's foreign-tenant case, (2) only incidentally by a `toEqual` on the value, (3) not at all. `src/__tests__/postgres-edges.test.ts` pins all three — a `typeof` assertion for (2), a `resolved: 0` for ids that resolve nothing for (1), and a Kysely `log`-based query count (2 SELECTs for a 6-row replay, vs 1+N for the naive shape) for (3). | — |
| 2026-09-19 | **The destroyed-Kysely error is a plain `Error('driver has already been destroyed')` from Kysely's own `RuntimeDriver`** — verified, not assumed, and pinned in `postgres-edges.test.ts`. | It had to be checked because `inStore` re-throws a `PluginError` UNTOUCHED: if Kysely had thrown one, every store outage would have surfaced under that error's code instead of `store-unavailable`, and the §4.4 cases would have failed for a reason that looks like a plugin bug. Note `RuntimeDriver.destroy()` is a no-op on a driver that was never initialised, so the probe only works after a real query. | — |
| 2026-09-19 | **`teardown()` in the postgres contract factory is idempotent, and the reset is a `TRUNCATE` at SETUP.** | The reset cannot live in teardown: the store-unavailable cases consume the teardown themselves (they disarm the shared `afterEach` and call it mid-test), so a teardown-time reset simply would not run for them and their rows would leak into the next test. A long-lived `adminDb`, separate from the per-test pool, is what can still truncate after that pool is destroyed. Idempotency is belt-and-braces — the contract currently disarms before calling, but its own comment says "not every backend promises that is safe". | Reset at teardown like the strata-postgres factory does — REJECTED: strata's contract never destroys the store mid-test, so the pattern does not transfer. |
| 2026-09-19 | **Follow-up: the U+0001 contract fixture change unpinned the ORIGINAL NUL-join bug (TASK-448) — re-pinned SQLITE-LOCALLY, not in the contract.** Verified before touching code: with the U+0000 fixture the NUL-join key collides (as designed); with U+0001 it does **not** — a straight revert of `closure.ts`/`plugin.ts`'s `JSON.stringify([about, slot])` back to a NUL-joined template string would now pass `runFactsContract` clean. Added `packages/memory-facts-sqlite/src/__tests__/nul-key-collision.test.ts` — two cases (`supersede`, `reindex`), constructing the plugin directly over a real `HookBus` (batch-atomicity.test.ts's pattern), using a literal `'\u0000'` escape (never a raw byte). | It cannot be pinned portably: a delimiter collision needs the delimiter INSIDE a field, and no postgres `TEXT` field can hold U+0000, so the NUL case is only reachable on sqlite. Package-local is therefore the correct home, not a contract regression. | Leave it unpinned since "the general claim survives" — REJECTED: the general claim (U+0001) and the specific NUL-join bug are different assertions, and only the specific one is what TASK-448 actually fixed; leaving it unpinned meant one line's revert in either file would silently un-fix a shipped bug. |
| 2026-09-19 | **Mutation-checked both sites, one at a time**: reverting `closure.ts`'s group key alone failed exactly the new `supersede` case (1 of 111, reindex case still green); reverting `plugin.ts`'s `reindex` group key alone failed exactly the new `reindex` case (1 of 111, supersede case still green). | 2026-09-19 | **sqlite `recall`'s ORDER BY gets `, id DESC` to match postgres's tiebreak (`valid_start DESC, id DESC`).** No contract case observes this — could not construct one that reliably fails without it, and said so rather than shipping a test that passes either way. | Postgres needed the tiebreak because ties on `valid_start` under a `LIMIT` are a nondeterministic result SET on a backend with no row-order promise; sqlite makes the identical promise gap in principle (its current stability is an implementation detail — rowid order — not a guarantee), so leaving it un-tiebroken is exactly the kind of divergence "two backends behind one contract" must not have, even though nothing today can see it. | Add a test using deliberately-colliding `valid_start` values and assert byte-identical output across repeated runs — REJECTED: on better-sqlite3 (single-threaded, synchronous, insertion-ordered rowid scan) there is no way to make the untiebroken query actually flip order within a test process, so the test would pass whether or not the tiebreak exists — worthless per the card's own bar. |
| 2026-09-19 | **The unconditional `presets/k8s` push had to be added to BOTH chat-path canaries' `PLUGINS_TO_DROP`** (`acceptance.test.ts`, `multi-tenant-acceptance.test.ts`). | Those canaries import the real preset list and then DROP the postgres trio, substituting storage-sqlite.
