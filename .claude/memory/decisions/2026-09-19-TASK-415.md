## 2026-09-19 — TASK-415 `.claude/memory/` stops being a serialization point

- `2026-09-19` (TASK-415) — **`merge=union` was REFUTED by measurement, not rejected on taste.** The card offered it as the cheap option and the reasoning behind it is sound as far as it goes: every collision was "both sides appended at EOF", which is the one case the built-in union driver is documented to handle, and it needs no config in any clone. Run against the real 3189-line `decisions.md` with two concurrent EOF appends and `git rebase` (git 2.52.0), four shapes: unique prose, two table entries, a shared closing line, and both sides ending on a blank. **All four merged without a conflict and all four LOST LINES** — one line where the appends shared only a leading blank, two where they shared a closing line, which left a multi-line row ending on `…before it closes with` and the next `##` heading welded straight on. Union is line-wise: git's diff matches whatever the two blocks share at their edges as ordinary context and emits it once. *Alternatives:* union plus a guard — REJECTED, see the next row.
- `2026-09-19` (TASK-415) — **The disqualifier was not that union loses lines, it is that `--numstat` reports `0` deletions while it does.** All four shapes measured a deletions column of 0. The loss happens *during* the merge, so relative to the base nothing was ever deleted. The card was explicit that the derive-and-assert property "is what caught the real risk here and must not be traded away" — a fix that blinds the sharpest check we have against the risk is not a fix, however cheap. Pinned executable in `scripts/__tests__/memory-shards.test.js` (`union merge SILENTLY DROPS lines`) so the next person to reason their way to union from the same correct premises meets the measurement instead.
- `2026-09-19` (TASK-415) — **Per-task shard files: `.claude/memory/<kind>/<YYYY-MM-DD>-<TASK-ID>.md`.** Two branches write two different paths, so git takes both and there is no merge at all. That is strictly stronger than resolving the merge well: nothing to resolve, nothing to re-resolve on the next rebase, and — the card's second hazard — nothing for `git rerere` to record or to replay against different `main` content. The five root `.md` files stay exactly where they are as frozen archives: still read, no longer appended to. *Alternatives:* per-DATE files (rejected — two branches on the same day still collide, which is the normal case under parallel drain); leave it alone and eat the rebases (rejected — 8 collisions/day × rebase + force-push + ~10 min CI is a substantial share of a run's wall clock, and the shard layout costs one command).
- `2026-09-19` (TASK-415) — **The guard asserts ZERO DELETIONS, not "my rows survived".** `scripts/memory-append-check.sh` fails on any deleted line under `.claude/memory/` (R1) and on any edit to a root archive at all (R2). R1 is deliberately stronger than row-presence because row-presence has already reported a false success here: a branch's resolution kept every one of its own rows while a whole-file blank-line normalization silently collapsed four pre-existing double-blank runs elsewhere in `decisions.md`. Nothing of that branch's was lost — and the unrelated churn manufactured the next agent's conflict. Unrelated churn in the one file that IS the serialization point is the failure mode; the deletions column is what sees it.
- `2026-09-19` (TASK-415) — **`--no-renames` on the guard's `git diff`, on purpose.** A rename of a memory file removes every row from the old path, which is exactly what R1 exists to notice; letting git report it as a rename would hide it behind a 0/0 line count. Same reasoning for treating a `-` numstat column (git cannot line-diff the file) as a violation rather than a skip: zero-deletions is *unprovable* there, and an unprovable claim is not a passing one.
- `2026-09-19` (TASK-415) — **The escape hatch is a `Memory-Rewrite: <reason>` commit trailer, not a flag or an allowlist.** Deliberate maintenance — a hygiene pass, an archive consolidation, fixing a stale citation — genuinely has to edit an archive, and CI has no way to be told "this one is fine" out of band. A trailer is visible in the log, survives rebase, requires a deliberate act, and needs no CI configuration. It downgrades both rules to warnings rather than silencing them, so the waiver still prints what it waived. *Alternatives:* a `--allow-rewrite` flag (rejected — CI would have to decide when to pass it, which is the problem restated); a PR label (rejected — invisible from a local run).

- `2026-09-19` (TASK-415, review round 2, Minor — CONFIRMED, and it is the reason the probe is shaped as it is) — **The old-git probe omitted `separator=%x0A`, which the real command uses.** Git stops at the first option it does not understand, so any git that supported `key=` but not `separator=` would let the probe parse clean while the real command echoed literally — fail-OPEN, undetected, and invisible to the test shim (which trips on any `%(trailers:` argument, so probe and real trip together). The probe now carries the identical option string, differing only in the key, so anything that breaks one breaks both and correctness stops depending on a version-history fact neither of us could cheaply verify.
