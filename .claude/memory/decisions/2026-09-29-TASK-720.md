# TASK-720 workspace commit over ~3 MiB wedges persistence; end-of-turn refusal unseen

| Date | Decision | Rationale | Alternatives |
|------|----------|-----------|--------------|
| 2026-09-29 | Card premise CONFIRMED from code (not yet by a test at decision time; T0 is the repro): the runner commit is a JSON action with a base64 bundle under the 4 MiB `MAX_FRAME`; over it the host answers 413 (or the write ECONNRESETs and the client retries for up to 120 s), `commitNotifyWithResync` swallows every throw as `kept`, `baseline` never moves, and every later bundle is `baseline..main` so it still carries the big blob: permanent wedge. Deleting the file does not help | Read `commit-notify-resync.ts`, `git-workspace.ts` `commitTurnAndBundle`, `ipc-client.ts` retry classes, `dispatcher.ts` readJsonBody | - |
| 2026-09-29 | Ship the bundle over a NEW binary action `workspace.commit-bundle` (raw octet-stream body, `parentVersion`/`reason` as query params, same JSON answer), the same channel `blob.put` and the transcript actions use (100 MiB `MAX_BLOB_BODY_BYTES`). The JSON `workspace.commit-notify` stays registered, sharing one handler core, for sandboxes started by the previous release that outlive a host rollout | A 5 MiB file is an ordinary thing for a person to save; 100 MiB is the host's existing per-request budget for runner uploads, so no new cap is invented. A separate path mirrors how every binary action is declared (`checkContentType` keys on pathname) | Split one turn into several JSON commits (cannot split a single blob over ~3 MiB); accept both content types on one path (special case in the content-type gate); remove the JSON action now (an old sandbox mid-session would 404 and lose its work) |
| 2026-09-29 | Over the cap, fail LOUDLY rather than wedge: the runner checks the bundle size before sending, and a host 413 is treated the same; both answer `rolled-back` with a `hard` reset to baseline, a model-facing `rejectionReason`, and `rejectionCode: 'too-large'` | A `hard` reset is what every terminal refusal already does (`recoverable:false`), and it is the only rollback that stops the next turn re-bundling the same blob. Losing the turn's files is bad; losing every later turn's files silently is worse. Other 4xx keep today's `kept` (a 404 from an older host must not destroy work) | `mixed` rollback (files stay in the tree, next commit re-bundles them, refuses again every turn); drop only the oversized paths (needs per-path sizes the bundle does not expose) |
| 2026-09-29 | The commit answer's rejected branch gains an optional machine `code` (forwarded from the `workspace:pre-apply` veto's `code`, e.g. `storage-full`, TASK-719). The runner reports an end-of-turn refusal on `event.turn-end` as `saveRefused: 'storage-full' \| 'too-large' \| 'refused'`; channel-web forwards it on the `done` frame and the workspace view shows one fixed sentence per code under the reply | The end-of-turn commit runs before `event.turn-end`, with the reqId still bound, so the turn-end is the ordered, already-addressed carrier to the right stream. A lying runner can only pick one of three fixed sentences. The veto's prose is written for the model and never shown to a person (TASK-719) | Host-side hook from the commit handler (the IPC ctx reqId is restamped, so it cannot address the stream, and it races the turn-end); a `chat:turn-error` (it would close the stream as a failure and mark a finished reply as broken); a runner-authored text chunk (lands in the assistant's reply, vanishes on reload) |
| 2026-09-29 | Not in scope: the notice is live only (not persisted, gone after reload); the final/idle commit (after the last `turn-end`) still has no person channel and only logs; the model is not told next turn that its files were removed. Returned as follow-ups | The `chat:start` storage-full front door (TASK-690) still covers the persisted storage-full case on the next send; the final commit only catches work after the last reply ended | Persist a notice row (needs a new conversation event kind) |
| 2026-09-29 | Review round 1 found the notice never reached the person: a turn that used tools emits role='tool' then role='assistant' turn-ends under one reqId, and the SSE `done` subscriber closes on the FIRST. Fixed by putting `saveRefused` on BOTH turn-ends (an earlier test had asserted the assistant-only shape as correct). Kept `usage` assistant-only — that one IS metered | Each half was tested in isolation and passed while the seam lost it; a save can only be refused on a turn that wrote files, i.e. used tools, i.e. emitted the tool turn-end first | Make the SSE subscriber close only on the assistant turn-end (delays the done frame and re-opens the TASK-569 overlap subtleties); add a new event (overkill for one field) |
| 2026-09-29 | Review round 1 also found every `commit-notify` exit reporting `input.parentVersion`, stale after a re-sync re-pinned `refs/heads/baseline` to the host's advanced parent. All four exits now report `currentParentVersion` (equal before any resync). Two existing tests had pinned the stale value as expected | The caller tracks this version and the next turn's thin bundle is built against it; a stale one desyncs runner from host | Fix only the new `tooLarge` exit (leaves the pre-existing kept/rolled-back exits wrong) |
