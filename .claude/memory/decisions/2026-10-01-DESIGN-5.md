# Decisions — Design 5 workspace and memory attribution

- Today and agent chat compose the same `ChatComposer`; only Today supplies the agent selector. Both transcript and composer use the shared 900px content width. Sidebar and agent rail collapse independently, with separate compact-screen Sheets.
- The main Memory tab lists agent-wide memories, rather than the narrower profile subset. Conversation-specific learned rows remain a separate feed; starting a conversation does not change the scope of the shared list.
- Search candidates are not evidence of answer usage. `memory_recall` supplies evidence IDs and a recall ID; `memory_use` records only the IDs the model selects as supporting its answer. Selection must belong to that caller's agent, user, conversation and recalled pool. This adds a tool call/model round trip; token overhead has not been measured.
- Receipt storage version 2 distinguishes pending retrieval from confirmed usage. Version 1 receipts cannot establish which candidates supported an answer, so their chips are hidden rather than relabelled. Retrieval ranking and stored agent memories are unchanged. The answer association still uses the original recall timestamp.
- Conversation create, rename and delete share JSON and CSRF request headers. Ownership comes from the authenticated session, never a body field. The full channel-web integration fixture must provide `conversations:set-title` when the channel manifest declares it.
- Browser verification on the real local kind backend showed one supporting memory for an agent with 15 memories; the expanded chip showed the relevant row and persisted after reload. Internal recall IDs are excluded from activity-step details.
