# Decisions — TASK-1101 (MCP directory: "Find in directory" UI in Admin › Connectors, prefill into the editor)

Plan: `docs/plans/2026-11-09-TASK-1101-directory-ui-plan.md`. Design: `docs/plans/2026-11-09-mcp-directory-connectors-design.md`. Planner rows, 2026-11-09. Every "card said X" below was checked against the code on `56d441452`; the approved mock's copy was read from its source (`Main.dc.html`).

| Date | Decision | Rationale | Alternatives |
|------|----------|-----------|--------------|
| 2026-11-09 | **Every directory prefill starts with `keyMode: 'personal'`, whatever the listing's auth.** The card said `'workspace'` for key auth "to match what agent proposals default to". | Proposals have no auth-based default: `connector_propose` makes the agent pick (`tool-connector-propose/src/descriptor.ts:40-43`) and `listAuthoredProposals` maps anything else to `'personal'` (`lib/connectors.ts:452`). The editor's own default is `'personal'` (`RemoteMcpConnectorForm.tsx:148-150`), and the approved mock's Set it up starts on "Each agent adds its own key". A shared key is the wider grant (invariant 5), and `'workspace'` would make the admin type a key value before Add (`remoteErrors`). For an OAuth server the form forces `'personal'` anyway. | `'workspace'` for key listings (rejected: wider default, contradicts the mock, blocks Add on a value). |
| 2026-11-09 | **Prefill shape: one http server `{ name: connectorId, url, allowedHosts: [], credentials: [] }`; the key or sign-in slot goes in TOP-LEVEL `capabilities.credentials` with `server: connectorId`; no top-level `allowedHosts`; `packages` empty.** Key with `keyHeader` → `{ slot: newHeaderSlot(), kind: 'api-key', headerName, server }`; `'signin'` → `{ slot: 'MCP_OAUTH', kind: 'oauth', server }`; key without a header and `'none'` → no slot. The card nested the slots inside the server and put the URL host in its `allowedHosts`. | `prefillForRemoteForm` carries only top-level slots whose `server` names the leading server and turns a server's own hosts and slots into `leftOut` (`connector-request-prefill.ts:85-118`), so the card's shape would arrive as "This request also asked for: access to mcp.linear.app …" with nothing filled in. `remoteCapabilities` names the saved server after the connector id and adds the URL host on save (`remote-mcp-form.ts:181-236`), so the prefill uses the same name and leaves hosts out. Header slot names come from the one minting function (TASK-767). A key listing with no usable header gets no slot: a slot without `headerName` would also land in `leftOut`. | Card's nested shape (rejected, measured above). A placeholder header such as `Authorization` when none is listed (rejected: a guess dressed as the listing's claim). |
| 2026-11-09 | **`connectorId` = a slug the server accepts plus `-` and 8 random hex: lowercase, every run outside `[a-z0-9]` becomes one `-`, trim `-`, first 48 chars, trim `-` again, empty becomes `connector`.** Not `connectorIdFromName(title)`. | `connectorIdFromName` keeps `.` (`connector-form.ts:653-655`), but the server's rule is `^[a-z0-9][a-z0-9_-]*$`, 1-128 (`packages/connectors/src/store.ts:28,72-78`), and titles fall back to registry names like `com.stripe/mcp`. The remote form shows no id field, so a plain-slug clash (two "GitHub" listings, or a re-add) would strand the admin on a 409. The form's own new ids are `remote-<8 hex>` (`RemoteMcpConnectorForm.tsx:175-178`); a suffixed id is never a reserved one (`authored`, `directory`). | Plain slug (rejected: collisions with no way out). Changing `connectorIdFromName` (rejected: it also derives server names in `connector-form.ts:282,457`). |
| 2026-11-09 | **Auth copy says only what the listing says.** Row chips: `'key'` → "API key", `'signin'` → "Sign-in", `'none'` → no chip. Sheet "How people connect": key with header → "Needs an API key, sent in the X header…"; key without → "…You'll add the request header it goes in when you set it up."; none → "The listing doesn't mention a key. When you set it up, we'll check whether people need to sign in." The card and the mock said "No sign-in" (mock long form: "Anyone whose agent has it can use it."). | `'none'` only means "declares no required key" (contract doc, `packages/connector-directory/src/contract.ts:23-30`; TASK-1100 decisions). Notion, Linear, Stripe, Atlassian, Figma and Canva are OAuth servers that declare no headers, so "No sign-in" would be false on the most-searched listings, and the mock's long form reads like "no auth at all". The editor's discovery is what actually finds sign-in. | "No sign-in" (rejected: false). "No key listed" chip (rejected: a negative chip on most rows is noise and reads as "free to use"). |
| 2026-11-09 | **`'account'` publishers read "Community · X" (row) and "A community listing. It isn't checked against any company." (sheet). The UI never says "GitHub". Design doc Decision 5 is corrected to match (rule-5 stale line, Task 3).** | `'account'` also covers namespaces that are neither `io.github.*` nor a clean domain, with the raw namespace as publisher (`derivePublisher`, `packages/connector-directory/src/normalize.ts:195-212`), and the design's boundary review keeps the `io.github.*` scheme inside the plugin. A UI that reads `'account'` as "GitHub user" keys a generic field to one backend, which breaks for the named alternate impls (subregistry, curated list). The shield still appears only for an exact `'domain'`. | "Community · GitHub user X" (rejected: false for fallback namespaces). Parse `entry.id` for `io.github.` (rejected: registry vocabulary in the UI). |
| 2026-11-09 | **`enabled: false` hides the "Find in directory" button.** `ConnectorsTab` asks `searchDirectory('')` once on mount; the button renders only when the answer says `enabled`. If that check fails (network, 5xx) the button shows (fail open), and the subview has its own error state. A 404 reads as off (mock mode and older hosts). The subview still renders an off state if a later answer says `enabled: false`. | Turned off is an operator choice, so a button that leads to "turned off" is a dead end. The approved mock has no off screen. The empty-query call is cheap: one state-row read, no search (`packages/connector-directory/src/search.ts`, `searchDirectory`). | Always show the button and an off state inside (rejected: dead end). Hide while unknown and on error (rejected: a blip hides a working feature). |
| 2026-11-09 | **"Already in your connectors" = a client-side server-address match. While the subview is mounted it reads each connector's full record (`getConnector`, `/admin/connectors`, `Promise.allSettled`) and compares `serverAddressKey` = `protocol//host` (WHATWG, so case and the default port normalize) + path without trailing slashes + query. Exact path: same host with another path does not count. A record that fails to load is skipped (fail open). The row gets an "Added" badge and the sheet a disabled "Already in your connectors".** | The brief asked for detection "from data the tab already has", but `GET /admin/connectors` returns summaries with no capabilities (`packages/connectors/src/types.ts:328-340`). The agent rail's Add view already reads every connector's full record (`AddConnector.tsx:200-212`), so this follows an existing pattern. Reads happen only in the subview: the list view must stay at zero `getConnector` calls (`ConnectorsTab.test.tsx:627-635`). Many listings share one host (hosted platforms), so a host match would mark unrelated listings. A missed match only allows a duplicate connector, which is harmless with suffixed ids. The mock keyed this on provenance (`dirId`), which TASK-1102 records but nothing reads yet; an address match also catches hand-entered connectors. | Name match (rejected: free text). A host field on the connector summary (rejected: `url` vocabulary on the connectors list, invariant 1). Wait for provenance (rejected: no reader exists, and it misses hand-entered servers). |
| 2026-11-09 | **Provenance seam: `ConnectorPrefill.fromDirectory?: { directoryId: string; version: string }` is added NOW, set only by `prefillFromDirectoryEntry` (`entry.id`, `entry.version` verbatim). Its presence switches the editor's copy. It is NOT sent with the save. TASK-1102 adds it to the create body in `RemoteMcpConnectorForm.tsx` `submit()` (`const input = {…}`, about line 569) and flips the test that pins the create body's keys to exactly `capabilities, connectorId, keyMode, name, usageNote`.** | The field name and shape are the TASK-1102 card's own ("carries an opaque `fromDirectory: { directoryId, version }`"), so 1102 does not rename anything. This card needs a directory/request discriminator for honest editor copy anyway, so the field is read here, not parked. Sending it now would reach a route that doesn't accept it (half-wired). | A `source: 'directory'` flag now and `fromDirectory` later (rejected: two fields for one concept). Leave everything to 1102 (rejected: the editor would say "Filled in from the request"). |
| 2026-11-09 | **The data layer is a new module, `lib/connector-directory.ts`, not `lib/connectors.ts` as the card placed it. Its normalizer never upgrades trust: an unknown `publisherProof` becomes `'account'`, an unknown `auth` becomes `'none'`, a listing without `id`/`url` or with a non-https URL is dropped, `keyHeader` is kept only if it passes `headerNamePattern`, and `nextCursor` only if it matches the route's `^[A-Za-z0-9_-]{1,64}$`.** | `lib/connectors.ts` is already 680 lines; the directory has its own route and its own untrusted-input normalizer. The server already shapes the body (`shapeDirectoryBody`); this is defense in depth at the render boundary, so a server bug can't put a shield on a listing. Same posture as `listAuthoredProposals`' normalizer. | Inline in `connectors.ts` (rejected: size, mixed concerns). Trust the server's shape blindly (rejected: the shield is the lookalike defense). |
| 2026-11-09 | **Navigation: Set it up closes the sheet and opens the create editor over the still-mounted subview. Cancel returns to the subview with the query and results intact. A successful save returns to the connectors list. No toast and no "From directory" pill.** | The list is where the new connector appears, and that is the confirmation the existing create flows use (none of them toast). The mock's "From directory" pill needs provenance reads, which no card owns yet. | Stay in the directory after save (rejected: the admin can't see what they made). | 2026-11-09 | **Copy deviations from the mock:** the intro doesn't name "the MCP Registry" ("Search a public directory of services that work with agents…"), the never-synced text covers the first-load window, the stale text drops "every hour", the trust note says "The directory checks who published a server…" (not "We check"), the usage-note help is direct ("The listing's publisher wrote it, so rewrite it in your own words.") instead of "if the publisher's blurb doesn't fit", and the result count says "More than N servers match" while a `nextCursor` exists. The verified-only line already says the same thing as the cut footnote. | Mock copy verbatim (rejected where it is false or can go stale). |
| 2026-11-09 | **No Vite dev-mock route for the directory.** In mock mode `GET /admin/connectors/directory` reaches the mock's `:id` handler and 404s, the client reads that as off, and the button hides. | Component tests cover every state; the mock server is optional dev tooling.
