| 2026-09-21 | Put bounded Docker metadata probes behind the shared checked-start wrapper, immediately before the existing container start. | This preserves lazy preset startup and keeps unrelated unit tests Docker-free; imports do no probing. The real container start still runs and its errors remain unchanged. | No eager global hook, daemon restart, container removal, or new runtime dependency. |
| 2026-09-21 | Share one 45-second deadline across fixed version/info commands, with an 8 KiB output cap and no shell. | The deadline fits inside the existing Docker startup budgets; it rejects missing/failed/hanging metadata instead of allowing a bare hook timeout to be the first explanation. Diagnostic messages do not copy external stdout/stderr or error causes. | Caller overrides may shorten, not remove or extend, the deadline. This does not bound the subsequent container start or prove that it will succeed. |
| 2026-09-21 | Warn at 20 reported running containers without failing on that count alone. | This is an advisory heuristic, not a measured saturation capacity. Counts do not establish resource pressure or health-starting state, and a responding daemon can still fail to start a container. | Do not use docker ps emptiness as liveness, claim complete daemon health, or turn workload counts into a test-skipping policy. |
| 2026-09-21 | Execute a real consumer's startup expression against a fake builder and executable Docker stubs; separately scan literal constructor wiring with TypeScript ASTs. | This makes the old direct-start path fail behaviorally without inventing a missing-API failure. The scan catches unwrapped current sites and ignores comments/string literals; it is not whole-program analysis of arbitrary factories or shadowing. | Keep fixture constructor syntax assembled from tokens so existing raw-source image/budget guards do not mistake fixture text for real container usage. |
