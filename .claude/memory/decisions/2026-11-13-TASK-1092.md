# Decisions — TASK-1092 (`auth:find-user-by-email`)

Plan: `docs/plans/2026-11-13-task-1092-auth-find-user-by-email-plan.md`. Design: `docs/plans/2026-11-09-channel-slack-design.md` §1.2, §1.3, §6. Stack: `.claude/memory/decisions/2026-11-12-TASK-1091.md` (1091 → 1092 → 1093 → 1094, one squash with 1094).

| Date | Decision | Rationale | Alternatives |
|------|----------|-----------|--------------|
| 2026-11-13 | **Planner: the hook is `auth:find-user-by-email`, `{ email } → { userId } \| null`, registered by `@ax/auth-better` with a strict, nullable zod `returns` schema (`z.object({ userId: z.string().min(1) }).strict().nullable()`). Host-internal: no HTTP route, no IPC action.** | Card and design §6. Same shape as `auth:get-user` (`User \| null`). auth-better is the only auth plugin (auth-oidc was retired 2026-05-20), and `HookBus.registerService` throws `duplicate-service` on a second registrant, so the bus enforces one source of truth. `.strict()` makes an implementation that returns more than the id fail loudly (`invalid-return`) instead of having the extra keys quietly stripped. | Return `User` (leaks email and the admin flag). `{ userId: string \| null }` or a reason code (would tell callers why, a bigger enumeration surface). |
| 2026-11-13 | **"Approved sign-in domains" = `parseDomains()` of the `google` row's `allowed_domains`, read from `auth_providers` at call time WHETHER OR NOT the row is enabled. No row or a blank list means any domain. One predicate, `isDomainAllowed`, is shared with the sign-in gate (`assertDomainAllowed` delegates to it).** | Design §1.2 says "the same domain AX's Google sign-in allows", and §1.3 says the Slack bar is "the same bar as signing up for AX". The Google-login design (2026-05-20) fixes blank ⇒ open. One predicate means the two can't drift (invariant 4). Turning Google sign-in off must not widen who Slack can map. Reading the table means a failed handler rebuild (old instance kept) can't leave this check on a stale list. | Fail closed on a blank list (Slack DMs would then only work after restricting AX sign-up too, which contradicts §1.3). Only enabled rows, like `loadProviders` (toggling sign-in off would open the bar). The union of every provider's list (only Google's list is enforced at sign-in today). The handler's in-memory list (new plumbing, and stale after a failed rebuild). |
| 2026-11-13 | **The domain rule is checked on the STORED verified email, after the match, not on the input.** | The card's rule is about the account's verified email. It also removes any gap between JS and Postgres lowercasing of the two strings. | Check the input's domain first (saves a query on a miss; the hook is host-internal, so the timing doesn't matter). |
| 2026-11-13 | **Verified = `email_verified = true`.** The wizard admin can't be found until a Google or GitHub sign-in links and verifies it. Email/password sign-ups never can. Checked: better-auth's `update-user` refuses email changes (`EMAIL_CAN_NOT_BE_UPDATED`), and `/change-email` isn't enabled. **Re-check this hook if anyone ever enables `user.changeEmail`.** | Both sides have to have verified the same address before Slack identity becomes AX identity. Linking flips `email_verified` only when the stored email equals the provider's lowercased email (`better-auth/dist/oauth2/link-account.mjs:188`). | Accept unverified rows on an approved domain. That's unsafe: anyone can register a colleague's address through the open email sign-up API (finding A below). |
| 2026-11-13 | **Match with SQL `lower(email) = lower($1)`, `=` only, no trimming. More than one verified match → `null` plus a code-only `auth_find_user_by_email_ambiguous` warning.** | better-auth lowercases on sign-up and lookup, but `auth:create-bootstrap-user` stores the email as typed, and the `UNIQUE` on `email` is case-sensitive, so case variants can coexist. Using the same function on both sides avoids a JS/Postgres mismatch. `LIKE`/`ILIKE` read `%` and `_` as wildcards. Returning the wrong person's id is this hook's worst failure, so an ambiguous match fails closed. | JS `toLowerCase()` on the input only (misses mixed-case stored rows). `ILIKE`. Pick the oldest row (could hand one person's agent to another). A migration that normalizes emails or adds a unique `lower(email)` index (hard to reverse, for a case today's code paths don't produce). |
| 2026-11-13 | **No `lower(email)` index (YAGNI).** | A company-sized users table makes a sequential scan cheap. TASK-1094 may call the hook on every channel message; add the index only if that shows up as a measured hot path. | Add a functional index now. |
| 2026-11-13 | **Input: `email` must be a string of 1–320 characters (`MAX_EMAIL_LEN`), else `invalid-payload` with fixed text that never echoes the value. A malformed string with the right type just finds nobody (`null`).** | The address comes from Slack's API through host code, so it's external data and PII. This is the same rails as `auth:create-bootstrap-user`. | Return `null` on a type error (hides caller bugs). A zod input schema with zod's own messages (the wording could change and leak). |
| 2026-11-13 | **`zod` `^3.23.8` joins auth-better's dependencies.** It resolves to the locked, patched `3.25.76` (GHSA-mrhx-c7xc-m3w5 patch), and the lockfile diff must be the importer entry only. | `registerService`'s `returns` is a `ZodType`. `^3.23.8` is the repo-wide range, so pnpm reuses the existing resolution and nothing new enters the supply chain. | An exact pin (the repo doesn't do that for zod outside routines-contract). |
| 2026-11-13 | **"Registered with a returns schema" is pinned by a spy on `HookBus.prototype.registerService`, installed before boot, that `safeParse`s the captured `opts.returns`.** | It proves both that the schema is attached and what it admits. An exported-schema unit test wouldn't prove registration. | Export the schema and unit-test it. Rely on review. |
| 2026-11-13 | **An ipc-core test pins that no `DISPATCHER_DEPENDENCIES` entry (required, optional or dynamic prefix) is an `auth:` hook.** | Design §6's mitigation for the account-existence oracle is "never an IPC action". `dependency-sync.test.ts` already forces every hook a handler reaches into that list, so the two tests together cover the whole runner surface. The guard is all of `auth:`, because `auth:get-user` returns email and the admin flag too. | Rely on review (a silent regression). Guard only this one hook name. |
| 2026-11-13 | **Timing and enumeration posture: host-internal, no constant-time work, and `null` never says which rule failed.** Caller contract (written into types.ts and the PR): pass only an email the caller fetched from the identity provider itself (Slack `users.info`), never one taken from message text or a slash-command argument. | The only party that could time it or enumerate with it is host code. Slack users can only make channel-slack ask about their own verified address. | Constant-time work (two queries every time, padding): no attacker can observe host timing. |
| 2026-11-13 | **Rule-5 stale-line fix, design `2026-11-09-channel-slack-design.md`:** §1.2:24-25 "a verified `@<approved domain>` email. That's the same domain AX's Google sign-in allows" becomes the list meaning (the Google provider's *Allowed email domains*; blank = any domain). §6:313 "Tier-3 attended turns" becomes "Attended channel turns (§2)". | These lines made the card read as one fixed domain. "Tier-3" isn't defined anywhere in the design; in that doc, Tier 2 and Tier 3 are Slack's API rate tiers. Card TASK-1094 also says "each tier". | Leave the doc (1093/1094 planners would plan from it). |
| 2026-11-13 | **Not done (YAGNI), with reasons:** an "approved domain?" answer for Slack members with no AX account (its first caller is 1094); caching the domain list; any HTTP surface; logging hits or misses. | Not load-bearing for this card. The stack squashes at 1094, so a second auth hook added there costs nothing in merge terms. | Build them now. |
| 2026-11-13 | **Learning for TASK-1093/1094.** (1) `null` means "no AX account we can vouch for": no account, unverified, off-domain or ambiguous. It doesn't mean "not an employee". (2) Channel-slack can't read the approved domains, and this hook only answers for people who have an AX account. TASK-1094's external admission (§2, any full company member) needs a separate answer from auth: add an auth hook in that card. Never copy the domain list into channel-slack config (invariant 4). (5) Pass the sender's `users.info` email, never message text. | So 1093/1094 plan from the real contract. | — |
| 2026-11-13 | **Out-of-scope FINDING A (from reading the code, not tried against a live host): email/password sign-up is open over the API.** `handler.ts:200` sets `emailAndPassword: { enabled: true }` with no `disableSignUp`. `POST /auth/sign-up/email` (no UI) creates an unverified user and an `ax_auth_session` for ANY address, and `social-signin.test.ts:206-237` shows it doing exactly that. The domain gate only covers `/callback/google`, and the CSRF gate only needs `X-Requested-With: ax-admin` or a trusted `Origin`, both of which a script can send. That contradicts `deploy/charts/ax-next/SECURITY.md:466` ("On canopyworks.ai sign-up is limited to canopyworks.com accounts") and the 2026-10-03 launch decision. Combined with `accountLinking.trustedProviders: ['google','github']` + `requireLocalEmailVerified: false`, it also allows **account pre-hijacking**: register a colleague's address with a password before their first Google sign-in; Google then links into that row and verifies it, and the password still works. This hook doesn't widen either one (it only returns verified rows, and a pre-hijacked row is the owner's own account), but Vinay should decide on a card (e.g. `disableSignUp: true`; the wizard admin is a direct insert and doesn't use sign-up). | Severity calls belong to a human. This card doesn't touch sign-up. | Fix it here (scope creep on a stacked PR; it changes a security boundary that has its own tests). |
| 2026-11-13 | **Out-of-scope FINDING B: the admin "Allowed email domains" field is shown for every provider kind, but only Google's list is enforced.** `AddProviderForm.tsx:154-170` shows the field and the hint "List your own domains to keep it to your organisation" for google, github and oidc. `handler.ts:190-192,311` only gates Google, so a GitHub list is silently ignored. This hook follows the enforced (Google) list. | An admin who sets a GitHub list believes sign-up is restricted, and it isn't. | Make this hook honour every provider's list (it would then disagree with what sign-in actually enforces). |
| 2026-11-13 | **Builder: accept the lockfile's peer-key renames** from adding `zod` to auth-better (7 `@better-auth/*` snapshot keys re-keyed `better-call@1.4.0(zod@4.6.7)` → `(zod@3.25.76…)`). | Measured: no `resolution`/`integrity` line changed and the set of package@version entries is identical before/after; better-auth still links zod 4.6.7 at runtime; both zod guard test files pass. The renames are pnpm's peer bookkeeping, not a supply-chain change. | Drop zod + the `returns` schema (contradicts the ARCH-13 schema rule and this card's own decision). |
