# Decisions — TASK-817 (a provider 401 on a stored, unexpired OAuth token)

| Date | Decision | Rationale | Alternatives |
|------|----------|-----------|--------------|
| 2026-10-04 | **Card premise corrected: the state is `needs-reconnect` (the TASK-741/756 marker), not `needs-sign-in`.** | `needs-sign-in` (TASK-795) means "`credentials:has` finds no row", and a revoked token is still a PRESENT row. needs-reconnect already means "you signed in, it is no longer accepted", with the rail's red icon + Reconnect, the details view's "Sign-in expired", and chat's `connector-needs-reconnect` (TASK-783). Chat's `connector-needs-sign-in` has been replay-only since TASK-806. | Delete the token on 401 so presence says absent (loses a refresh token that may heal it; a third-party 401 could wipe a team's shared sign-in). Read inventory `needs-auth` in `healthOf` (stale after sign-in; also what a never-signed-in connector reports, which is why TASK-741 refused it). |
| 2026-10-04 | **Root cause: the resolver trusts the clock.** An unexpired token returned early (`resolver.ts` `valid`), so nothing ever wrote the marker for a token the provider revoked. Fix: `credentials:get {rejected: true}` → `credentials:resolve:<kind> {rejected: true}` → the mcp-oauth resolver renews instead of answering. A refused renewal is the existing NeedsReconnectError + marker, on the token OWNER. | Renewing is the remedy the resolver already owns. The vault walk (findRow) knows the row's scope, so the marker lands on the right owner (agent for a shared sign-in). A mcp-oauth-only "mark this" hook would not know the scope. | New `mcp-oauth:token-rejected` hook (owner unknown to the caller). |
| 2026-10-04 | **While a marker stands, an UNEXPIRED token is not answered as-is: the resolver renews it (one indexed `hasNeedsReconnect` read, only for valid-by-clock tokens; a failed read counts as unmarked).** | Without this, the next chat turn's `proxy:open-session` resolves the same refused token and the session silently lacks the tools. With it, the turn fails as `connector-needs-reconnect`, or heals if the provider recovered. The marker is written ONLY when an authorization server refused us, so a marked valid token is known-dead. | Throw NeedsReconnectError straight from the marker (no self-heal). No read (the chat path stays silent). |
| 2026-10-04 | **A rejected read never shares, nor runs beside, an in-flight ordinary read of the same row; ordinary reads arriving during a renewal share it.** | Sharing would return the refused value. Running in parallel could double-spend a rotating refresh token, and a reuse rejection would write a FALSE marker. | Separate mutex key (parallel refreshes). |
| 2026-10-04 | **Only a 401 is `rejected` (not 403); only servers that got an OAuth bearer renew; one renewal + one re-list per server per check.** A renewal that throws after the server was asked answers `needs-auth` (never `credential-unavailable`, which means "nothing was sent"). | A 403 is an accepted credential that is not allowed to do this, so renewing cannot help. API keys cannot be renewed. No loop. | Renew on 403 (wasted refreshes). |
| 2026-10-04 | **Details view: a `needs-auth` tool read under a row the list calls `ok` re-reads the list once per tool read (`onHealthStale` → `refresh`).** | The details view's tool read is where the walk first saw the 401, and that check writes the marker; the row's health comes from the list. Once per read object, so a connector that stays needs-auth with no marker (403, nobody signed in) never loops. Complements TASK-812 (re-reads tools when the row's health changes). | Add `health` to the tools route (a second health source). |
| 2026-10-04 | **Out of scope, follow-up: detection inside the runner.** A chat-only user whose SDK gets the 401 on `initialize`/`tools/list` is still silent: `agent-claude-sdk-runner` ignores `system/init`'s `mcp_servers` status. | Needs a runner→host signal (new IPC surface + boundary review). Host-side detection covers the rail, details, Retry and every check, and the chat path reports from the next turn after any of them. | Build the IPC now (doubles the card). |
| 2026-10-04 | **Implemented inline, not one subagent per task.** | Four small, tightly coupled edits across 4 packages (TASK-783 precedent). Each step was test-first and red before the fix. | Subagent per task. |
