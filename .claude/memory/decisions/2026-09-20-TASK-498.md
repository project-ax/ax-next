# TASK-498 — a failed turn made legible and durable in the agent view

## `agent:invoke` ran on the HookBus default timeout (120 s) against a 10-minute chat timeout

`packages/chat-orchestrator/src/plugin.ts` registered `agent:invoke` with no
`timeoutMs`, so it used `DEFAULT_SERVICE_TIMEOUT_MS = 120_000`, while
`DEFAULT_CHAT_TIMEOUT_MS` is `10 * 60 * 1000`. **Every turn longer than two
minutes had its `bus.call('agent:invoke')` rejected while the turn was alive and
streaming.** Nobody noticed because channel-web dispatches fire-and-forget and
only logged the rejection (`chat_run_dispatch_failed`).

It is now `chatTimeoutMs + AGENT_INVOKE_TIMEOUT_SLACK_MS (60 s)` — strictly after
the orchestrator's own bound, so a rejection means "the handler never settled".
**The `exceeded 120000ms` line in a walk report is very likely this, not a hang.**
TASK-505 ("agent:invoke hangs 120s") is probably the same number.

## `conversations:get`'s `displayEvents` had no reader anywhere in the repo

Persisted since TASK-66 (`turn-error` + `permission-card` host-only display
events), projected on every read, and `grep -r displayEvents packages` outside
`@ax/conversations` returned **nothing** on 2026-09-20. The chat shell does not
read it either. So Fault A (#137/#138) only ever solved the LIVE half; no
surface has ever replayed a failure after a reload. `buildThread` in
`routes-workspace.ts` is now the first consumer.

## The workspace roster's `working` meant "a sandbox is up", not "a turn is running"

`deriveState` probed `session:is-alive` over each conversation's
`activeSessionId`. But `chat:turn-end` clears `active_req_id` and **deliberately
keeps** `active_session_id` (TASK-124 warm reuse), and the session row stays
`terminated = false` until the reaper. So every agent that had ever answered
anything read **"Working"** until the pod was reaped — through reloads and host
restarts. It now reads `agent-activity:get`, which `@ax/agent-activity` sets on
`chat:start` and clears on `chat:end` AND on `chat:turn-error`. `session:is-alive`
left channel-web's manifest entirely.

## Pattern: the wire carries the reason CODE, the client owns the words

`ThreadMessage` gained `{ kind: 'error', id, reason, detail?, at }` — `reason` is
the same backend-agnostic code the SSE `error` frame carries, and
`lib/turn-error-labels.ts` (now exporting `turnErrorText(reason, detail)`) turns
it into a sentence on BOTH paths. Same idiom as `phase`. The fold key `reqId` is
kept off the wire; it appears only inside the opaque row id `turn-error:<key>`.
